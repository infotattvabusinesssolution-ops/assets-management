Standard Asset360 UI design convention for all screens 
Backgroun: White 
All text/words: Black, including headings, labels, table content, menus and navigation
Primary accent: Purple
Icons: Purple or black
Buttons: Purple with white text where needed for primary actions; secondary buttons white with black text/purple border
Selected tabs/navigation: Light purple background with black text
Tables/cards: White with subtle light-grey borders
Dropdowns and filters: White background, black text, purple outline/highlight
Status indicators: Small status badges may use green/red/amber for functional status identification, while their text remains dark/black where readable
No dark sidebar or dark shaded panels
Overall style: Clean, professional enterprise UI with consistent spacing, rounded controls and minimal visual clutter.
The Asset360 Web Login Screen
The Asset360 Login Screen provides a secure and user-friendly entry point to the Asset Management platform, supporting standard username and password authentication together with Single Sign-On (SSO) using organizational credentials. The screen provides password recovery, Remember Me, language selection, and support access while ensuring authenticated users are directed to functionality based on their assigned roles and permissions. The login interface also introduces Asset360’s core capabilities, including complete asset lifecycle management, Real-Time Location Tracking (RTLS), RFID and barcode-based identification and tracking, Auto Discovery of IT assets, maintenance management, and reports and analytics, giving users a clear overview of the platform’s capabilities before accessing the system.
Dashboard – Developer Functional Description
The Asset360 Dashboard shall be developed as the primary landing screen after successful user authentication and shall provide a consolidated, role-based, near-real-time view of the asset portfolio and activities accessible to the logged-in user. The dashboard shall retrieve data according to the user's assigned company/legal entity, business unit, department, site/location and role permissions and display configurable KPI cards for Total Assets, Assets In Use, Assets Under Maintenance, Overdue Maintenance, Pending Disposal, Pending Approvals and other exception counts. Each KPI card shall be interactive and act as a drill-down filter; for example, selecting Under Maintenance shall navigate to the corresponding asset/work-order list pre-filtered to that status. The screen shall provide dashboard tabs such as Overview, Asset Health, Maintenance, Location & Movement, Financials and Compliance, with widgets displaying Assets by Category, Assets by Location, Asset Status/Condition, Maintenance Status, Asset Movement Trends, Top Asset Types, Warranty/Contract Expiry, depreciation or asset-value summaries, RFID/RTLS location exceptions and Auto Discovery reconciliation status where the user has access to those functions. Charts and widgets shall support drill-down navigation so selecting a chart segment, location, category or status opens the corresponding detailed records with the selected criteria retained. A configurable date-range filter shall refresh applicable KPIs and trend widgets, while global search shall allow navigation to assets using Asset ID, barcode/QR/RFID tag, serial number, description or location. A right-side information area shall display Recent Activities, Upcoming Maintenance, Alerts & Notifications and Pending Actions, with each record clickable to open the related asset, work order, transfer, approval, audit, disposal or maintenance transaction. The dashboard shall also provide Quick Actions such as New Asset Registration, My Assets, Asset Transfer, Maintenance and Reports, subject to role permissions. Data should be loaded through reusable dashboard APIs/services rather than hard-coded widget logic, with each widget supporting loading, empty-data, error and refresh states. The UI shall use the established Asset360 white background, purple primary actions/icons, dark headings and light-grey card borders, remain responsive for standard desktop resolutions, and preserve the common left navigation and top header. The intended user maneuvering shall follow Dashboard → Review KPI/Alert → Select Card or Widget → Drill Down to Filtered Records → Review Detail → Perform Authorized Action → Return to Dashboard, making the Dashboard the operational command center for monitoring asset health, maintenance, movement, RFID/RTLS, Auto Discovery, financial and compliance activities across Asset360.
The Asset360 Sidebar provides a consistent, role-based navigation framework for accessing the complete asset lifecycle from a single interface. It organizes functionality into logical operational areas including Dashboard, Assets, Receiving & Tagging, Tracking & Location, Auto Discovery, Assignment & Movement, Verification & Audit, Maintenance, Finance, Contracts & Compliance, Disposal, Reports & Analytics, Master Data, Administration and Audit Log. Expandable menus allow users to access detailed functions without overcrowding the workspace, while the active module is clearly highlighted in Asset360 purple. Menu visibility and available actions can be controlled according to the user’s role, company, business unit, site and assigned permissions, providing a clean and secure navigation experience across the platform.
The Assets Screen serves as the primary operational workspace for managing Asset360’s centralized asset register. It provides real-time KPI summaries such as Total Assets, In Service, Assigned, In Store, Under Maintenance, Missing/Not Found, Untagged and Pending Approval, together with advanced search and filters for company, site, category, status, condition and custodian. Users can search assets using Asset ID, barcode/QR/RFID tag, serial number, description, custodian or location and access detailed records showing classification, ownership, physical location, condition and lifecycle status. Authorized users can create new assets, perform bulk uploads, edit records, manage asset hierarchies and approvals, and initiate related actions such as assignment, transfer, RFID tagging, map/RTLS location, verification, maintenance and disposal. Selecting an asset provides a consolidated Asset 360° view, bringing together identification, financial, location, custody, maintenance, warranty, Auto Discovery, documents, transactions and complete audit history within a single authoritative asset record.
Note : User Permissions determine which actions appear per user .
New Asset Registration Module – Developer Functional Specification
A major UX  would be to open a right-side Asset 360° drawer when the user clicks an asset rather than immediately leaving the Asset Register.
The New Asset Registration Module in Asset360 provides a controlled, structured process for creating a complete asset record and establishing the asset as part of the organization's official asset register. The screen should capture the asset's unique identity, classification, manufacturer/model information, organizational ownership, physical location, custodian, acquisition and financial information, warranty, maintenance requirements, barcode/RFID identification, supporting documents and, where applicable, Auto Discovery information. Asset classification should follow the configurable Asset Group → Class → Category → Subcategory hierarchy, while location should follow the organization's configured structure such as Company → Business Unit → Department/Cost Center → Site → Building → Floor → Room/Zone/Storage Area. This reflects the FSD requirement for a single authoritative asset record containing identification, classification, organizational, location, acquisition, financial, maintenance, compliance and system/discovery information. 
The registration process should support manual creation, barcode/QR scanning, RFID association and Auto Discovery-based creation, with configurable mandatory fields, duplicate validation and master-data-driven dropdowns. New or modified asset records can be routed through QA and Asset Approval before activation; the supporting WaveTrack specification specifically calls for completeness/correctness checks, QA comments and correction requests followed by final authorization and activation. The user should therefore be able to Save as Draft, Submit for Approval, Save Asset, or cancel the transaction depending on the configured workflow and permissions.
My Assets Module – Developer Functional Specification
The My Assets Module shall be developed as a personalized, role-based workspace within Asset360 that displays assets currently or historically associated with the logged-in user. The module is intended primarily for employees, custodians and department users to view assets under their responsibility and perform permitted self-service transactions without accessing the complete organizational Asset Register. The screen shall retrieve asset information based on the authenticated User ID, Custodian/Employee ID, organization and applicable data-access permissions and shall provide current asset identification, assignment, location, condition, maintenance, tagging and transaction information.
1. Screen Initialization and Data Retrieval
When the user opens Assets → My Assets, the application shall identify the authenticated user and retrieve assets where the user is the current custodian, assigned employee, responsible person or authorized department representative. The backend should return only records permitted by the user's company, business unit, department, site and role scope. The screen shall not retrieve the complete enterprise Asset Register and filter it only at the browser level; filtering must be enforced through the backend/API and SQL query layer.
The initial response should provide the asset list together with summary counts required for KPI cards, including My Assets, In Use, Under Maintenance, Action Required/Overdue and Pending Return.
2. My Assets Summary Cards
The screen shall display interactive KPI cards providing a summary of the logged-in user's asset portfolio. Each card shall function as a quick filter. For example, selecting Under Maintenance shall refresh the register to display only the user's assets currently undergoing maintenance, while selecting Pending Return shall display assets associated with an active return transaction.
The selected KPI filter should remain active until cleared or another lifecycle tab/filter is selected.
3. Lifecycle Navigation Tabs
The screen shall provide lifecycle tabs such as:
Currently Assigned | Under Maintenance | Pending Return | Returned | Requested | History
The tabs shall retrieve records according to the corresponding assignment or transaction status. Currently Assigned represents active custody; Under Maintenance identifies assigned assets with active maintenance activities; Pending Return represents initiated but incomplete returns; Returned provides previously returned assets; Requested displays asset requests initiated by the user; and History provides historical custody and transaction records.
Counts should preferably be returned by the backend so that the UI does not calculate lifecycle totals from only the currently loaded page.
4. Search and Filtering
The module shall provide a search field capable of finding the user's assets using Asset ID, Asset Name/Description, Serial Number, Barcode, QR Code and RFID Tag/EPC. Additional filters should include Category, Asset Type, Status, Condition, Location, Manufacturer, Model and Assigned Date.
More Filters may expose additional criteria without overcrowding the default screen. Search, filtering, sorting and pagination should be performed server-side.
For example:
GET /api/my-assets?userId={currentUser}&status=IN_USE&categoryId=12&search=AST-00128&page=1&pageSize=20
The API should derive the effective user identity from the authenticated session/token rather than trusting a client-supplied User ID for security-sensitive filtering.
5. My Assets Register Grid
The main register shall display configurable columns such as:
Asset ID | Asset Image | Asset Name | Category | Tag/RFID | Serial Number | Location | Status | Condition | Assigned Date | Actions
The Asset ID and Asset Name should be clickable. Selecting either should open the Asset 360° quick-view panel.
Status and condition shall use visually distinct badges such as In Use, Under Maintenance, Pending Return, Returned, Good, Fair or Damaged. The values themselves should originate from controlled master/status data rather than free-text values.
The grid shall support server-side sorting, pagination and configurable page size, such as 10, 25, 50 or 100 records per page.
6. Asset 360° Quick View
Selecting an asset shall open a right-side Asset 360° drawer without navigating away from the My Assets Register. The drawer should retrieve detailed information only for the selected Asset ID and provide tabs such as:
Details | Location | Maintenance | History
The Details tab should contain Asset ID, Serial Number, Barcode/QR/RFID EPC, Category, Manufacturer, Model, Status and Condition. Location should show Company/Site, Building, Floor, Room, Department, Cost Center and current Custodian. Maintenance should display warranty status, next service date, maintenance type, active work orders and applicable checklist. History should show relevant assignment, transfer, return and maintenance transactions.
Closing the drawer must return the user to the same list position, filters and pagination state.
7. Context-Sensitive Asset Actions
Each asset row shall provide a three-dot Actions menu. The actions displayed must be determined dynamically from the asset's current lifecycle status, available technology and logged-in user's permissions.
Typical actions shall include:
View Asset 360° | Acknowledge Receipt | Request Transfer | Request Return | Report Issue/Damage | Locate on Map | RFID Locate | View Maintenance | View Documents | View Assignment History
For example, Acknowledge Receipt should only be displayed when an assignment requires acknowledgement; Request Return should only apply to an active assignment; RFID Locate should only appear when a valid RFID tag is associated with the asset and the relevant RFID capability is available.
8. Asset Acknowledgement
When an asset is newly assigned to a user and acknowledgement is required, Asset360 shall display an acknowledgement action. The acknowledgement screen/dialog should display the asset, assigned date, assigned by, condition, location and accessories where applicable.
On confirmation, the backend shall record the User ID, Asset ID, Assignment ID, acknowledgement status, date/time, condition and remarks. The acknowledgement should become part of the permanent assignment history.
If the user identifies a discrepancy, they should be able to reject/report the discrepancy instead of acknowledging the asset.
9. Request Transfer
Request Transfer shall allow the current custodian to initiate movement of an asset to another authorized employee, department or location. The transaction should capture the asset, current custodian/location, proposed custodian/location, reason, requested date and remarks.
The request shall be submitted into the configured approval workflow rather than immediately changing the Asset Master. The asset's current assignment must remain unchanged until the transfer is approved and completed.
Once completed, the system shall close the previous assignment, create the new assignment/location record and write the movement to transaction history.
10. Request Return
Request Return shall allow a user to initiate return of an assigned asset. The form should capture return reason, proposed return location/store, asset condition, accessories, remarks and optional evidence.
Submitting the request shall create a return transaction with a status such as Pending Return. The asset shall remain assigned to the current user until the receiving/asset-management team physically verifies and completes the return.
After completion, the backend shall close the user's custody record and update the asset's appropriate lifecycle/location status.
11. Report Issue or Damage
Users shall be able to report problems directly from My Assets. The form should capture Issue Type, Severity, Description, Asset Condition, Date Reported, Photographs/Documents and whether the asset is unusable or requires maintenance.
Depending on configuration, submission may automatically create a maintenance request/work order or send the issue for review by the maintenance/asset team.
The issue reference and current status should subsequently be visible against the asset.
12. Map and RFID Location
Where applicable, Locate on Map shall open the asset's configured or most recently confirmed location within the Asset360 mapping component. The displayed position should be derived from the current location record or available tracking information.
For RFID-enabled assets, RFID Locate may provide the available RFID location information or invoke the applicable RFID locating workflow. The My Assets screen should consume these services rather than implement separate location logic.
13. Maintenance Integration
Selecting View Maintenance shall show the selected asset's current and upcoming maintenance information, including next preventive maintenance date, open work orders, maintenance status and recent service history.
If an assigned asset is currently under maintenance, the My Assets Register should reflect this using the Under Maintenance status and provide access to the associated maintenance record where permissions allow.
14. Documents
The user shall be able to view authorized documents associated with their asset, such as user manuals, warranty information, assignment documents, certificates and asset photographs. Document access must respect document-level and role-based permissions.
Users should not automatically receive permission to modify controlled asset documents simply because the asset is assigned to them.
15. Request Asset
The Request Asset button should provide a controlled method for employees to request a new or replacement asset. The request may capture Asset Category/Type, required date, business justification, department/cost center, preferred specifications and remarks.
Submission should create an asset request and route it through the configured approval workflow. Approved requests can subsequently feed the procurement, receiving or asset-assignment process rather than creating an Asset Master record directly.
16. Backend and SQL Considerations
The My Assets screen should primarily retrieve information by joining the central Asset record with current assignment/custody, employee/user, location, category/model, tag/RFID, maintenance, document and transaction-history data. The exact table names should follow the final Asset360 database design rather than being hard-coded from the UI specification.
For performance, the developer should provide separate optimized API operations for the register, KPI counts and Asset 360° details. Appropriate SQL indexes should be maintained on commonly queried fields such as Asset ID, Custodian/Employee ID, Assignment Status, Asset Status, Tag ID/EPC, Serial Number and Location ID.
All queries must use parameterized SQL/ORM operations and enforce tenant/company and role-based data scope at the backend.
17. Audit and Security
Every transactional action initiated from My Assets—including Acknowledgement, Transfer Request, Return Request, Issue Reporting and Asset Request—shall create an auditable transaction containing the user, asset, transaction type, previous state where applicable, new/requested state, timestamp and remarks.
The frontend shall hide unauthorized actions for usability; however, the backend API must independently validate authorization. Hiding a button is not sufficient access control.
Navigation Flow
The recommended maneuvering for the module is:
Login → Dashboard → Assets → My Assets → Review KPI/Lifecycle Tab → Search or Filter → Select Asset → Open Asset 360° Quick View → Review Details/Location/Maintenance/History → Select Required Action → Complete Request or Transaction → Receive Confirmation → Return to My Assets with previous filters retained.
This approach makes My Assets the employee's personal asset self-service workspace while the Asset Register remains the administrative workspace for managing the organization's complete asset portfolio.
Asset Edit / Update – Developer Functional Specification
The Asset Edit / Update function shall allow authorized Asset360 users to search and select an existing asset and modify permitted asset information while maintaining data integrity, approval controls and complete change history. When an asset is selected, the system shall load its current information across Basic Information, Technical Details, Location & Ownership, Financial & Warranty, Maintenance Setup, Tagging & Identification, Auto Discovery, Additional Information and Documents. Fields shall be dynamically configured as editable, read-only or hidden based on user role, asset status and field-level permissions. The system shall validate all modified values against applicable master data and business rules, including mandatory fields, valid category/model relationships and uniqueness of Asset ID, Serial Number, Barcode/QR and RFID EPC where applicable. Controlled transactions such as custodian changes, physical location transfers, RFID/tag replacement, disposal and maintenance execution should not directly overwrite the Asset Master; instead, the user should be redirected to the corresponding Asset360 transaction workflow so that movement and lifecycle history are preserved. When the user selects Submit Changes, the application shall compare the original and modified values, perform server-side validation and either update the asset immediately or create an Asset Change Approval request depending on configured approval rules. Approved changes shall update the current Asset Master and related records, while rejected changes shall leave the existing asset information unchanged. Every successful modification shall create an audit record containing Asset ID, changed field, previous value, new value, changed by, date/time and approval reference where applicable. The screen should provide Save as Draft, Submit Changes, Cancel/Back to Register, View Asset 360° and View Change History actions and retain the user's Asset Register search/filter state when returning to the register. The recommended navigation flow is Asset Register → Search/Select Asset → Asset Edit/Update → Review Current Information → Modify Authorized Fields → Validate → Submit → Approval if Required → Update Asset Record → Audit Log → Confirmation.
Bulk Upload – Developer Functional Specification
The Bulk Upload Module shall allow authorized Asset360 users to create or update multiple asset records in a single transaction using a predefined Excel/CSV template. The screen should provide actions to Download Template, Upload File, Validate Data, Preview Records and Submit Upload. During validation, the backend shall check mandatory fields, master-data references, data formats, duplicate Asset IDs, Serial Numbers, Barcode/QR values and RFID EPCs, and identify invalid company, location, category, model, custodian or financial references before any record is committed. The validation result should clearly classify rows as Valid, Warning or Error, with downloadable error details containing row number, field name and reason for failure. Users should be able to correct the source file and re-upload it without creating partial or duplicate records. On final submission, only validated records shall be processed, preferably within controlled database transactions, and the system should return a summary such as Total Rows, Successfully Created, Successfully Updated, Failed and Skipped. Where asset approval is configured, successfully uploaded records should enter the applicable QA/Asset Approval workflow rather than being immediately activated. Every bulk upload must generate a batch reference and audit trail containing file name, uploaded by, upload date/time, total records, successful/failed counts and resulting Asset IDs. The recommended flow is Bulk Upload → Download Template → Populate File → Upload → Server Validation → Preview Errors/Valid Records → Correct if Required → Submit → Create/Update Assets → Approval if Required → Display Upload Summary and Audit Reference.
Asset Hierarchy – Developer Functional Specification
The Asset Hierarchy Module shall allow authorized users to define, view and manage the structural relationship between assets within Asset360 using a parent–child hierarchy. The screen should provide a searchable tree structure such as Parent Asset → Sub-Asset → Component → Sub-Component, enabling users to expand or collapse nodes and select any asset to view its Asset ID, description, category, status, location, custodian and condition. Users with appropriate permissions shall be able to Add Child Asset, Assign/Change Parent, Remove from Hierarchy and View Asset 360°, with backend validation preventing duplicate relationships, circular references and assignment of an asset to itself. Moving an asset within the hierarchy should update only its hierarchy relationship and must not automatically change its physical location, custodian or financial ownership unless a separate approved transaction is performed. The system should maintain the relationship using Asset ID and Parent Asset ID or a dedicated hierarchy table and retain effective dates/history where required. All hierarchy additions, removals and changes shall be recorded in the Audit Log with the previous and new relationship, user and date/time. The recommended navigation flow is Assets → Asset Hierarchy → Search/Select Parent Asset → Expand Hierarchy → View Child/Component Assets → Add or Modify Relationship → Validate → Save → Refresh Hierarchy → Audit History.
Asset Approval Screen – Functional Description
The Asset Approval Screen shall serve as the centralized approval workspace within Asset360 for reviewing and processing asset-related transactions generated from configured dynamic workflows. The screen should display approval requests relevant to the logged-in approver and provide tabs such as Pending Approvals, My Requests, Approved, Rejected and All Requests. Each request should show key information including Request Number, Transaction Type, Asset ID, Asset Name, Requested By, Request Date, Current Approval Level, SLA/Due Date and Status. Users should be able to search and filter requests by Asset ID, request number, transaction type, status, requester and date range. The screen should support approval transactions originating from New Asset Registration, Asset Edit/Update, Asset Assignment/Transfer, Tag Replacement, Financial Changes, Disposal and other configured Asset360 processes.
When the approver selects a request, the screen should open an Approval Details area showing the asset information, request details, supporting documents and reason for the request. For transactions that modify an existing asset, a Current Value vs Proposed Value comparison should clearly highlight exactly what is being changed—for example, current and proposed category, custodian, location, condition, purchase value or other affected attributes. A Workflow Progress panel should display all applicable approval levels, showing completed, current and upcoming stages together with approver, date/time, comments and status. The approval levels shown must be generated from the applicable workflow configuration rather than hard-coded into the screen.
The current authorized approver should be provided with Approve, Reject and Return for Correction actions, together with a comments field and attachment viewing capability. Selecting Approve shall complete the current approval level and automatically route the request to the next applicable level; if no additional level is required, the system shall mark the request as finally approved and execute the associated asset transaction. Reject shall terminate the request without applying the proposed changes, while Return for Correction shall return it to the requester for modification and resubmission. The backend must verify that the logged-in user is the valid approver for the current workflow stage before accepting any approval action.
The screen should also visually identify Pending, Approved, Rejected, Returned, Escalated and SLA Overdue requests and provide notification indicators for transactions requiring immediate attention. Every action must update the workflow instance and create an immutable history containing Request ID, Asset ID, Workflow Level, Approver, Action, Comments, Date/Time and resulting status. Once final approval is completed, the relevant Asset360 service should execute the underlying transaction—such as activating a new asset, applying an approved asset amendment, completing an assignment/transfer or progressing a disposal—rather than the approval screen directly updating unrelated database tables.
The recommended navigation flow is Asset Approvals → Pending Approvals → Search/Select Request → Review Asset & Transaction Details → Compare Current vs Proposed Information → Review Workflow Progress & Documents → Approve / Reject / Return for Correction → Route to Next Level if Required → Final Approval → Execute Transaction → Notify Stakeholders → Record Audit History. This makes the Asset Approval screen the operational interface for the dynamic workflow engine configured through Administration → Workflow Configuration.
 Asset Approval (Dynamic Workflow) – Developer Functional Specification
The Asset Approval Module shall be developed as a configurable and dynamic workflow engine used to review and approve asset-related transactions before they update the live Asset360 records. Approval workflows must not be hard-coded; administrators should be able to configure approval levels, approvers and routing conditions based on transaction type, asset value, category, company/legal entity, business unit, department, location, asset criticality and other defined parameters. The same approval framework should be reusable for New Asset Registration, Asset Edit/Update, Assignment, Transfer, Return, Tag Replacement, Financial Changes, Disposal and other controlled asset transactions.
The approval process should support single-level and multi-level workflows, for example Requester → Asset Manager → Department Manager → Finance → Final Approval, with levels dynamically included or skipped based on configured conditions. Approvers may be assigned by User, Role, Department, Reporting Manager, Asset Manager, Finance Role or Approval Group, and the system should support sequential approvals, optional parallel approvals, configurable approval thresholds and escalation/delegation where required. Each approval request shall display the Transaction Reference, Asset ID/Asset Details, Request Type, Requested By, Requested Date, Current Approval Level, Proposed Changes, Supporting Documents and Approval History. For edit transactions, the approver should clearly see Current Value → Proposed Value before making a decision.
The screen shall provide Approve, Reject, Return for Correction, Add Comment and View Details actions. Approval must move the transaction to the next configured level; final approval shall trigger the relevant business transaction and update the Asset Master or associated transactional records. Rejection shall stop the workflow without modifying the live asset record, while Return for Correction shall send the request back to the requester for amendment and resubmission. The backend must validate that the logged-in user is an authorized approver for the current workflow level before accepting any action.
Administrators should be able to configure workflow rules such as Transaction Type → Conditions → Number of Approval Levels → Approver Type → Approver → Sequence → SLA/Escalation → Final Action. For example, an asset below AED 10,000 may require only Asset Manager approval, while a high-value asset could dynamically require Asset Manager and Finance approval. Changes to financial information may route directly to Finance, while disposal may require Asset Manager, Department Head and Finance approval.
Every workflow event shall maintain a complete audit trail containing Workflow ID, Transaction Reference, Asset ID, Approval Level, Approver, Action, Comments, Date/Time and Previous/New Status. Recommended statuses include Draft, Submitted, Pending Approval, Returned for Correction, Partially Approved, Approved, Rejected and Cancelled.
The recommended navigation flow is:
Asset Transaction → Submit for Approval → Determine Applicable Workflow Rules → Generate Dynamic Approval Levels → Route to Level 1 Approver → Approve/Reject/Return → Route to Next Applicable Level → Final Approval → Execute Asset Transaction → Update Asset360 Records → Notification → Audit History.
The key development principle is to build one reusable dynamic approval engine for Asset360 rather than developing separate approval logic inside each module. This will allow future modules and approval rules to be added through configuration without requiring application code changes.
Receiving & Tagging Screen – Developer Functional Description
The Receiving & Tagging screen shall be developed as the operational interface for receiving physical assets into Asset360, validating them against purchase or receiving information, capturing individual asset identifiers and associating Barcode, QR or RFID tags before the assets proceed to registration and approval. The screen should support both Receive with PO and Receive without PO processes, while additional functions such as Tag Assets, Bulk Tagging, Print Tags and Receiving History should be accessible from the Receiving & Tagging menu. The interface should follow a guided workflow of PO/Source Selection → Asset Verification → Tagging → Review & Submit, with the current stage clearly indicated to the user.
For Receive with PO, the user shall search or enter the PO number and the backend shall retrieve the available PO header and line information from the configured ERP/integration source or Asset360 receiving database. Supplier, PO Date and Expected Delivery Date should be automatically populated and normally displayed as read-only source information. The system shall then allow the user to capture Receiving Date, Receiving Location, Received By, GRN/Reference Number and Remarks. Mandatory fields must be validated before receiving transactions can be submitted.
The PO Line Items grid shall display all relevant items from the selected PO with information such as Item Description, Part Number, Ordered Quantity, Previously Received Quantity, Current Received Quantity, Pending Quantity and Status. The developer must support partial receiving, allowing the same PO line to be received across multiple deliveries. Pending quantity should therefore be calculated from cumulative completed receiving transactions and must not simply be overwritten by the current transaction. Statuses such as Pending, Partially Received/In Progress and Completed should update automatically according to the quantities received.
When the user selects Receive against a PO line, Asset360 shall move the user into individual asset verification. For serialized assets, each physical unit should be captured independently using the manufacturer's Serial Number, Barcode or other identifier. The system shall validate that the scanned serial number has not already been registered or received where uniqueness is required. The selected PO line, model/category and receiving information should remain associated with the scanned unit so users do not repeatedly enter the same information.
The Scan & Tag panel shall support scanner input, manual entry and RFID reader input. After scanning the physical asset identifier, the system should display an Asset Preview containing information such as Asset Name, Serial Number, Category, Model and current tagging status. The user can then scan an existing RFID/Barcode tag or generate/print a tag according to the configured Asset360 numbering scheme. Selecting Assign Tag shall validate that the tag is available and not already associated with another active asset before creating the relationship between the received asset and Tag ID/RFID EPC.
For RFID receiving, the application should treat the RFID EPC as a controlled unique identifier. The backend must prevent the same active EPC from being associated with multiple assets. Where RFID TID is available from supported hardware, it can also be captured for additional tag verification. Tag replacement should not be performed by simply editing the EPC; it should use the dedicated controlled tag replacement process so previous associations remain traceable.
The Print Labels tab should allow authorized users to generate and print Barcode/QR/RFID labels using configured Tag Format, Numbering Scheme, Label Template and Printer. The adjacent Tagging Settings control can be used to select the appropriate printer/template where multiple configurations are available. Printing a label does not by itself complete the association—the tag should be considered assigned only after successful validation and confirmation against the physical asset.
The Recent Scanned Items section shall provide immediate transaction feedback by showing recently processed records including Scan Time, Serial Number, Tag Number/RFID EPC, Asset Name and Tagging Status. This section should refresh after successful receiving/tagging actions without requiring the complete page to reload and can provide an option to open or correct the selected item before final submission where permissions allow.
The Summary section shall calculate operational counts such as PO Items, Units Received, Units Tagged and Pending Units. These values should be obtained from backend transaction data and refreshed whenever an item is received, tagged, removed or corrected. The summary must therefore represent the current receiving session rather than being calculated only from the visible page of the grid.
Save as Draft shall preserve the incomplete receiving session and allow the user to continue later without posting the transaction. Proceed to Review shall perform server-side validation and present a final review of the PO, received quantities, individual assets, serial numbers and tag associations. On final submission, the backend should create the receiving transactions, generate/update the applicable asset records and route records to the next configured registration/approval stage. Records requiring Asset Approval should be submitted to the dynamic approval workflow rather than automatically becoming active assets.
The Receive without PO option should use the same verification and tagging principles but replace PO selection with controlled manual/source information such as Supplier, Delivery Note/Reference, Receiving Location, Asset Category/Model, Quantity and Reason for Non-PO Receipt. Depending on configuration, non-PO receiving may require additional approval before the asset is activated.
The Receiving History screen shall provide a searchable history of previous receiving transactions using criteria such as Receiving Reference, PO Number, Asset ID, Serial Number, Tag/RFID EPC, Supplier, Receiving Location, Received By, Date and Status. Selecting a transaction should display its associated PO lines, individual received assets, tags and processing history.
From a developer perspective, receiving, tagging and asset creation should be treated as related but separate transactions. The backend should maintain references between the PO/Source → Receiving Header → Receiving Lines → Individual Received Asset → Asset Record → Tag Association → Approval/Audit History rather than storing everything directly in the Asset Master. All receive, scan, tag, untag, print, correction and submission events should be auditable with the User ID, date/time, source transaction and affected asset/tag.
The recommended screen maneuvering is:
Receiving & Tagging → Receive with PO / Without PO → Select Source/PO → Load Items → Select Item → Scan/Verify Physical Asset → Scan or Generate Tag → Assign Tag → Continue Next Asset → Review Received/Tagged Counts → Save Draft or Proceed to Review → Validate → Submit → Asset Registration/Approval → Receiving History.
This design allows the screen to function as a controlled physical receiving and identification gateway between procurement/receipt and the permanent Asset360 Asset Register.
Receive Without PO – Developer Functional Description
The Receive Without PO screen shall allow authorized Asset360 users to receive and register assets that are not linked to a Purchase Order, such as initial stock, donated assets, transferred assets, replacement equipment, legacy assets or other approved non-PO receipts. The screen should follow the same Asset360 Receiving & Tagging workflow and visual structure as Receive with PO, using the process Asset Details → Asset Verification → Tagging → Review & Submit.
The Receiving Information section shall capture the transaction-level information including Supplier/Source, Receiving Date, Delivery Note/Reference Number, Receiving Location, Received By, Reason for Non-PO Receipt and Remarks. Mandatory fields must be validated at both UI and backend levels. The Reason for Non-PO Receipt should be retrieved from configurable master data rather than hard-coded. The system should automatically generate a unique Receiving Transaction/GRN Reference where required and associate all assets received during the session with this transaction.
The Asset Default Information section shall allow the user to select common information applicable to multiple assets being received, including Asset Group/Class where applicable, Category, Subcategory, Manufacturer, Model, Condition and Warranty Period. Dropdown values must be retrieved from Asset360 master tables and should follow dependent relationships—for example, selecting a Category should restrict Subcategories and selecting Manufacturer should restrict applicable Models. These values should automatically populate newly scanned or manually added assets but remain editable at individual asset level where the user's permissions allow.
The Received Assets grid shall contain every physical asset captured during the receiving session and display fields such as Serial Number, Asset Name, Category, Model, Condition, Tag Number and Status. Users should be able to add assets through barcode/serial-number scanning, manual entry or controlled file import. Each serialized asset must be maintained as an individual record. The backend shall validate duplicate Serial Numbers and other configured unique identifiers against both the current receiving batch and existing Asset360 records before accepting the item.
The Scan & Tag panel shall support Barcode/QR scanner input and RFID reader input. When a Serial Number or asset barcode is scanned, the application shall identify or create the current receiving item and display its information in the Asset Preview panel. The user may then scan an RFID EPC, Barcode or QR tag and select Assign Tag. Before association, the backend must verify that the tag is valid, active/available and not already assigned to another asset. Successful association shall update the received asset's tagging status and refresh the Received Assets grid, Recent Scanned Items and Summary without requiring a complete screen reload.
The Print Labels function shall allow users to generate Barcode, QR or RFID labels using configured Asset Numbering Scheme, Tag Format, Label Template and Printer. The system should support the creation of an Asset ID/tag number where required; however, printing a label must not automatically mean that the physical tag has been successfully associated. Tag assignment should be confirmed separately after scanning or validating the tag.
The Asset Preview panel shall provide immediate confirmation of the currently selected/scanned asset and display information such as Serial Number, Asset Name, Category, Model, Tag Number and Tagging Status. Clear shall reset only the current scanning/tagging context and should not remove assets already saved in the receiving session. Assign Tag shall associate the scanned/generated tag with the selected asset after backend validation.
The Recent Scanned Items section shall display recently processed items with Timestamp, Serial Number, Tag Number, Asset Name and Status, providing operational feedback during high-volume receiving. The Summary cards shall show session-level values such as Assets Received, Tagged, Pending Tagging and Issues/Exceptions. These figures should be returned or recalculated from backend transaction data whenever the receiving session changes.
Save as Draft shall save the incomplete receiving header, received asset lines and completed tag associations so the user can continue the transaction later. Proceed to Review shall execute full server-side validation and present the complete receiving batch for confirmation. The validation should identify missing mandatory information, duplicate serial numbers, duplicate tags, untagged assets where tagging is mandatory, invalid master references and other configured exceptions before allowing final submission.
On final submission, the backend should process the relationship as Non-PO Receiving Header → Received Asset Lines → Individual Asset Records → Tag Associations → Asset Registration/Approval. Where dynamic Asset Approval is configured, the newly received assets should enter the appropriate approval workflow before becoming active in the Asset Register. All actions including creation, modification, scanning, tagging, removal, submission and approval should be captured in the Audit Log with user, timestamp and transaction reference.
The recommended navigation flow is Receiving & Tagging → Receive without PO → Enter Receiving Information → Select Asset Defaults → Scan/Add/Import Assets → Verify Asset Information → Scan/Generate Barcode or RFID Tag → Assign Tag → Review Received Assets & Exceptions → Save Draft or Proceed to Review → Validate → Submit → Approval if Required → Create/Activate Assets → Update Asset Register and Receiving History.
Tag Assets Screen – Developer Functional Description
The Tag Assets screen shall be developed as the operational workspace for assigning RFID, Barcode or QR tags to assets that already exist in Asset360 but are currently untagged or require controlled tag association. The recommended user flow is Select Asset → Scan/Generate Tag → Verify Asset & Tag → Assign Tag → Complete, with each stage reflected in the screen stepper. The Search Assets area shall allow users to locate eligible assets using Asset Number, Asset Name, Serial Number, Category, Location, Department, Custodian and Tag Status, with results filtered according to the logged-in user's permissions. The Assets to Tag grid shall display the selected records together with Asset Number, Asset Name, Category, Location, Serial Number, Current Tag and Status; users can select a row or use the Tag action to load the asset into the Asset Preview panel. The Scan & Assign Tag panel shall accept Barcode/QR scanner input, RFID reader input or manual/generate-tag actions, and the backend must validate that the scanned Tag ID/RFID EPC is valid, active and not already associated with another asset before assignment. Once a valid tag is read, the Asset Preview shall display the asset details, current tag if any, new proposed tag and a validation status such as Valid Tag / Ready to Assign. Selecting Assign Tag shall create the asset-to-tag association, update the asset's current tag status, preserve any previous tag relationship where applicable, refresh the asset grid and add the transaction to Recently Tagged Assets. The Print Labels tab shall support label generation using configured tag numbering schemes, label templates and printers, but printing a label must remain separate from the actual tag assignment confirmation. The screen should also support Add Manually and Import from File for controlled multi-asset preparation, while Clear resets the current scanning context without removing already processed records. The Tagging Summary shall dynamically show counts such as Selected, Tagged, Pending and Failed, and the Save as Draft action shall retain incomplete tagging sessions for later continuation. Complete Tagging shall perform a final server-side validation for duplicate tags, missing mandatory identifiers, invalid asset status and unassigned selected records before closing the session. All tagging actions—including scan, generate, assign, replace, unassign where permitted and completion—must be written to the audit history with Asset ID, Tag ID/RFID EPC, previous tag, new tag, user and date/time. The recommended maneuvering is Receiving & Tagging → Tag Assets → Search/Select Asset → Load Asset Preview → Scan/Generate RFID/Barcode/QR Tag → Validate Tag → Assign Tag → Repeat for Remaining Assets → Review Summary → Save Draft or Complete Tagging → Update Asset Register and Tagging History.
Bulk Tagging – Developer Functional Description
The Bulk Tagging screen shall allow authorized Asset360 users to assign RFID, Barcode or QR tags to multiple existing assets in one controlled session. The module should support high-volume tagging through continuous scanning, automatic tag generation or file-based tag mapping while ensuring that every tag is uniquely associated with the correct Asset ID.
The screen shall follow the workflow Select Assets → Tag Assignment → Verify & Review → Complete. In Select Assets, users should search and filter eligible assets using Asset Number, Category, Location, Department, Asset Type, Custodian and Tag Status. The backend should return only assets within the user's permitted scope and normally default the result to Not Tagged assets. Users may select individual assets, select multiple records, add assets manually or import an approved asset list from a file.
The Tag Assignment section shall support three methods: Scan Tags, Auto Generate Tags and Import Tag File. For continuous RFID/Barcode/QR scanning, the system should maintain the selected assets in a defined sequence and assign each successfully scanned tag to the next pending asset. Before assignment, the backend must validate the tag for format, uniqueness, availability and existing association. RFID EPC values already associated with another active asset must be rejected and displayed as an exception rather than overwritten.
The Tag Preview shall show the Next Asset awaiting tagging together with the scanned/generated Tag Number and validation result. Selecting Assign Tag to Selected Asset/Next Asset shall create the association, change the asset's tagging status to Tagged, timestamp the transaction and automatically advance to the next pending asset. The screen should refresh dynamically so operators can perform repetitive tagging without reloading the page.
For Auto Generate Tags, Asset360 should generate tag numbers according to the configured Tag Numbering Scheme, Asset Category and Tag Type. Where physical labels are required, generated identifiers should be passed to the configured label-printing service. For Import Tag File, the application should validate the Asset Number-to-Tag Number mapping before committing any association and provide row-level errors for invalid Asset IDs, duplicate tags, missing tags or existing tag associations.
The Tagging Progress section shall continuously display completed mappings with Asset Number, Asset Name, Tag Number, Assigned Time and Status, while a progress indicator should show completed records against the total selected. The Summary cards shall display Selected, Tagged, Pending and Failed counts. Failed records should remain available for correction or retry without requiring successfully tagged assets to be processed again.
Save as Draft shall preserve the bulk-tagging session, including selected assets and completed tag associations, allowing the operator to resume later. Proceed to Review shall display the final Asset-to-Tag mappings and execute server-side validation before completion. On confirmation, the session shall be marked completed and the applicable Asset Register and tagging history updated.
Every successful or failed tagging operation should create an auditable record containing Bulk Tagging Batch ID, Asset ID, Tag Type, Tag Number/RFID EPC, previous tag where applicable, new tag, status, assigned by and date/time. The backend should use transaction controls so a failed individual record does not incorrectly duplicate or overwrite another asset's tag association.
The recommended navigation is Receiving & Tagging → Bulk Tagging → Search/Select Assets → Choose Tagging Method → Scan/Generate/Import Tags → Validate Asset-to-Tag Mapping → Assign and Automatically Advance → Monitor Progress & Exceptions → Proceed to Review → Complete Bulk Tagging → Update Asset Register & Tagging History.
Print Tags Screen – Developer Functional Description
The Print Tags screen shall be developed as the controlled interface for generating and printing Barcode, QR Code and RFID-enabled asset labels for assets already available in Asset360. The screen should follow a simple flow of Select Assets → Configure & Preview → Generate & Print. Users must be able to search and filter assets using fields such as Asset Number, Asset Name, Category, Location, Department, Tag Status, Asset Type and Custodian, then select one or multiple assets for printing. The system should also support Upload from File for bulk selection and maintain a Selected Assets list showing Asset Number, Asset Name, Serial Number, Tag Number and Print Status. The developer should provide configurable tabs such as Search & Select, Upload from File, Tag Templates, Print Settings, Preview & Layout and Print History so users can complete all printing-related activities from the same workspace.
The Tag Templates section should allow users to choose from predefined label templates maintained in Asset360 configuration. Each template should define parameters such as Label Size, Tag Type, Orientation, Barcode/QR/RFID format, fields to display, company logo, asset image and layout positioning. The screen should dynamically preview the selected template using data from the currently selected asset. Template configuration should be master-data driven so new templates can be added without code changes.
The Print Settings section shall allow users to select the Tag Type, Label Size, Printer, Number of Copies and optional data elements such as Asset Number, Asset Name, Serial Number, Company Logo or Asset Image. The application should detect available configured printers and provide a Test Print option before bulk printing. The developer should separate printer configuration from the application logic so different network, desktop or RFID label printers can be supported through configurable print services or drivers.
The Preview & Layout section should show an accurate label preview before printing. Users should be able to navigate through selected assets and verify the final output for each label. The preview should display the actual values that will be encoded or printed, including Asset Number, Barcode/QR content and RFID EPC where relevant. Where supported, the system should validate that the encoded value matches the assigned Asset360 tag record before printing.
When the user selects Print Tags, the backend should create a print job containing the selected assets, chosen template, printer, number of copies and print parameters. The system should then send the job to the configured print service and update each record with a print result such as Ready to Print, Printed, Failed or Reprint Required. Failed print jobs should not change the tag-assignment status and should be available for retry.
The Print History tab should maintain a searchable log of all print transactions, including Print Job ID, Asset ID, Tag Number, Template, Printer, Copies, Printed By, Printed Date/Time and Result Status. Reprinting should create a new history entry rather than overwrite the original print record. All print and reprint actions should also be written to the Asset360 Audit Log.
The recommended maneuvering is Receiving & Tagging → Print Tags → Search/Select or Upload Assets → Choose Tag Template → Configure Printer & Print Options → Preview Labels → Test Print if Required → Print Tags → Capture Print Status → Review Print History / Reprint if Needed. This screen should remain focused on label generation and printing only; actual tag assignment to an asset should continue to be handled through Tag Assets / Bulk Tagging so printing and tag association remain controlled as separate processes.
ZPL printing integration:
The Print Tags function should also include a dedicated Zebra ZPL printing integration layer so Asset360 can generate and print labels consistently across supported Zebra industrial, desktop and mobile printers from both cloud-hosted and on-premise deployments. The application should generate the final label content as ZPL (Zebra Programming Language) based on the selected Asset360 template and dynamically substitute asset data such as Asset Number, Asset Name, Serial Number, Barcode/QR value, RFID EPC, logo and other configured fields. Rather than sending screenshots or PDFs to the printer, the backend should build a valid ZPL payload and send it to a configurable print service, allowing the same label definition to be reused across printer models that support ZPL.
For on-premise deployments, Asset360 can communicate directly with network-connected Zebra printers using their configured IP address/hostname and print port through an internal print service. The printer configuration should therefore store fields such as Printer Name, Model, IP Address, Port, DPI, Label Width, Label Height, Printer Type and ZPL Capability. When the user selects Print Tags, the application should generate the ZPL, submit it to the print service and receive a success/failure response for each job. Printer-specific settings such as 203/300/600 DPI, media width and RFID encoding capability should be stored in the printer master so the ZPL is generated correctly for each device.
For cloud deployment, the browser or cloud backend generally should not attempt to directly reach a printer on a customer's private LAN. Instead, Asset360 should use a lightweight Asset360 Print Agent / Local Print Connector installed within the customer network. The cloud application creates the print job and ZPL payload, then the local agent securely retrieves or receives the authorized job over HTTPS, forwards the ZPL to the selected Zebra printer and returns the print result to Asset360. This approach allows centrally hosted Asset360 environments to print to local industrial, desktop or mobile Zebra printers without exposing printers directly to the internet. The connector should support printer discovery/configuration, secure authentication, queued jobs, retry logic, offline buffering and printer-status reporting.
For mobile Zebra printers, the print architecture should also allow the Asset360 mobile application or local connector to send ZPL over supported connectivity such as Wi-Fi, network printing or Bluetooth, depending on the device and deployment model. The application should use the same Asset360 label template and ZPL generation logic so a label printed from a warehouse industrial printer and one printed from a mobile printer remain functionally identical. Any connectivity-specific printer SDK or local service should be isolated behind the Print Service interface rather than embedded into the asset-management business logic.
The Tag Template Master should therefore store both the visual/template definition and its corresponding ZPL template, with placeholders such as asset ID, serial number, barcode/QR content and RFID data. At runtime, Asset360 should replace these placeholders with actual values, validate the generated ZPL and optionally provide a rendered preview before printing. Administrators should be able to create multiple templates for different printer DPI, label dimensions, asset categories and customer branding.
For RFID-capable Zebra printers, the integration should support ZPL-based RFID encoding and printing where the specific printer and media support it. Asset360 should pass the required EPC value to the ZPL template, trigger encoding and record the result separately from the visual print result. A failed RFID encode must not be treated as a successfully assigned RFID tag even if the visible label was printed.
The recommended technical flow is:
Asset360 Print Tags → Select Assets → Select ZPL Template → Select Configured Zebra Printer → Generate ZPL Payload → Send to Print Service → On-Prem Direct Print OR Cloud Print Agent → Zebra Printer Executes ZPL → Return Printer/Encoding Result → Update Print Job Status → Write Print History and Audit Log.
From a developer perspective, the best architecture is to keep label design, ZPL generation, transport to printer, printer status and audit logging as separate services. This will make Asset360 printer-independent at the business layer while still allowing reliable integration with Zebra industrial, desktop and mobile printers across cloud and on-premise deployments.
Receive History – Developer Functional Description
The Receive History screen shall provide a centralized, read-focused view of all asset receiving transactions completed or initiated through Receive with PO and Receive without PO. The developer should retrieve receiving transactions according to the logged-in user's company, location and role permissions and provide search/filter options for Receive Number, PO Number, Receive Type, Status, Date Range, Supplier, Category, Location, Received By and Tagging Status. The transaction grid should display Receive Number, Receive Date, PO Number, Supplier/Source, Receive Type, Total Items, Tagged Items, Status and Received By, with pagination, sorting and export capability. Typical statuses should include Completed, Partial, Pending Tagging, Draft and Cancelled.
When a user selects a receiving transaction, the application should open the Receive Details panel without leaving the history screen. It should retrieve the complete receiving header information including Receive Number, Receive Date/Time, PO Number, Supplier/Source, Receive Type, Receiving Location, Received By, Remarks and Status. The Items Received section should display the individual assets belonging to that transaction with Asset ID/Name, Serial Number, Tag Number/RFID EPC and Tag Status. A View All Items action should open the complete item list where the receiving transaction contains more records than can reasonably be displayed in the side panel.
The Tagging Summary should be calculated from the transaction detail records and show Total Received, Tagged, Pending Tagging and Failed/Exception counts. The screen should also provide controlled actions such as View, Reprint Tags and Generate Report. Reprint Tags should route selected received assets to the Print Tags functionality without creating a new tag association, while Generate Report should produce a receiving report containing header, asset and tagging information. Export should support the filtered history data rather than only the currently visible page.

Search, filtering, sorting and pagination should be performed server-side for scalability. Clicking a transaction should call the detailed data service only when required rather than loading every asset for every receipt during the initial page load. All sensitive actions must follow role-based access control, while activities such as reprinting, exporting and report generation should be captured in the Audit Log.
The expected navigation is Receiving & Tagging → Receive History → Search/Filter Transactions → Select Receive Record → View Receive Details → Review Received Assets & Tagging Status → View All Items / Reprint Tags / Generate Report / Export.
Tracking & Location – Developer Functional Description
The Tracking & Location screen shall provide a centralized operational view for locating assets and displaying their current or last-known physical location using information available from Asset360 transactions, RFID/RTLS infrastructure and location master data. The screen should support multiple views—Map View, Floor Plan, List View and Geofence View—while maintaining the same selected asset and filter context when the user moves between views. The application should clearly differentiate between an asset's master/assigned location and its last detected location, since a detection from RFID/RTLS should not automatically overwrite the Asset Master location unless the applicable movement/transfer business process is completed.
The top-level KPI cards should dynamically show Total Assets, Assets Online/RTLS Active, Assets in Expected Location and Assets Out of Zone, together with the last refresh time. Selecting a KPI should act as a quick filter—for example, clicking Assets Out of Zone should display only assets whose latest detected location violates their configured location or geofence rule. The Refresh action should request the latest available tracking information from the backend without requiring a full page reload.
The Asset List on the left should support search by Asset ID, Asset Name, Serial Number, Barcode/QR and RFID EPC, together with advanced filters such as Company, Site, Building, Floor, Room/Zone, Category, Department, Custodian, Asset Status and Tracking Status. Selecting an asset should highlight it in the list, locate/highlight the corresponding marker on the map and populate the Asset Details panel on the right. Search, filters, pagination and sorting should be server-side so the screen remains responsive for large asset populations.
The central Map/Floor Plan area should obtain the applicable map from the Asset360 Location/Map Master according to Site → Building → Floor selection. Asset markers should be plotted using stored coordinates or the latest coordinates/location zone received from the tracking engine. Status should be visually differentiated—for example In Location, Recently Moved, Out of Zone, Offline/Not Recently Seen and Selected. The developer should support zoom, pan, fit-to-map and marker selection. Clicking a marker must select the corresponding asset in the asset list and refresh the right-side details.
The Asset Details panel should display the selected asset's Asset Number, Asset Name, Category, Serial Number, Tag/RFID EPC, Assigned Location, Current/Last Detected Location, Last Seen timestamp, Custodian/Department, Asset Status and device/tag information where available. Tabs such as Details, Location History, Movements and Maintenance should load information on demand. Location History should show previous detections with timestamp and source; Movements should show approved transfers/assignments; Maintenance should provide relevant maintenance status without duplicating the complete Maintenance module.
The Locate action should initiate the appropriate locating process according to the asset's tracking technology. For an RFID/RTLS-enabled asset, the backend should request or retrieve the most recent observations from the applicable reader/location service. Where handheld RFID locating is required, the web screen should provide the necessary asset/tag information to the corresponding mobile RFID Locate workflow. View on Map should automatically navigate to the correct Site/Building/Floor and center/highlight the selected asset.
For RFID/RTLS integration, the backend should process reader events using information such as Reader ID, Antenna/Zone, RFID EPC, Read Timestamp, Signal/Detection information and mapped location. Reader and antenna identifiers should be mapped through Asset360 master configuration to a Site → Building → Floor → Room/Zone/Map Position. Repeated raw RFID reads should be processed by the tracking service before being presented to users so the UI receives a meaningful latest-location event rather than thousands of duplicate reads.
The Geofence View should compare the asset's permitted or expected zone against its latest detected zone. If an asset moves outside the configured area, the system should create an exception such as Out of Zone and, where configured, generate a notification. Geofence rules should be configurable by asset, category, department, location or other applicable grouping rather than hard-coded.
The Location History should be maintained separately from the current Asset Master record. Each meaningful tracking event should retain information such as Asset ID, Tag/EPC, Location/Zone, Reader/Source, Detection Date-Time and event type. This allows Asset360 to display the movement trail and determine where and when an asset was last detected.
From a navigation perspective, the expected maneuvering is Tracking & Location → Asset Tracking → Search/Filter Asset → Select Site/Building/Floor → Select Asset from List or Map → Display Current/Last-Known Position → Open Asset Details → Review Location History/Movements → Locate or View on Map → Perform further controlled action if required.
The important development principle is to keep tracking and transactional movement separate. RFID/RTLS data represents where Asset360 has detected an asset, while Assignment & Movement represents where the organization has officially assigned or transferred the asset. The Tracking & Location screen should compare these two datasets and highlight discrepancies rather than automatically changing ownership or official asset location.
Location Map – Developer Functional Description
The Location Map screen shall provide users with an interactive visual representation of assets across configured sites, buildings, floors, rooms and zones. The screen should allow the user to select Site → Building → Floor, after which the application dynamically loads the corresponding uploaded floor plan and displays assets belonging to that location. Users should be able to search assets by Asset Number, Asset Name, Serial Number, Barcode/QR or RFID EPC and apply filters such as Category, Department, Custodian, Asset Type, Status, Zone and Tracking Type. Selecting an asset either from the asset list or directly from the map should highlight its map position and display the Asset Details panel containing identification, category, tag information, assigned location, current/last detected location and last-seen date/time. Map markers should use clear statuses such as In Location, Moving, Out of Zone and Offline, and controls should support zoom, pan, reset/fit-to-map and full-screen viewing.
The floor plans should be managed through an administrative Map/Floor Plan Configuration function. An administrator should be able to upload an existing architectural or simplified floor plan in supported formats such as JPG, PNG or PDF and associate it with the relevant Site, Building and Floor master records. Where a PDF drawing is uploaded, the application can convert the required page into a web-compatible map image for display. The administrator should then calibrate the drawing using a known physical distance so that the system can establish the relationship between actual dimensions and map coordinates. After calibration, the administrator should be able to draw and name rooms, corridors, storage areas, work areas and other zones directly over the floor plan and save these as coordinate/polygon definitions linked to the Location Master. The map should therefore be treated as a configurable digital floor-plan layer rather than storing asset positions directly inside the uploaded image.
Asset positions should be stored using map coordinates and/or configured zone references. For manually positioned assets, an authorized administrator can select or drag the asset onto the floor plan and save its X/Y position. For RFID and RTLS-enabled assets, the location should instead be derived from reader events. Asset360 should map the RFID Reader/Antenna or RTLS locator to its configured Site, Building, Floor and Zone; when the tagged asset is detected, the tracking service updates its latest detected location and timestamp. The UI then refreshes the corresponding marker on the floor plan. Historical detections should be maintained separately so that users can open Location History and review where an asset was previously detected rather than losing previous positions whenever the current position changes.
The Layers function should allow users to switch map information on or off, including asset markers, rooms/zones, RFID/RTLS reader positions, geofences, labels and optionally heatmaps. This is important for large sites where displaying every object simultaneously may make the map difficult to use. The right-side Assets/Zones panel should provide a synchronized list of assets and configured zones for the selected floor. Clicking an asset in the list highlights it on the map, while clicking a map marker selects the corresponding asset in the list and loads its details. Actions such as Locate, View History and More Actions should then allow the user to start RFID/RTLS locating, inspect movement history or navigate to related Asset360 functions.
From the development perspective, the map functionality should therefore maintain a relationship of Site → Building → Floor → Floor Plan → Zone/Room → Map Coordinates → RFID/RTLS Reader → Asset Detection. The uploaded drawing, calibration information, zone polygons, reader positions and asset coordinates should be stored independently so the floor-plan image can be replaced or updated without losing the underlying asset and location records. The frontend should render these layers dynamically, while the backend should provide APIs for map configuration, asset positions, zones, latest tracking events and location history. For live RFID/RTLS operation, updates can be pushed to the screen through a real-time mechanism such as WebSocket/SignalR so asset markers can move or change status without requiring the user to reload the page.
Geofencing – Developer Functional Description
The Geofencing screen should be developed as a configurable location-control interface within Asset360 that allows authorized users to define virtual zones on an uploaded floor plan and monitor whether tagged assets remain inside or outside those permitted areas. The user should first select the applicable Site, Building and Floor, after which the system loads the corresponding configured floor plan together with existing geofence zones and live or last-known asset positions. Zones should be created by drawing polygons directly on the map and assigning each zone a Zone Name, Zone Type, Status and applicable asset/category rules. Typical zone types should include Inclusion Zones, where selected assets are expected to remain inside the defined boundary, and Exclusion or Restricted Zones, where selected assets are not permitted to enter. Each zone should be stored in the database as map coordinates or polygon points linked to the applicable Site, Building and Floor so that the geofence definition remains independent of the floor-plan image itself.
The map should visually display all configured geofence boundaries using distinct colors and should also show RFID/RTLS-enabled asset markers based on their latest detected locations. Asset status should be calculated by comparing the asset's most recent location coordinates or detected zone against the configured geofence rule and displayed using statuses such as In Zone, Moving, Out of Zone and Offline. The Zones panel should list all configured zones for the selected floor, showing zone type, number of assets currently associated with the zone, active/inactive status and actions to edit, disable or remove the zone. Selecting a zone from the list should highlight the corresponding polygon on the map, while selecting an asset marker should allow the user to view its asset details and current geofence state.
The Geofence Rules section should allow administrators to define which assets the zone applies to and what event should trigger an exception. Rules may be assigned to individual assets, asset categories, departments, locations, asset values or other configurable criteria. Typical conditions should include asset leaves zone, asset enters restricted zone, movement occurs outside permitted hours, asset remains outside zone for a configured duration or asset is not detected for a specified period. Each rule should define the applicable Zone, Rule Type, Asset/Category Scope, Trigger Condition, Notification Method and Status. The system should evaluate these rules against the latest tracking events generated from RFID readers, RTLS infrastructure or other supported location sources rather than relying only on manually stored asset locations.
The Alerts & Events section should maintain both real-time and historical geofence violations. When a rule is triggered, the system should create an event containing the Asset ID, Tag/RFID EPC, Zone, Event Type, Detection Time, Reader/Location Source and current status and send notifications according to the configured channels such as in-app notification, email or SMS where supported. Repeated RFID reads should be consolidated by the backend tracking service so that the user is not flooded with duplicate alerts for the same continuing violation. The system should also allow an event to be acknowledged, resolved or reviewed, while keeping the original violation in the historical log.
From a development perspective, the geofencing functionality should use the relationship Site → Building → Floor → Floor Plan → Geofence Zone → Rule → Asset Scope → Tracking Event → Alert/Event. The frontend should render the map, zone polygons and asset markers dynamically, while the backend should store zone coordinates, evaluate location events against active geofence rules, generate alerts and maintain history. Live movement changes should ideally be pushed to the screen using WebSocket/SignalR or equivalent real-time updates, allowing the marker color and zone status to change without requiring a page refresh. The overall navigation should be Tracking & Location → Geofencing → Select Site/Building/Floor → View Existing Zones → Add/Edit Zone → Configure Rules → Monitor Live Asset Positions → Review Alerts & Events → Investigate Asset/Location History.
Location History – Developer Functional Description
The Location History screen shall provide a complete chronological record of an asset’s physical location and movement based on RFID/RTLS detections and other supported location events. The user should first select or search for an asset using Asset Number, Asset Name, Serial Number, Barcode/QR or RFID EPC, then specify a Date Range, Location Type and Event Type. Selecting Apply Filter should retrieve the relevant historical records from the backend, while Reset restores the default criteria. The screen should display the selected asset's key information, including Asset Number, Asset Name, Serial Number, RFID EPC, Category, Assigned To, Current/Last Known Location and Last Seen timestamp, so the user can immediately identify the asset whose history is being investigated.
The Movement on Map section should plot the selected asset's historical detections on the configured Site/Building/Floor plan. Each meaningful location event should appear as a numbered marker in chronological sequence, with a directional path connecting the locations. The marker should display or reveal the timestamp, location/zone and event information when selected. The Play Movement function should replay the historical movement chronologically, moving the highlighted position through the recorded locations according to their timestamps. Playback controls should support Play/Pause, playback speed and full-screen view. Where movement crosses multiple floors or buildings, the application should automatically load the appropriate floor plan as the playback reaches the corresponding location event rather than attempting to display all movements on one map.
The Location History grid should provide the detailed transactional record behind the map and contain fields such as Date & Time, Site/Building/Floor, Location, Zone, Event Type, Reader/Source and Remarks. Event types can include Zone Enter, Zone Exit, Movement, RFID Detection, RTLS Detection, Geofence Violation or Location Update according to the configured tracking technology. Clicking a history record should highlight the corresponding point on the map and the matching event in the Location Timeline. Search, filtering, sorting, pagination and export should be handled server-side to support assets with large historical datasets.
The Location Timeline on the right should provide a simplified chronological view of the same movement history. Each timeline event should show the date/time, detected location, zone, event type and RFID/RTLS reader or source. Selecting a timeline event should synchronize the map and history grid with that event. The timeline should visually differentiate events such as normal movement, zone entry/exit and geofence exceptions so users can quickly understand the asset's movement pattern.
For RFID/RTLS integration, the backend should receive raw tracking information containing values such as RFID EPC/Tag ID, Reader ID, Antenna/Locator ID, Detection Timestamp, Signal information where available and source system. Asset360 should map the reader or locator to the configured Site → Building → Floor → Room/Zone and resolve the EPC to the corresponding Asset ID. Because fixed RFID readers can generate many repeated reads within seconds, raw reads should not be displayed directly as individual movement records. The tracking engine should consolidate repeated observations and create meaningful location events only when the asset changes location, enters/exits a zone, remains detected according to configured rules or generates an exception.
From the database perspective, current location and historical location should be maintained separately. The current-location record can contain the latest confirmed detection for fast dashboard and map retrieval, while the Location History table should preserve records such as Asset ID, Tag/EPC, Event Timestamp, Site ID, Building ID, Floor ID, Zone ID, Reader/Locator ID, Event Type, Source and coordinates where applicable. Historical records should never be overwritten when the asset changes location. This structure allows Asset360 to reconstruct the complete movement path for any selected period.
The expected screen navigation is Tracking & Location → Location History → Search/Select Asset → Select Date Range and Event Filters → Apply Filter → Display Historical Movement on Map → Review Location Timeline → Select Individual Event → View Reader/Zone Details → Play Movement History → Export History if required. The key development requirement is that the map, history table and timeline remain synchronized: selecting an event in any one component should automatically highlight the corresponding information in the other two components, giving the user a complete visual and transactional history of where the asset was detected and when.
Proximity Search  – Developer Functional Description
The Proximity Search screen shall allow users to identify assets physically located near a selected asset or a chosen location within a configured Site, Building and Floor. The screen should support two search modes: Search by Asset and Search by Location. In Search by Asset, the user selects an Asset Number, Asset Name, Serial Number, Barcode/QR or RFID EPC, and the system retrieves its current or last-known mapped position. In Search by Location, the user selects or clicks a point on the configured floor plan. The user then defines a Search Radius such as 5 m, 10 m, 20 m or a permitted custom distance and selects the relevant floor/view before clicking Search Nearby Assets.
The map should display the selected asset or location as the search center and draw a visible radius boundary around it. Assets located within the defined radius should be highlighted separately from other assets using clear status colors. The developer should use the configured floor-plan calibration data and stored asset coordinates to calculate distance between the reference point and nearby assets. Where Asset360 only has zone/room-level tracking rather than exact X/Y coordinates, the system may use configured zone relationships such as same room, adjacent room or nearby zone, but the result should clearly indicate that the proximity is zone-based rather than precise distance. The map should support zoom, pan, floor selection and layers for Assets, Nearby Assets, Rooms/Zones, RFID/RTLS Readers and Search Radius.
The Selected Asset Details panel should display the reference asset's Asset Number, Asset Name, Category, Serial Number, RFID EPC/Tag Number, Current Location and Last Seen timestamp. Search Parameters should show the active radius and reference location. The Statistics section should summarize results such as Total Assets Found, Assets in Same Room/Zone and Assets in Adjacent Rooms/Zones, helping users quickly understand the nearby asset distribution.
The Nearby Assets grid should display all matching assets sorted by nearest distance, with columns such as Asset Number, Asset Name, Category, Current Location, Distance, Last Seen and Status. Clicking a result should highlight the corresponding marker on the map and allow actions such as View Asset 360°, Locate on Map, View Location History or other permitted asset actions. Export should download the filtered proximity-search result rather than the complete asset register.
From a backend perspective, the search service should query the latest Asset Location/Tracking record and calculate proximity using the selected asset's/map point's coordinates and the configured map scale. For exact coordinates, standard distance calculations can be performed against the stored X/Y position on the same calibrated floor plan. The service should normally prevent direct distance comparison between unrelated floors/buildings unless configured adjacency logic is available. RFID/RTLS updates should refresh asset positions through the existing tracking service so proximity searches use the most recent valid detection rather than stale master-location information.
The recommended navigation is Tracking & Location → Proximity Search → Search by Asset or Location → Define Radius/Floor → Search Nearby Assets → Display Radius & Results on Map → Review Nearby Assets → Select Result → View/Locate Asset or Open History. The key development requirement is to keep the map, selected reference asset, statistics and results grid synchronized, so changing the asset, location or search radius immediately generates a consistent set of proximity results.
Auto Discovery – Developer Functional Description
The Auto Discovery screen should be developed as the central workspace for identifying network-connected IT devices and reconciling them with existing Asset360 records. The screen should provide three main areas: Discovery Configuration, Discovery Summary/Status, and Discovered Devices. In Discovery Configuration, authorized IT users should be able to select the discovery method, define the approved IP range or subnet, choose a saved discovery profile and secure credential set, and then either Start Discovery immediately or Save/Schedule the job. The FSD supports network discovery through IP/subnet scanning, permitted agentless methods such as SNMP, WMI/WinRM, SSH and directory/network-management APIs, optional endpoint agents, and integration/import from endpoint-management, MDM, EDR, CMDB or network-management platforms. Discovery must be limited to authorized network scopes and credentials must be securely stored and never exposed back in plain text.
Once a discovery job is started, the Discovery Status panel should show each processing stage and its current state, for example Scanning IP Range → Identifying Devices → Collecting Device Details → Matching with Asset Database → Generating Results. The screen should display progress, elapsed time, completion/failure state and last scan timestamp. The developer should implement discovery as a background job rather than a long-running browser request, with the UI polling or receiving real-time progress updates from the backend. The summary cards should display counts for Devices Discovered, Matched Assets, New/Unregistered Devices, Suggested Matches/Requires Review, Conflicts and Stale Assets, because these are the classifications required by the FSD.
The Discovered Devices grid should be the main working area and support server-side search, filtering, sorting and pagination. Columns should include IP Address, Hostname, MAC Address, Device Type, Manufacturer, Model, Serial Number, Discovery Source, Last Seen and Reconciliation Status. The discovered dataset should also be capable of storing network information such as DNS, subnet/VLAN and switch/AP reference; hardware information such as CPU, RAM, storage and BIOS/firmware identifiers; operating-system information; authorized logged-on-user/owner hints; and discovery metadata such as first seen, last seen, collector, confidence, status and fingerprint. Optional software inventory may also be stored where enabled and authorized.
When a user selects a row, the lower Selected Device Details area should display the full discovery record and provide tabs such as Hardware Details, Network Info, Installed Software and Asset Match. The Asset Match tab is particularly important because the backend reconciliation engine should compare discovered devices against Asset360 Asset Master records using configurable weighted keys such as Serial Number, BIOS/UUID, MAC Address, Hostname and Model. The result should then be classified as Matched, Suggested Match, New/Unregistered, Duplicate, Stale/Not Seen or Conflict, with a confidence score where appropriate.
For Suggested Match or ambiguous results, the screen should not automatically merge records. Instead, the user should be able to open a comparison view showing Discovered Value vs Asset360 Value and then choose actions such as Confirm Match, Reject Match, Select Another Asset or Create New Asset. For a confirmed match, Asset360 should link the discovery record to the existing Asset ID. For an unknown device, the user can initiate New Asset Registration with permitted technical fields pre-populated. For a conflict or duplicate, the record should move to an exception state for manual resolution. The FSD specifically requires users to review suggested/ambiguous matches and requires discovery not to overwrite controlled financial values, tag numbers or approved ownership information without explicit workflow rules.
The developer should keep the Discovery Repository separate from the Asset Master. Discovery data represents observed technical information and can change frequently, while Asset360 remains the controlled system of record. The database should therefore maintain discovery job/header records, discovered device records, source-value history, match results and the link to Asset ID where reconciled. Technical attributes may be refreshed according to configured rules, but protected fields such as financial values, custody, ownership and physical tag information should remain controlled by the relevant Asset360 business workflows. The FSD also requires maintaining source-value history and the last discovery timestamp.
The Discovery Jobs tab should provide a history of scheduled and completed scans with information such as Job Name, Discovery Type, Scope/IP Range, Collector, Schedule, Started On, Completed On, Devices Found, Status and Error details. Discovery Settings should allow administrators to configure discovery profiles, credential references, permitted protocols/connectors, stale-device thresholds, matching weights, confidence thresholds and notification rules. If a registered IT asset is not discovered beyond the configured threshold, or if an unknown device is detected, the system should create a Discovery Exception and optionally notify the responsible IT team. Discovery exceptions and sync errors are also identified in the FSD as notification events.
The expected developer navigation is Auto Discovery → Network Discovery → Configure Scope/Profile → Start or Schedule Discovery → Monitor Job Status → Review Discovered Devices → Select Device → Review Hardware/Network/Software Data → Review Suggested Asset Match → Confirm/Reject/Create Asset → Open Asset 360° → Maintain Discovery and Audit History. The most important implementation principle is that Auto Discovery should function as a technical observation and reconciliation layer, not as a direct uncontrolled editor of the Asset Master.
Discovery Jobs – Developer Functional Description
The Discovery Jobs screen shall be developed as the operational and monitoring workspace for all Auto Discovery scans configured in Asset360. It should allow authorized IT users to create, schedule, monitor, rerun and review discovery jobs while maintaining a complete history of every execution. The screen should show summary cards such as Total Jobs, Completed, Running, Failed and Scheduled, with each card acting as a quick filter. The main grid should support search and filters for Job Name, Discovery Type, Status, Created By and Date Range and display columns such as Job Name, Discovery Type, IP Range/Target, Discovery Profile, Schedule, Started On, Completed On, Devices Found, Status and Created By. Discovery methods should align with the FSD, including IP/subnet discovery, supported agentless methods, agent-based discovery and imports/connectors from endpoint-management platforms.
Selecting a job should populate the Job Details panel without leaving the screen. This panel should show the unique Job ID, configuration scope, discovery type, IP range/subnet or target system, profile, schedule, creator, creation date, execution start/completion times, duration and resulting counts such as Devices Found, Matched Assets, New Assets and Requires Review. The backend should maintain the job definition separately from individual job executions so a recurring scheduled job has one configuration but multiple execution-history records. This also allows the user to compare results from previous runs.
The Discovery Progress section should provide stage-by-stage status for the selected execution, such as Initializing Discovery → Scanning/Connecting → Identifying Devices → Collecting Device Details → Matching with Asset Database → Generating Results/Report. Each step should have a status such as Pending, Running, Completed or Failed together with timestamps and error information where applicable. Because discovery scans may take several minutes or longer, execution should run asynchronously through a background worker/job service rather than keeping a browser HTTP request open. The UI should receive progress using periodic API polling or real-time notifications such as SignalR/WebSocket.
The New Discovery Job function should open a configuration form allowing the user to enter Job Name, Discovery Type, IP Range/Subnet/Target, Discovery Profile, secure Credential Reference and Schedule. Scheduling should support manual runs and configured recurring schedules such as daily, weekly or monthly. Credentials must be selected through secure references and should never be returned to the browser in plain text. The backend must also enforce that discovery operates only against authorized network scopes, as required by the FSD.
The Job Actions panel should be context-sensitive. View Discovered Devices should open the results from that specific execution; Download Report should generate/export the discovery result; Re-run Job should create a new execution using the same configuration; Edit Job should modify the future job configuration without changing historical executions; and Clone Job should create a new draft job using the existing configuration as a starting point. Pause/Cancel may be shown for running jobs, while Delete Job should normally archive/deactivate the configuration rather than destroy historical scan and audit records.
For failed jobs, the screen should provide useful diagnostic information such as failure stage, error message, target/subnet, collector/connector and retry status. A failed discovery should not delete partial results already captured; instead, the execution should be marked Failed and retain enough information for administrators to troubleshoot and rerun it. Discovery or synchronization failures may also generate notification events, which aligns with the FSD's requirement for discovery exceptions and sync-error alerts.
From a backend perspective, I recommend maintaining separate entities for Discovery Job Definition, Discovery Schedule, Discovery Execution/Run, Execution Step Log, Discovered Device and Reconciliation Result. Each execution should have a unique Run ID and reference its parent Job ID. The discovered devices from that run should remain traceable to the exact execution that generated them, including first/last seen and discovery source information. This supports the FSD requirement to maintain discovery source/value history and timestamps.
The recommended maneuvering is Auto Discovery → Discovery Jobs → Search/Filter Jobs → Select Job → Review Configuration & Progress → View Results / Download Report / Rerun → Create or Edit Schedule as Required → Open Discovered Devices for Reconciliation. The key development principle is that the Discovery Jobs screen controls and monitors the discovery process, while the Discovered Devices screen handles the resulting devices and reconciliation with Asset360 assets.
The Filters and Actions functionality on the Discovered Devices screen should allow IT administrators to quickly narrow the discovery repository and perform controlled reconciliation activities without navigating away from the page. When the user selects More Filters, the application should open an Advanced Filters drawer or modal containing fields such as IP Address, Hostname, MAC Address, Serial Number, Device Type, Manufacturer, Model, Operating System, Asset/Reconciliation Status, Location, Discovery Job, Discovery Source and Last Seen From/To. Filters should support multiple criteria simultaneously and be executed server-side so the screen remains responsive with large discovery datasets. Selecting Apply Filters should refresh the device grid and KPI counts using the selected conditions, while Reset should clear all criteria and return to the default device population. A useful additional option is Show Latest Records Only, which prevents historical observations of the same device from appearing as separate current records. The FSD requires the discovery repository to maintain first-seen/last-seen information, discovery source, status and device information, making these appropriate filtering dimensions.
The Actions menu should be dynamic and depend on the selected device's reconciliation status and the logged-in user's permissions. Selecting View Details should open the complete discovery record showing Overview, Hardware, Network, Installed Software and Discovery History. View in Asset 360° should only be enabled when the discovered device is already linked to an Asset360 asset and should open the corresponding complete asset record. Create Asset should be available for New/Unregistered devices and should launch New Asset Registration with discovered information such as hostname, serial number, manufacturer, model, device type and technical attributes automatically pre-populated. The user should still complete mandatory business information such as asset classification, company, department, location and custodian before creating the asset. Once created successfully, the new Asset ID should be linked back to the discovery record.
The Match with Existing Asset action should open a reconciliation window showing the discovered device information alongside potential Asset360 matches. The backend matching engine should search existing assets using weighted identifiers such as Serial Number, BIOS/UUID, MAC Address, Hostname and Model and return possible matches with a confidence score. The user can then select an existing asset and confirm the relationship. Suggested or ambiguous matches must require manual confirmation rather than being automatically merged, as required by the FSD. If no appropriate match exists, the user should be able to return to the Create Asset workflow.
The Edit Device option should only allow correction or enrichment of permitted discovery-management information and must not convert the discovery repository into another Asset Master. Discovery-generated technical values should preferably remain identifiable as source values. The FSD specifically requires discovery not to overwrite controlled financial information, tag numbers or approved ownership information without an explicit rule or workflow. Any manually changed value should therefore retain the original discovered value, modified value, user, date/time and reason in history where applicable.
Selecting View Discovery History should display the device's observations across previous discovery executions, including First Seen, Last Seen, IP Address, MAC Address, Hostname, Discovery Job, Discovery Source, Collector, detected hardware/OS changes and reconciliation status. This allows administrators to determine whether a device has changed IP address, hostname, operating system or other technical characteristics over time. The FSD requires source-value history and the latest discovery timestamp to be retained.
The Export Device / Export Results functionality should allow the user to export either the currently filtered results or the complete permitted discovery dataset. The export dialog can provide formats such as Excel, CSV and PDF and allow the user to select which columns should be included. For large exports, the backend should generate the file asynchronously rather than requiring the browser to process thousands of rows. Export permissions and activity should be recorded in the Audit Log.
For exception records, Mark as Resolved should be available where an unknown device, conflict or other discovery exception has been investigated. The system should require an optional or mandatory resolution comment according to configuration and store Resolved By, Resolved Date/Time, Resolution Type and Remarks. Resolving the exception should not delete the underlying discovery record. Similarly, Delete Device should be highly restricted; preferably it should archive or suppress an invalid discovery record rather than physically deleting discovery history, and the user should receive a confirmation dialog before the action is completed.
When the user enters the Discovered Devices screen from Discovery Jobs → View Discovered Devices, the grid should automatically apply the selected Discovery Job/Run ID as a filter and display only devices discovered during that execution. The user can then search and filter those results further. Likewise, actions such as Re-run Discovery Job should create a new execution of the existing job configuration while retaining the previous execution and its results. Editing the discovery job should modify future executions without altering historical results.
Overall, the developer should implement the maneuvering as Discovered Devices → Search/More Filters → Apply Criteria → Select Device → Actions → View / Match / Create Asset / Resolve / Export → Refresh Device Status. The grid, selected-device details and available actions should remain synchronized. For example, a New device that is successfully matched should immediately change to Matched, display its linked Asset ID and enable View in Asset 360° without requiring the user to leave and reopen the screen. All reconciliation actions should be permission-controlled and written to the Asset360 Audit Log.
Discovered Devices – Developer Functional Description

The screen should display summary cards for Total Devices, Matched with Assets, New/Unregistered, Suggested Match/Requires Review, Conflicts and Stale/Not Seen because the FSD requires discovery results to be classified into these reconciliation states. Users should be able to search devices using IP Address, Hostname, MAC Address, Serial Number or Model and filter by Device Type, Reconciliation Status, Location, Discovery Job, Discovery Source and Last Seen date. Search, sorting, filtering and pagination should be performed on the backend to support large device inventories.
The main Discovered Devices grid should show core information such as IP Address, Hostname, MAC Address, Device Type, Manufacturer, Model, Serial Number, Last Seen, Discovery Source and Asset Status. Additional technical fields should be available through the details panel, including DNS, subnet/VLAN, switch/AP reference, CPU, RAM, storage, BIOS/firmware information, operating system, architecture, system UUID and logged-on-user or device-owner hints where authorized. The FSD also requires discovery metadata such as First Seen, Last Seen, Discovery Source, Collector, Confidence, Status and Fingerprint, with optional installed software inventory where enabled.

The recommended navigation is Auto Discovery → Discovered Devices → Search/Filter → Select Device → Review Hardware/Network/Software Details → Open Asset Match → Confirm Match / Reject / Create New Asset / Resolve Conflict → Open Asset 360° if matched → Review Discovery History. Import to Asset 360 – Developer Functional Description
The Import to Asset360 feature should provide a controlled workflow for converting discovered IT devices into registered Asset360 assets or linking them to existing asset records. The screen should guide the user through a structured process of Select Devices → Map Fields → Review & Validate → Import → Results. In the Select Devices stage, users should be able to choose individual or multiple discovered devices and search or filter them by hostname, IP address, MAC address, serial number, device type, discovery job, location and reconciliation status. Summary indicators should show how many selected devices will result in New Assets, Existing Asset Matches, or Records Requiring Review, allowing the administrator to understand the expected import result before proceeding.
For every selected device, the system should determine an Asset Action such as Create New or Match Existing. New or unregistered devices should be eligible to create new Asset360 records, while devices already reconciled with an existing asset should be linked rather than duplicated. The developer should provide an option for the administrator to change the proposed action where permitted. Devices classified as conflicts, duplicates or ambiguous suggested matches should normally be excluded from automatic import until the reconciliation issue has been resolved, since the FSD requires ambiguous matches to be reviewed before records are merged. 
The Map Fields stage should define how discovered technical information maps to Asset360 fields. For example, Hostname → Asset Name, Serial Number → Serial Number, Manufacturer → Manufacturer, Model → Model, Device Type → Asset Type/Category, MAC Address → MAC Address, IP Address → IP Address, Operating System → OS Information and System UUID → Discovery Identifier. Where the discovery data cannot provide mandatory business information such as Company, Business Unit, Department, Cost Center, Asset Category, Physical Location or Custodian, the user should be required to provide the information manually or apply a common value to multiple selected devices. Discovery information should therefore assist asset creation without bypassing Asset360 master-data controls.
Before import, the Review & Validate stage should validate mandatory fields, duplicate serial numbers, duplicate MAC/UUID identifiers, valid master-data references and existing Asset360 relationships. Records with validation problems should be clearly identified and the user should be able to open Validation Details to see the device, affected field, reason for failure and corrective action required. Depending on configuration, the administrator may be allowed to exclude invalid records and continue with valid devices rather than cancelling the entire batch.
The Import Options section should control the behavior of the operation, including options such as Create New Assets for Unregistered Devices, Link Matched Devices to Existing Assets, Skip Devices with Missing Mandatory Fields, Update Permitted Technical/Location Information and Send Notification after Import. These options must respect role permissions and configured data-governance rules. In particular, discovery should not automatically overwrite controlled financial information, tag numbers or approved ownership information unless an explicit Asset360 rule or workflow permits the update. 
When the user confirms the import, the backend should process it as a controlled batch transaction and maintain an Import Batch ID linking every selected discovery record to its result. Successful new records should receive an Asset360 Asset ID, while matched devices should receive the corresponding Asset ID relationship. The original discovery record should remain available and its reconciliation status should automatically change—for example, New → Matched/Imported. The system should retain the discovery source and source-value history so users can distinguish information obtained through discovery from manually maintained Asset Master information. 
Finally, the Results stage should provide a clear summary showing Total Processed, Assets Created, Existing Assets Linked, Skipped Records, Failed Records and Records Requiring Review. Users should be able to open the newly created Asset 360° record, review failed records, retry eligible failures and export an import-result report. The entire operation—including who initiated the import, selected devices, field mappings, validation results, created/linked Asset IDs and date/time—should be recorded in the Audit Log. This makes the Import to Asset360 function the controlled bridge between the Auto Discovery repository and the authoritative Asset Register, rather than allowing discovered devices to automatically become assets without validation and reconciliation.
Discovery Settings – Developer Functional Description
The Discovery Settings screen should be developed as the administration and configuration layer for the Asset360 Auto Discovery module. It should allow only authorized IT/System Administrators to define Discovery Profiles, Credential References, Connectors/Integrations, Matching Rules, Device Classification, Discovery Schedules and Global Settings. The purpose of this screen is to centralize all parameters used by Network Discovery, Discovery Jobs and Discovered Devices so that discovery behavior can be changed through configuration rather than application code. The FSD requires discovery to be configurable, credential-controlled and restricted to authorized network scopes, with support for IP/subnet scans, agentless methods, endpoint agents and imports/connectors from external IT management platforms.
The Discovery Profiles section should allow administrators to create reusable profiles for different environments such as corporate networks, data centers, branch offices, printers or network devices. Each profile should contain Profile Name, Description, Discovery Type, Target Scope/IP Range/Subnet, supported scan methods, timeout, retry attempts, device types and whether OS/software inventory is enabled. Depending on the selected Discovery Type, relevant configuration fields should appear dynamically—for example IP Range for network scanning, connector selection for MDM/CMDB imports or agent configuration for agent-based discovery. Profiles should support Active/Inactive status, Clone, Edit and Delete/Archive. Any new Discovery Job should reference a saved profile instead of duplicating all settings.
The Credential Vault should manage secure credential references used by discovery protocols such as Windows/WMI, SSH or SNMP. The UI may show Credential Name, Type, Username/Account Reference, Profiles Using It and Status, but passwords, private keys and secrets must never be returned to or displayed in the browser after being saved. Secrets should be encrypted and preferably stored using the application's secure secrets mechanism or external vault. Profiles and jobs should store only a credential reference ID. If a credential is currently used by an active profile, the application should warn the administrator before disabling or removing it.
The Connectors & Integrations section should configure integrations to platforms such as endpoint management, MDM, EDR, directory, CMDB or network-management tools. This aligns with the FSD requirement to support imports/connectors from those external platforms. Each connector should store information such as Connector Name, Connector Type, Target System, Endpoint/Connection Configuration, Credential Reference, Sync Direction/Frequency, Status and Last Sync. Actions should include Add, Edit, Test Connection, Activate/Deactivate and View Sync History. Connector implementations should use a common integration interface so additional systems can be added without redesigning the Auto Discovery module.
The Matching Rules section should control how discovered devices are reconciled against existing Asset360 assets. The FSD specifically identifies Serial Number, BIOS/UUID, MAC Address, Hostname and Model as configurable weighted matching keys. The screen should therefore allow an administrator to enable or disable each matching attribute and configure a percentage/weight or priority. The backend should calculate a confidence score using the active rules and apply configurable thresholds for outcomes such as Automatic Match, Suggested Match and Requires Review. Matching rules should be versioned or audited because changes to weights can materially change reconciliation results.
The Device Classification configuration should allow discovered technical devices to be mapped into Asset360 classifications such as Device Type → Asset Group → Asset Class → Category → Subcategory. For example, a device identified as a Windows laptop may automatically suggest IT Equipment → End User Computing → Laptop. These should remain suggested/default classifications until the asset is formally created or approved. Administrators should be able to map discovered manufacturer/model/device-type patterns to Asset360 master data to improve consistency when creating new assets from discovery.
The Discovery Schedule tab should define reusable schedules for automatic discovery runs, such as hourly where supported operationally, daily, weekly or monthly, together with start time, timezone, applicable profile and enabled status. A scheduled run should create a new Discovery Execution under the configured Discovery Job while retaining all previous execution history. Administrators should also be able to temporarily disable a schedule without deleting the job or its history.
The Global Settings section should hold system-wide Auto Discovery parameters such as Stale Device Threshold, Auto-Create Exception for Unknown Devices, Software Inventory Enablement, Default Discovery Schedule, Notification Recipients and Discovery Audit Logging. The FSD requires exceptions when registered IT assets are not discovered beyond a configurable threshold or when unknown devices are detected, so the stale threshold and unknown-device exception behavior should be configurable here. Global settings should provide defaults only; profile-specific settings may override them where explicitly allowed.
The developer should also enforce that Auto Discovery settings cannot permit uncontrolled updates to protected Asset360 fields. Discovery may update or suggest technical/network information according to configured rules, but controlled financial values, tag numbers and approved ownership data must remain protected unless an explicit workflow permits changes. All changes to profiles, credentials, connectors, matching weights, schedules and global settings should be written to the Audit Log with previous value, new value, changed by and timestamp.
The recommended developer navigation is Auto Discovery → Discovery Settings → Select Configuration Tab → Create/Edit Profile or Rule → Validate Configuration → Test Where Applicable → Save → Activate → Discovery Jobs consume the settings during execution. The key architectural principle is that Discovery Settings defines configuration, Discovery Jobs executes it, and Discovered Devices handles the results and reconciliation.
Assignment & Movement – Developer Functional Description
The Assignment & Movement module should be developed as the central workspace for assigning assets to employees, departments, projects, vehicles, rooms or other organizational owners, and for transferring assets between locations, custodians, departments, sites or companies. The FSD requires the transfer flow to support location-to-location, department-to-department, custodian transfer, site-to-site, inter-company movement, bulk transfer, dispatch, in-transit status, receipt confirmation and approval routing, with complete movement history maintained for every asset. The screen should therefore be structured around four main tabs: Asset Assignment, Asset Movement/Transfer, Approvals and Movement History.
The top summary cards should show operational counts such as Total Assets, Assigned Assets, Unassigned Assets, Pending Transfers and Transfers This Month. These values should come from the backend and act as quick filters. The primary asset grid should support search by Asset ID, Asset Name, Serial Number, Barcode/QR or RFID EPC and filters for Site, Building, Floor/Location, Asset Type, Department, Assigned To/Custodian and Status. The grid should display fields such as Asset Number, Asset Name, Asset Type, Current Location, Assigned To, Status, Last Moved Date and Actions. Search, filtering, sorting and pagination should be server-side so that the module remains responsive for large asset populations.
When a user selects an asset, the Asset Details panel should show the current controlled record, including Asset Number, Serial Number, Tag/EPC, Category, Model, Status, Current Location, Assigned To, Assigned Date, Last Movement Date and relevant remarks. Tabs such as Details, Assignment, Movement History and Related Information should load contextual information without navigating away from the screen. The current asset location and custodian shown here should represent the official Asset360 assignment record, not simply an RTLS/RFID detected location.
The Asset Assignment function should be used when an asset is issued or assigned to a person, department, project, vehicle, room or other permitted entity. The FSD requires assignment to support scanning the asset, selecting the employee/department/project/vehicle/room, recording issue condition, issue date, expected return date for temporary assignments, digital acknowledgement, signature and supporting photo/evidence where required. The assignment screen should therefore capture the selected Asset, Assignment Type, Assigned To, Department/Project/Room, Assignment Date, Expected Return Date, Condition, Remarks and acknowledgement/evidence fields. Once submitted and approved where required, the backend should create an assignment transaction and update the asset's current custodian/assignment status.
The Transfer / Movement workflow should follow a guided process such as Select Asset → Current Location → Destination → New Custodian → Reason → Condition → Review → Submit, matching the FSD's recommended flow. The Current Location, Current Department and Current Custodian should be read-only values retrieved from the Asset Master. The user should then select the destination hierarchy, such as Company → Site → Building → Floor → Room/Zone, and optionally a new Department or Custodian. Mandatory fields should include Transfer Type, Destination, Effective/Movement Date, Reason and Asset Condition where applicable.
The transfer engine should support different movement scenarios. An intra-site transfer may update only floor, room or zone; an inter-site transfer should include dispatch and receipt confirmation; an inter-company transfer should require the appropriate approval and ownership transition; a custodian transfer may change Assigned To without changing physical location; and a bulk transfer should allow multiple selected assets to be moved under one movement request while maintaining individual asset transaction records. The backend should determine required validations and workflow routing based on the selected movement type rather than using one hard-coded transfer process.
For transfers that cannot be completed immediately, the system should support In Transit status. When dispatch is confirmed, the asset should move from its previous status/location to an in-transit state while retaining the origin and intended destination. Final location/custodian should only become effective after the destination user confirms receipt where receipt confirmation is configured. This prevents the Asset Register from showing the asset as fully received before the destination acknowledges it.
The Approvals tab should integrate with Asset360's dynamic Workflow Configuration. Transfers and assignments requiring approval should create a workflow instance rather than update the Asset Master immediately. The Approvals view should show Request ID, Asset ID, Request Type, Requested By, Request Date, Current Approval Level and Status. Once final approval is obtained, the Assignment/Movement service should execute the transaction. If rejected, the existing asset location and assignment should remain unchanged. The FSD specifically includes approval routing within transfer transactions.
The Movement History tab should provide a permanent chronological audit of asset movements. Each record should retain information such as Movement ID, Asset ID, Movement Type, From Company/Site/Building/Floor/Room, To Company/Site/Building/Floor/Room, Previous Custodian, New Custodian, Movement Date, Requested By, Approved By, Received By, Reason, Status and Remarks. Historical records must never be overwritten when the asset moves again. Selecting a movement should open its full transaction details and approval/history information.
The Recent Assignments & Movements panel on the main screen should display recently completed activity, including Asset Number, Asset Name, Action, From, To, Performed By and Status. This gives users operational visibility without opening Movement History. Likewise, the Pending Approvals panel should surface assignment/transfer requests awaiting action and allow authorized approvers to navigate directly to the Approval screen.
The New Assignment / Transfer button should provide context-sensitive options such as Assign Asset, Transfer Asset, Bulk Transfer, Return/Check-In and possibly Dispatch/Receive Transfer depending on role permissions. The FSD also defines Return/Check-In as a related process containing current custodian, return destination, condition, accessories, notes, photo and the ability to create a maintenance request automatically if the asset is returned damaged.
From a backend perspective, the developer should keep the Asset Master, Assignment Transactions and Movement Transactions separate. A recommended relationship is Asset → Assignment Header/History → Movement Header → Movement Assets → Approval Workflow → Dispatch/Receipt Confirmation → Asset Master Update. The Asset Master should contain only the current effective assignment and location, while complete transactional history remains in movement/assignment tables. Every create, approve, reject, dispatch, receive, cancel or amendment operation should be recorded in the Audit Log.
The system should also differentiate between official movement and RTLS/RFID detection. If RTLS detects an asset in another room, that information belongs to Tracking & Location. It should not automatically alter the official assignment or location. A detected mismatch may create an exception or suggest a transfer, but the official Asset Master should only change through the controlled Assignment & Movement process.
The recommended navigation is Assignment & Movement → Search/Select Asset → Review Current Assignment & Location → Assign Asset or Transfer/Movement → Enter Destination/Custodian/Reason/Condition → Review → Submit → Approval if Required → Dispatch/In Transit where applicable → Receipt Confirmation → Update Asset Master → Record Movement History and Audit Log.
Assign Asset  – Developer Functional Description
The Assign Asset screen should be developed as a guided transaction workflow that allows an authorized user to select an available asset and assign it to an employee, department, project, vehicle, room or other configured entity. The FSD requires the assignment process to capture the selected assignee/entity, issue condition, assignment date, expected return date where temporary, digital acknowledgement, signature and photo/evidence where required. The screen should therefore follow a clear sequence such as Select Asset → Assignment Details → Review & Confirm → Completion, with each step preserving entered data until the transaction is submitted or saved as draft.
The Select Asset section should allow the user to search by Asset Number, Asset Name, Serial Number, Barcode/QR or RFID EPC and optionally scan an asset using a connected scanner. The result grid should show key fields such as Asset Number, Asset Name, Serial Number, Tag/EPC, Asset Type, Current Location and Status. When an asset is selected, the right-side Selected Asset panel should display its image, category, model, serial number, tag/EPC, current location and current status so the user can verify the correct item before proceeding.
The Assignment Details section should capture Assignment Type, Assigned To, Department, Location, Building, Floor, Room/Zone, Assignment Date, Expected Return Date, Assignment Purpose, Condition at Issue, Accessories Included and Remarks. Assignment Type should control which lookup is presented—for example Employee opens the employee master, Department opens the department master, and Room opens the location master. The Acknowledgement section should support configurable acknowledgement requirements. Where enabled, the assigned user should be able to confirm receipt using Digital Signature, Photo Capture or another configured acknowledgement method, and the system should record Acknowledged By, Date/Time and confirmation statement. When the user selects Submit Assignment, the backend should run final validations, including asset eligibility, assignee validity, required fields, overlapping assignments and any workflow rules. If approval is required, the system should create a pending assignment request and leave the current Asset Master unchanged until approval is completed. If no approval is required, the assignment should become effective immediately and update the asset's current custodian/assigned entity, assignment status and effective location where applicable, while preserving the previous assignment in history. Save as Draft should store incomplete transactions without updating the Asset Master.
From a data perspective, the developer should maintain Asset Master, Assignment Transaction and Assignment History separately. The Asset Master should store only the current effective assignment, while each transaction should retain values such as Assignment ID, Asset ID, Assignment Type, Assigned To, Department, Location, Assignment Date, Expected Return Date, Condition, Accessories, Remarks, Acknowledgement, Evidence, Created By, Approved By and Status. This ensures that every previous issue/assignment can be audited without being overwritten.
The recommended navigation flow is Assignment & Movement → Assign Asset → Search/Scan Asset → Select Asset → Enter Assignment Details → Capture Condition & Accessories → Capture Acknowledgement/Evidence → Review → Submit → Approval if Required → Update Current Asset Assignment → Record Assignment History & Audit Log.
Transfer and Movement  – Developer Functional Description
The Transfer & Movement screen should allow authorized users to transfer one or multiple assets between locations, departments, custodians, sites or companies while maintaining complete movement history. The user should first search or scan assets using Asset No., Asset Name, Serial No., Barcode/QR or RFID EPC. The asset grid should display the current location, current custodian and status, and support multi-selection for bulk movement. Once selected, the right-side panel should display the selected assets and their key details so the user can verify them before proceeding. The system should validate that each selected asset is eligible for transfer and prevent invalid movements such as disposed assets or assets already involved in an active transfer.
The Transfer Details section should capture the Transfer Type, Transfer Date, Effective Date, Destination Location, Department, New Custodian and Movement Reason. The existing Site → Building → Floor → Room/Zone should be automatically retrieved and displayed as read-only information, while the destination hierarchy should use dependent dropdowns—for example, selecting a Site should load only Buildings belonging to that Site, followed by its Floors and Rooms/Zones. Transfer Type should determine which fields are mandatory; a Location Transfer requires a destination location, while a Custodian Transfer requires a new custodian. The same transaction should also support combined location and custodian changes where permitted.
The Additional Information section should capture the asset's Condition at Transfer, Accessories Included, Remarks and Reference Number, with optional supporting documents such as handover forms, photographs or transfer documents. Before submission, the Review & Confirm stage should clearly show the selected assets, From Location, To Location, previous/new custodian, transfer date and reason. The backend must perform final validation before accepting the request. Save as Draft should preserve the transaction without changing the Asset Master, while Submit Transfer should either initiate the configured approval workflow or proceed to movement processing where approval is not required.
For transfers requiring approval, the asset's official location and custodian should remain unchanged until the required approval is completed. For physical movements between sites or controlled locations, the system should support Approved → Dispatched → In Transit → Received → Completed statuses. Once receipt is confirmed, the backend should update the Asset Master with the new effective location/custodian and write the previous values into Movement History. Every transaction should retain the Movement ID, Asset IDs, From/To locations, previous/new custodian, reason, condition, requester, approver, dispatcher, receiver, timestamps and supporting documents. This provides a complete audit trail and prevents historical movements from being overwritten.
The developer should implement the navigation as Assignment & Movement → Transfer/Movement → Select/Scan Asset(s) → Enter Transfer Details → Add Condition/Documents → Review & Confirm → Submit → Approval if applicable → Dispatch/In Transit → Receipt Confirmation → Update Asset Master → Movement History. All controls and actions should be permission-based, and bulk transfers should use one transfer header while maintaining an individual movement record for each asset. The official Asset Master should only be updated after the applicable workflow is successfully completed.
Movement Approval  – Developer Functional Description
The Movement Approval – Action screen should allow an authorized approver to take a controlled decision on an asset assignment or movement request. When the user selects Approve, Reject, or Request Changes, the application should open the Action window showing the Request ID, request type, current status, requester, department, request date and time so the approver can confirm the transaction being processed. Only actions permitted for the user's role and the current workflow stage should be enabled.
The Approval Decision section should provide Approve, Reject and Request Changes/Send Back. When Approve is selected, the request should proceed to the next configured approval level; if the user is the final approver, the movement should progress to the applicable execution stage, such as Approved, Dispatch, In Transit, Receipt Confirmation, or Completed. Reject should terminate the approval process without changing the asset's official location or custodian. Request Changes should return the transaction to the requester for correction and resubmission while preserving the same request and its previous approval history.
The Comments field should capture the approver's remarks. Comments can be optional for approval but should be mandatory for Reject and Request Changes so the requester understands the reason. The screen should also support optional supporting-document upload, allowing the approver to attach evidence or approval-related documents. Notification options can allow the system to notify the requester, next approver, or other configured recipients after the action is completed.
When Submit is clicked, the backend must validate that the request is still pending with the current approver to prevent duplicate or conflicting decisions. It should then save the decision, comments, attachments, approver ID, date/time and workflow level in the approval history. The application should refresh the Movement Approval screen immediately after successful submission and update the request status. Cancel should close the Action window without saving any changes.
All approval actions should be fully audit logged. The developer should maintain the approval transaction separately from the Asset Master and record Request ID, Workflow Instance ID, Approval Level, Approver, Action, Comments, Action Date/Time and supporting documents. Most importantly, an approval action should not directly modify the Asset Master unless the configured workflow determines that the movement has reached its effective completion stage. This ensures a complete and traceable approval history for every asset movement.
Movement Approval  – Developer Functional Description
The Movement History screen should be developed as a read-focused, auditable view of all historical asset movements and assignments. The FSD requires Asset360 to support intra-site, inter-site, inter-department and inter-company movements with complete movement history, including dispatch, in-transit status, receipt confirmation and approval routing. The screen should therefore provide KPI cards such as Total Movements, Completed, In Transit, Pending Receipt and Cancelled/Rejected, followed by filters for Asset No./Name, Movement ID, Movement Type, From Site/Location, To Site/Location, Department, Custodian, Status, Requested By and Date Range. The screen should allow View Asset 360°, View Approval History, View Documents, Export and Print Movement Report, but direct editing of completed movement history should normally be prohibited. The expected flow is Assignment & Movement → Movement History → Search/Filter → Select Movement → Review Transaction Details → Review Asset(s)/Workflow/Timeline/Documents → Export or Open Asset 360°.
Verification and Audit  – Developer Functional Description
The Verification & Audit screen should be developed as the main workspace for executing physical asset verification campaigns and reconciling the results against Asset360 system records. The FSD requires verification campaigns to be created by company, site, location, category, custodian, cost center or custom selection, with the expected asset population snapshotted at campaign start and tasks assigned to specific users or teams. It also requires support for full census, cycle count, sample count and exception recheck. The screen should therefore display the selected Audit ID, Audit Name, Audit Type, Location, Planned Start/End dates and Overall Progress, together with tabs such as Asset Verification, Discrepancies, Summary, Audit Trail and Attachments.
The Asset Verification tab should list the campaign’s expected assets and allow the auditor to search or scan using Asset No., Serial Number, Barcode/QR or RFID EPC. The grid should compare the System Location/Custodian against the Verified Location/Custodian and show a clear verification outcome for each asset. The FSD defines outcomes such as Found – Correct Location, Found – Wrong Location, Found – Wrong Custodian, Unregistered Asset, Expected – Not Found, Duplicate Tag/Serial and Damaged/Condition Issue. Accordingly, the right-side action panel should provide controlled options such as Mark as Verified, Mark as Moved/Wrong Location, Mark as Not Found, Mark as Damaged, with remarks and evidence capture where necessary.
The Scan / Verify Asset panel should support both scanning and manual entry. Barcode, QR and RFID scans should resolve the physical item against the campaign expected list. RFID bulk scanning should de-duplicate repeated tag reads and match them against expected assets, as required by the FSD. Once an asset is identified, the Asset Details section should show its Asset Number, Tag/EPC, category, system location, verified location, system custodian, verified custodian, condition and last verification information. The verifier should then confirm the appropriate outcome and optionally add remarks, photographs or other evidence.
The Discrepancies tab should automatically collect exceptions such as wrong location, wrong custodian, unregistered assets, not-found assets, duplicate tags and damaged assets. These records should not silently update the Asset Master. Instead, they should create controlled reconciliation actions such as relocation, custodian correction, provisional asset creation, maintenance request or investigation. The FSD explicitly requires wrong-location and wrong-custodian findings to result in reconciliation actions, unregistered assets to create exceptions or provisional records, and damaged assets to optionally create maintenance requests.
The Summary tab should calculate campaign KPIs such as Expected, Verified, Pending, Not Found, Excess/Unregistered, Relocated and Exceptions, while the progress bar should be calculated from the verified campaign population. The FSD requires these counts and also states that campaign closure must require configured exceptions to be resolved or approved. Therefore, Complete Audit should only be enabled when the campaign meets the configured closure rules. On closure, Asset360 should generate and retain an immutable reconciliation result/report for audit purposes.
The Audit Management / Instruction functionality behind this screen should allow authorized users to schedule or trigger audits, assign auditors to locations or asset groups, define full or partial scope, generate audit checklists and monitor execution progress. The related approval flow should support approval of the audit schedule and scope, assignment validation, multi-level approval, timeline confirmation and notification to audit teams. This means the execution screen should only allow auditors to work on campaigns that have reached the appropriate approved/active status.
From a development perspective, the recommended flow is Verification & Audit → Select Approved Campaign → Load Expected Asset Snapshot → Search/Scan Assets → Compare System vs Physical Data → Record Verification Outcome → Capture Remarks/Evidence → Route Exceptions → Monitor Progress → Resolve/Approve Exceptions → Complete Audit → Generate Reconciliation Report and Audit Trail. The campaign result should be maintained separately from the Asset Master so the original expected population and every verification decision remain permanently traceable.
The Asset Verification screen should be developed as the operational workspace used by an auditor during an active verification campaign. At the top, the screen should display the selected Audit ID, Audit Name, Location, Audit Type, Planned Dates and Progress, together with KPI cards for Expected Assets, Verified, Pending, Not Found and Exceptions. The FSD requires campaigns to work from a defined expected population and to calculate verified, pending, not-found, excess/unregistered, relocated and exception counts. Filters should allow the user to narrow the asset list by Site, Building, Floor/Room, Department, Category, Custodian and Verification Status, while search should support Asset ID, Serial Number, Barcode/QR and RFID EPC.
The main Asset Verification grid should compare the system record against the physical verification result. Recommended columns are Asset No., Asset Name, Category, System Location, Verified Location, System Custodian, Verified Custodian, Condition, Verification Status, Verified By/Time and Actions. When an asset is scanned or selected, the right-side panel should load its details and allow the auditor to record one of the FSD-defined outcomes: Found – Correct Location, Found – Wrong Location, Found – Wrong Custodian, Unregistered Asset, Expected – Not Found, Duplicate Tag/Serial, or Damaged/Condition Issue. Wrong-location and wrong-custodian outcomes should create controlled reconciliation actions rather than directly changing the Asset Master, while damaged assets may optionally initiate a maintenance request.
The Scan / Verify section should support barcode, QR and RFID scanning as well as manual entry. RFID verification should support rapid multi-read, duplicate-read suppression and matching against the campaign expected list. Once an item is identified, the screen should display the expected asset information and allow the verifier to confirm its actual Location, Custodian and Condition and add remarks, photographs or other evidence. If a scanned tag is not part of the expected population, the system should classify it as Unregistered/Excess and create an exception or provisional asset workflow rather than automatically adding it to the register.
Every verification action should create an immutable campaign transaction containing the Campaign ID, Asset ID/Tag, expected values, observed values, outcome, verifier, date/time, condition, remarks and evidence. The Asset Master should not be directly overwritten by the verification screen; approved reconciliation processes should handle corrections after the audit. Campaign completion should also be prevented where configured exceptions remain unresolved, because the FSD requires resolution/approval of configured exception types before closure and retention of a signed reconciliation report and immutable campaign result.
The expected user flow should be Verification & Audit → Asset Verification → Select Active Campaign → Search/Scan Asset → Compare Expected vs Physical Data → Select Verification Outcome → Capture Location/Custodian/Condition → Add Remarks/Evidence → Save Verification → Generate Exception if Required → Continue to Next Asset.

The key architectural requirement is to maintain the Audit Header, Scope Definition, Expected Asset Snapshot, Assigned Tasks, Approval Workflow, Verification Transactions and Exceptions as separate linked records so the complete audit lifecycle remains traceable and auditable.
The Create Audit screen should allow an authorized administrator or audit manager to configure a new physical asset verification campaign before it is released to auditors. The screen should follow a guided workflow such as Basic Information → Audit Scope → Assign Users → Schedule → Review & Submit. Basic Information should capture the Audit Name, Audit Type, Reference Number, Description, Audit Objective, Company/Entity and Business Unit. Audit ID/Reference Number can be automatically generated by the backend according to the configured numbering sequence. Mandatory fields must be validated before the user can proceed, while Save as Draft should allow an incomplete audit to be stored without generating verification tasks.
The Audit Scope section determines which assets will participate in the campaign. The user should be able to define the population By Location, Asset Category, Custodian, Cost Center or Custom Selection. For location-based audits, the application should display the configured hierarchy such as Company → Site → Building → Floor → Room/Zone, with an option to include sublocations. Additional filters such as Asset Group, Category and Asset Status can further restrict the population. As the scope changes, the backend should calculate and display the estimated number of assets matching the criteria. At this stage the system is defining the scope; the final Expected Asset Snapshot should be generated/frozen when the audit reaches the configured activation/start stage so that the original audit population remains traceable.
The Audit Parameters section should capture Planned Start Date, Planned End Date, Verification Method and Sampling Method. Verification Method should support the configured options such as Barcode/QR, RFID and Manual Entry, while Sampling should support Full Count, Cycle Count, Sample Count and Exception Recheck where applicable. Configuration options should also determine whether auditors may record unregistered assets, whether photographs are required, whether remarks are mandatory for exceptions, and any specific audit instructions that must be downloaded to the mobile application.
The Assign Users stage should allow auditors, supervisors or audit teams to be assigned to the campaign and, where required, to individual locations or portions of the expected asset population. The developer should validate that assigned users are active and have the required verification permissions. The Schedule section should define execution dates and applicable task targets. Notifications should allow assigned users and configured recipients to receive messages when an audit is approved, assigned, started, approaching its deadline or otherwise reaches a configured workflow event.
The screen should also support Attachments for audit instructions, checklists, floor plans or supporting documents. Files should be stored against the Audit ID rather than directly in the Asset Master, with file type, size, uploader and upload date recorded. During the Review & Submit stage, the system should present a summary of the audit configuration including scope, estimated asset population, assigned auditors, dates, verification methods and important rules so the creator can confirm the setup before submission.
When Submit is selected, the backend should perform final validation and either move the audit to Pending Approval when an approval workflow is configured or to the appropriate ready/approved state when approval is not required. The developer should keep the Audit Header, Scope Criteria, Assigned Users, Schedule, Parameters, Attachments and Approval Workflow as separate related records. Once the campaign starts, Asset360 should create the expected asset snapshot required by the FSD and make the relevant audit package available to assigned mobile users for online/offline verification.
The Audit Execution screen should be developed as the operational workspace for auditors to perform and monitor an active physical asset verification campaign. When the screen opens, it should load the selected audit information including Audit ID, Audit Name, Location, Audit Type, Audit Period and Status, together with real-time progress such as Total Assets, Verified, Pending, Not Found, Wrong Location, Wrong Custodian, Unregistered and Damaged. The progress percentage and KPI counters should be calculated from saved verification transactions and automatically refreshed whenever a verification result is recorded or synchronized from the mobile application.
The main Asset Verification grid should display the expected asset population for the audit and compare the system information against the physically verified information. Recommended fields include Asset No., Asset Name, Asset Type, System Location, Verified Location, System Custodian, Verified Custodian, Verification Status and Last Verified Date/Time. Search should support Asset Number, Asset Name, Serial Number and Tag/RFID EPC, with filters for location and verification status. Tabs such as Asset Verification, Exceptions, Not Found, Summary and Audit Notes should allow the auditor or supervisor to quickly review different parts of the audit without leaving the execution screen.
The Scan / Verify Asset panel should allow the auditor to identify an asset using Barcode, QR, RFID or manual entry. Once an asset is scanned or selected from the grid, its complete information should appear in the Asset Details panel showing the expected system location/custodian alongside the physically verified values. The auditor should then select the appropriate verification result such as Verified, Wrong Location/Moved, Wrong Custodian, Not Found, Damaged or Unregistered Asset. Depending on the selected result, the screen should dynamically request additional information—for example, actual location for Wrong Location, actual custodian for Wrong Custodian, condition details for Damaged, or identification details for an Unregistered Asset. Remarks and photographs should be captured where required.
When Save Verification is selected, the backend should validate that the audit is active, the user is assigned and authorized, the asset belongs to the expected population where applicable, and the same verification transaction has not already been submitted. The system should save the expected values, observed values, verification outcome, auditor, timestamp, remarks and evidence as an audit transaction. Verification discrepancies must not directly overwrite the Asset Master. Instead, results such as Wrong Location, Wrong Custodian, Unregistered or Damaged should create an exception/reconciliation record for subsequent review and corrective action.
The screen should support both individual and RFID-based bulk verification. For RFID scanning, multiple EPCs may be received rapidly; the application should de-duplicate repeated reads, match each unique EPC against the expected audit population and classify the result accordingly. Assets successfully matched should update their verification status, while unknown EPCs should be identified as potential unregistered/excess assets. Already verified assets should be clearly identified to prevent accidental duplicate verification.
The Exceptions and Not Found tabs should provide focused views of unresolved audit findings. Supervisors should be able to review each discrepancy, supporting evidence and verification history and initiate the appropriate reconciliation process. The Summary tab should consolidate the audit result and show overall completion percentages and exception counts. The audit should only be eligible for completion when the required verification activities and configured exception-resolution rules have been satisfied.
From the developer perspective, the expected flow is Select Active Audit → Load Expected Asset Snapshot → Search/Scan Asset → Display System Details → Capture Physical Details → Select Verification Outcome → Add Remarks/Evidence → Validate → Save Verification → Update Audit Progress → Create Exception if Required → Continue to Next Asset. The Audit Execution records should remain separate from the Asset Master so the original expected values and actual physical findings are permanently retained for reconciliation, reporting and audit trail purposes.
The Audit Report screen should be developed as the reporting and analysis layer of the Verification & Audit module. It should allow users to select a completed or active audit and view consolidated results without changing the underlying verification transactions. The top section should provide filters for Audit, Company/Entity, Site/Location, Date Range and Status. Selecting Generate Report should retrieve the audit header, expected asset snapshot, verification transactions and exceptions from the backend and calculate the report results. The Audit Information panel should show the Audit ID, Audit Name, Audit Type, Company, Location, Audit Period, Status, Created By, Created Date and Completed Date.
The Audit Summary should provide KPI cards showing Total Expected Assets, Verified, Pending, Not Found, Wrong Location, Wrong Custodian, Unregistered/Excess and Damaged Assets, including both count and percentage where appropriate. These values must be calculated from the audit's stored verification results rather than directly from the current Asset Master, ensuring that historical audit reports remain unchanged even if an asset is subsequently transferred or updated. Clicking a KPI card should act as a quick filter and display the corresponding records in the detailed results section.
The screen should provide graphical analysis such as Verification Results, Verification Trend and Results by Location. Verification Results should visually show the distribution of verified assets and different exception types. Verification Trend should display daily and cumulative verification progress over the audit period. Results by Location should compare verified and exception counts across Site, Building, Floor, Room/Zone or other applicable location levels. The charts should be generated from the same report dataset used by the detailed grid so that counts remain consistent between the graphical and tabular views.
The Detailed Results section should contain tabs such as All Results, Exceptions, Not Found, Wrong Location/Moved Assets, Wrong Custodian, Damaged and Unregistered Assets. The grid should display information such as Asset Number, Asset Name, Asset Type, System Location, Verified Location, System Custodian, Verified Custodian, Verification Status, Verified Date/Time, Verified By and Remarks. Selecting an individual record should allow the user to view its verification details, photographs/evidence and related exception or reconciliation history without modifying the original audit result.
The report should clearly preserve the difference between System/Expected Values and Physically Verified Values. For example, if the Asset Master expected an asset in IT-101 but the auditor found it in IT-201, both locations must remain visible in the report even if the asset is later formally transferred to IT-201. This is important because the Audit Report represents the condition observed at the time of the audit and should therefore be treated as a historical record rather than a live Asset Register view.
The screen should support Export and Print functionality. Export should allow the filtered report or complete audit results to be generated in formats such as Excel, CSV or PDF, subject to user permissions. The printable/PDF report should include the audit information, summary KPIs, verification results, exception summary and detailed reconciliation results. For large datasets, report generation should preferably be handled server-side rather than loading all records into the browser.
Once an audit is formally closed, its report dataset should be treated as read-only and auditable. The developer should generate the report using linked records such as Audit Header → Expected Asset Snapshot → Verification Transactions → Exceptions → Reconciliation Results → Approval/Audit Trail. This ensures that Audit Reports provide management with an accurate historical record of what the system expected, what the auditor physically found, what discrepancies were identified, and how those discrepancies were subsequently handled.
 Asset Maintainence    – Developer Functional Description 
The Maintenance screen should be developed as the central workspace for managing the complete maintenance lifecycle of assets, including preventive maintenance, corrective maintenance, inspections, work orders, technician activities, parts consumption, downtime, service history and closure. The FSD requires preventive schedules based on calendar intervals, meter readings or condition triggers, and corrective work orders following the lifecycle Open → Assigned → In Progress → On Hold → Completed → Verified/Closed. It also requires capture of technician/vendor details, labor time, parts/material, cost, downtime, root cause, failure code, notes, photos and attachments. The main screen should therefore provide a consolidated view of all work orders while allowing the user to drill into each transaction.
The top section should provide Search and Filters for Work Order Number, Asset Number/Name, Maintenance Type, Priority, Status, Asset Category, Location, Assigned Technician and Date Range. The main grid should show fields such as WO Number, Asset Number, Asset Name, Maintenance Type, Priority, Scheduled Date, Due Date, Status and Assigned To. Selecting a work order should automatically load its complete details in the right-side panel without navigating away from the screen. The Work Order Details panel should show the selected asset, maintenance type, priority, scheduled date, due date, assigned technician/vendor, current location, problem description and current work-order status.
The screen should support two major entry actions: Create Work Order and Schedule Maintenance. Create Work Order should normally be used for corrective maintenance, breakdowns, inspection findings or manually raised service requests. Schedule Maintenance should be used for planned preventive activities based on a defined maintenance plan. When a preventive schedule becomes due, Asset360 should be able to create the corresponding work order automatically or make it available for controlled generation according to configuration. The maintenance plan may be based on calendar frequency, meter reading or condition trigger, as required by the FSD.
When the user selects Update Status, the available options should depend on the current work-order state. For example, an Open work order may be assigned, an Assigned order may be started, an In Progress order may be placed On Hold or Completed, and a Completed order may proceed to Verification/Closure. The developer should enforce valid status transitions on the backend rather than allowing users to manually select any status. Each transition should capture the user, date/time and optional comments so the full maintenance workflow remains traceable.
The Add Time Log function should allow technicians or supervisors to record labor activity against the selected work order, including technician, work date, start/end time or hours worked, activity performed and remarks. The Add Parts Used function should capture spare part/material, quantity consumed and applicable cost information. Where the Inventory module is integrated, posting a part consumption transaction should reduce the available quantity according to the configured stock process rather than merely storing free-text information.
The lower part of the screen should provide contextual tabs such as Maintenance History, Scheduled Maintenance, Parts & Consumables, Time Logs, Attachments and Notes. Maintenance History should show all previous work performed on the selected asset, including date, work order, maintenance type, description, performed by, status and cost. The FSD specifically requires maintenance history to remain visible from the asset record and reporting layer. This history allows maintenance users to understand repeated failures, previous repairs and servicing frequency before taking action.
The Asset Information panel should remain synchronized with the selected work order and provide quick reference information including Asset ID, Asset Name, Category, Manufacturer/Brand, Model, Serial Number, Current Location and Custodian. Additional information such as warranty coverage, AMC/service contract and next scheduled service may also be displayed. Warranty and contract information is important because the FSD requires the system to identify whether maintenance work is warranty-covered and to maintain AMC/service contract information including vendor, SLA, coverage dates, visit entitlement and cost.
When Close Work Order is selected, the application should validate mandatory completion information before closure. Depending on the maintenance type, this can include work performed, checklist completion, technician, labor time, parts used, failure code, root cause, downtime, asset condition, photos/evidence and completion comments. A completed work order should not be physically deleted or overwritten; it should become part of the permanent Maintenance History. If a verification stage is configured, the system should first move the work order to Completed and require an authorized supervisor to Verify/Close it.
From a navigation perspective, the developer should implement the flow as Maintenance → Work Order List → Search/Filter → Select Work Order → Review Work Order & Asset Details → Update Status / Add Time / Add Parts / Execute Checklist → Add Notes or Evidence → Complete Work → Verify & Close → Maintenance History. For planned maintenance, the flow should be Maintenance Plan → Due Schedule → Generate Work Order → Assign Technician → Execute → Record Activities/Parts/Readings → Complete → Verify/Close → Calculate Next Due Date.
The key technical principle is to keep Asset Master, Maintenance Plan, Maintenance Schedule, Work Order, Work Order Activities, Time Logs, Parts Consumption, Checklist Results and Maintenance History as separate linked records. The Asset Master should show the asset's latest maintenance state and next service information, while all detailed maintenance transactions should remain permanently traceable through the Work Order and Maintenance History records.
The Create Work Order screen should be developed as the primary transaction screen for creating preventive, corrective, breakdown or inspection-related maintenance activities against an Asset360 asset. The user should first select the Work Order Type, Maintenance Type and Priority, while the system automatically generates the Work Order Number and initial status. A clear problem description should be mandatory so that the technician understands the required work. Typical work-order statuses should follow the maintenance lifecycle Open → Assigned → In Progress → On Hold → Completed → Verified/Closed. The application should enforce valid status transitions from the backend rather than allowing users to freely change statuses.
The Asset Information section should allow the user to search for an asset using Asset Number, Serial Number, Tag/Barcode/QR or RFID EPC. Once selected, Asset360 should automatically retrieve related information such as Asset Name, Category, Manufacturer, Model, Serial Number, Custodian and Current Location from the Asset Master. The user should not have to re-enter these values. The system should also check whether another active work order already exists for the asset and provide a warning where appropriate. Asset status should be validated so that work orders cannot accidentally be raised against assets that are disposed or otherwise unavailable unless business rules explicitly permit it.
The Scheduling section should capture Planned Start Date, Planned End Date, Due Date and Estimated Duration. For an unplanned breakdown, the user should be able to mark the work order as a breakdown so the system can distinguish reactive maintenance from planned activities. For preventive maintenance, these dates may be automatically populated from the related Maintenance Plan or Schedule. The system should also track overdue work orders by comparing the due date with the current work-order status.
The Assignment section should allow the work order to be assigned to an internal technician, maintenance team or external service provider. When an internal technician is selected, the system should validate that the technician is active and eligible for the selected maintenance category. When an external vendor is selected, Asset360 should retrieve the applicable vendor/service-provider details. Assignment should generate the configured notification to the technician or vendor and should also make the work order available in the technician's mobile or web My Work Orders view.
The Warranty and AMC/Service Contract information should be automatically evaluated based on the selected asset. If the asset is still under warranty or covered by an AMC/service contract, the screen should indicate the applicable coverage and service provider so the maintenance manager can determine whether the work should be internally performed or routed to the contracted vendor. The system should retain the contract reference against the work order for later cost and SLA reporting.
The optional Checklist section should allow the user to select an appropriate maintenance checklist template based on asset category or maintenance type. Selecting Load Checklist should copy the checklist items into the work-order transaction so technicians can execute them independently of future changes to the master template. Checklist items may contain Yes/No checks, Pass/Fail results, numeric measurements, meter readings, text observations and mandatory evidence requirements. Completion of mandatory checklist items should be validated before the work order can be completed.
The lower tabs should manage the operational information associated with the work order. Parts & Materials should allow spare parts and consumables to be planned or subsequently consumed, capturing Part Number, Description, UOM, Quantity and Cost. Labor/Time Logs should record technician, activity, date, hours and labor cost. Attachments should store photos, inspection reports and service documents. Related Work Orders should show earlier or linked maintenance transactions for the same asset, while Notes should maintain operational comments. These child records should be stored separately and linked through the Work Order ID.
The Failure Code and Root Cause fields should primarily become mandatory during corrective-maintenance completion rather than necessarily at initial work-order creation. The technician or maintenance supervisor should record the actual failure classification and root cause after inspection. This information should later support failure analysis, recurring-problem reports and maintenance analytics. Additional completion information should include actual work performed, downtime, condition after repair, meter readings where relevant and technician comments.
The Estimated Cost Summary should automatically calculate planned costs from Parts Cost + Labor Cost + Other Cost. Costs entered in related tabs should immediately update the summary. At completion, the system should separately maintain estimated and actual costs so management can compare planned versus actual maintenance expenditure without overwriting the original estimate.
Save as Draft should store the work order without making it operational or notifying the technician. Submit Work Order should validate all mandatory fields, create the work-order transaction, generate its Work Order Number where not already reserved, create checklist instances where applicable, assign the technician/vendor and trigger configured notifications. Depending on workflow configuration, the work order may either become Open/Assigned immediately or enter a Pending Approval state.
From a development perspective, the recommended processing flow is Create Work Order → Select Asset → Retrieve Asset/Warranty/Contract Information → Define Maintenance Type & Priority → Schedule Work → Assign Technician/Vendor → Attach Checklist → Plan Parts/Labor → Add Instructions/Documents → Validate → Save Draft or Submit → Execute Work Order → Capture Actual Labor/Parts/Failure Information → Complete → Verify/Close → Update Maintenance History & Next Service Information. The backend should maintain separate but related records for the Work Order Header, Asset Reference, Assignment, Checklist Instance, Parts Usage, Time Logs, Attachments, Status History and Cost Transactions, providing a complete audit trail of the maintenance activity.
The Maintenance Plans screen should be developed as the configuration and management workspace for defining recurring preventive maintenance and inspection requirements for Asset360 assets. The main grid should display all configured plans with fields such as Plan No., Plan Name, Asset Category, Maintenance Type, Frequency, Status and Next Due Date. Users should be able to search and filter plans by plan number/name, asset category, maintenance type, status and location. When a plan is selected, its configuration should load in the Plan Details panel on the right without navigating away from the page. The Create Maintenance Plan button should open the same panel in creation mode, while Edit should enable modification of an existing plan based on user permissions.
The Plan Details and Scheduling section should capture the Plan Name, Asset Category, Maintenance Type, Description, Start Date and frequency rules. The scheduling engine should support calendar-based intervals and usage/meter-based intervals, such as every 1 month, 3 months, 6 months, 250 operating hours or 500 operating hours. The system should calculate the Next Due Date/Reading based on the applicable scheduling rule and the asset's previous completed maintenance. Changes to a plan should affect future schedules only and must not alter historical work orders that were already generated.
The Apply To section determines which assets are governed by the maintenance plan. The administrator should be able to apply a plan to all assets within a selected category, specific assets, assets at selected locations, assets assigned to a particular user/custodian, or assets matching configured filters. The Applicable Assets tab should dynamically display the assets matching these rules, including Asset Number, Asset Name, Location, Last Service Date, Next Due Date and Status. The developer should validate that inactive, disposed or otherwise ineligible assets are excluded according to configured business rules.
The Additional Settings should control maintenance automation. When Automatically Create Work Order is enabled, the backend scheduler should generate a work order when the maintenance activity reaches the configured trigger point and link it back to the Maintenance Plan and applicable asset. Send Notification Before Due Date should allow the administrator to specify the number of days before the due date when alerts should be sent. The plan should also optionally link to an AMC/Service Provider and a Maintenance Checklist, so generated work orders automatically inherit the appropriate vendor/contract and checklist requirements.
The lower tabs should provide operational visibility into the selected plan. Generated Work Orders should show all work orders created from the plan and their current status. Checklist should display the checklist template associated with the plan. Comments should maintain administrative notes, while History should record changes such as creation, activation, deactivation, frequency changes and modifications to applicable assets. Historical transactions must remain read-only so that plan changes do not affect previously completed maintenance records.
When Save Plan is selected, the backend should validate mandatory information, frequency rules, asset applicability and checklist/service-provider references before saving. The recommended processing flow is Maintenance → Maintenance Plans → Create/Select Plan → Define Maintenance Type → Configure Frequency → Define Applicable Assets → Configure Work Order Automation/Notifications → Attach Checklist or AMC → Save & Activate → Calculate Due Schedule → Generate Work Orders when Due → Recalculate Next Due after Maintenance Completion. The developer should maintain the Maintenance Plan, Scheduling Rules, Applicable Asset Mapping, Checklist Mapping, Generated Work Orders and Plan History as separate linked records to ensure proper control and auditability.
The Preventive Maintenance screen should be developed as the operational scheduling workspace for monitoring upcoming maintenance activities and generating work orders from configured Maintenance Plans. When the screen loads, it should retrieve all active preventive schedules and display Schedule No., Asset No., Asset Name, Schedule Type, Frequency, Next Due Date and Status. Users should be able to filter the list by Asset Category, Location, Schedule Status, Due Period and Date Range. Statuses such as Scheduled, Due Soon, Overdue, Work Order Generated and Completed should be calculated automatically based on the due date, maintenance-plan configuration and related work-order status.
When the user selects a schedule, the Schedule Details panel should load the corresponding asset and maintenance configuration. It should show the Asset Number, Asset Name, Category, Location, Schedule Type, frequency rule, Start Date, Next Due Date, Checklist Template, Service Provider/AMC and maintenance description. The schedule may be time-based—for example every 3 months—or meter/usage-based, such as every 250 operating hours. The developer should calculate the next maintenance requirement using the relevant rule and prevent manual changes that would break the relationship with the underlying Maintenance Plan.
The Generate Work Order function should convert a due preventive-maintenance schedule into an operational work order. The generated work order should automatically inherit the Asset, Maintenance Type, Priority/default rules, Planned Date, Checklist, Service Provider/AMC and maintenance instructions from the schedule and its Maintenance Plan. The system must prevent duplicate active work orders from being generated for the same asset and schedule occurrence. Once successfully generated, the schedule should show the associated Work Order Number and change its status accordingly. Where Automatically Generate Work Order When Due is enabled, the same process should be performed by a backend scheduler without requiring manual action.
The lower section should provide views such as Upcoming Schedules, Completed, Overdue and Generated Work Orders. Upcoming Schedules should show activities approaching their due dates; Overdue should identify schedules where the due date or meter threshold has passed without the required maintenance being completed; Completed should show previous preventive-maintenance occurrences; and Generated Work Orders should provide direct navigation to the corresponding work-order transactions. Clicking a Work Order Number should open the Work Order screen so the user can follow its execution and completion.
The Additional Settings should control automation around the schedule. Users should be able to configure advance notifications, mandatory checklist completion, service-provider notification and whether successful completion should update the asset's Last Service Date and Next Service Date. Notifications should be generated according to the configured lead period—for example, seven days before the maintenance due date. If the maintenance activity is covered by an AMC or external service contract, the applicable service provider should be linked to the generated work order.
When a preventive work order is completed and verified, the backend should update the corresponding schedule occurrence and calculate the next due date or meter threshold according to the Maintenance Plan. The completed schedule must remain in history and a new occurrence should be created rather than overwriting the previous record. This ensures that Asset360 maintains a complete maintenance history showing when maintenance was planned, when the work order was generated, when work was actually performed and when the next service becomes due.
From the developer perspective, the processing flow should be Maintenance Plan → Generate Preventive Schedule → Monitor Due Date/Meter Reading → Due Soon Notification → Generate Work Order → Assign Technician/Vendor → Execute Maintenance → Complete Checklist/Parts/Time Logs → Verify & Close Work Order → Mark Schedule Completed → Update Asset Service Information → Calculate Next Schedule. The Maintenance Plan, Schedule Occurrence and Work Order should remain separate but linked records so that changes to future maintenance rules never alter historical maintenance transactions.
The Service Provider Action / Add Service Provider screen should be developed as the master-data entry and maintenance screen for registering external maintenance companies, AMC providers, OEM partners and other service vendors used within Asset360. The screen should support both Create and Edit modes. In Create mode, the system should generate or validate a unique Provider Code and capture Provider Name, Provider Type, Status, company registration details, TRN, website, currency, payment terms and remarks. Mandatory fields must be validated before saving, and the system should prevent duplicate provider records based on configured identifiers such as provider name, registration number or TRN.
The screen should use tabs such as General Information, Contact & Address, Services & Categories, Contracts/AMC, Documents, Service History and Notes. Contact & Address should maintain the primary and alternate contacts, designation, email, telephone and complete address. Services & Categories should define what the provider is authorized to maintain—for example HVAC, electrical, lifts, IT equipment or fire and safety equipment—and these mappings should control which providers appear when assigning a Maintenance Plan or Work Order. The system should also support attributes such as Preferred Provider, Lead Time and Rating, while provider status should determine whether the provider can be selected for new maintenance transactions.
The Contracts / AMC tab should allow one provider to have multiple service contracts. Each contract should capture information such as Contract Number, Contract Name, Start Date, End Date, Coverage, SLA, Covered Assets/Categories/Locations, Visit Entitlement and Contract Value. The application should identify whether a contract is Active, Expiring or Expired based on its dates. When a work order is raised for an asset covered by an active AMC, Asset360 should be able to identify the applicable provider and contract automatically. Expired or inactive contracts should remain visible historically but should not normally be selectable for new maintenance activities.
The Documents tab should store supporting records such as AMC agreements, trade licenses, insurance documents, quotations, certifications and service reports. Service History should be read-only and automatically populated from completed and active work orders linked to the provider, allowing users to review previous maintenance activities, response history and associated assets. The developer should not duplicate these transactions inside the provider master; the screen should retrieve them through the Provider ID relationship.
When Save is selected, the backend should validate mandatory information and save the provider together with its service-category mappings, contacts and related configuration. Save as Draft should allow an incomplete provider record to be retained without making it available for operational selection. Editing an existing provider should update the master information while maintaining a history of important changes. Providers that already have historical maintenance transactions should normally be deactivated rather than deleted, preserving all previous work-order and AMC references.
From the developer perspective, the integration flow should be Service Provider Master → Service Categories → AMC/Contract → Applicable Assets/Locations → Maintenance Plan → Preventive Schedule → Work Order → Service Execution → Completion → Service History. The backend should maintain Provider Master, Contacts, Addresses, Service Category Mapping, Contracts/AMC, Contract Coverage, Documents and Provider History as separate linked records, allowing the same service provider to support multiple categories, contracts, locations and maintenance activities without duplicating master information.
The Services & Categories screen should be developed to define exactly what maintenance services a Service Provider is qualified and authorized to perform within Asset360. The user should be able to map the provider to one or more Asset Categories such as HVAC, Electrical, Lifts & Elevators, Fire & Safety or IT Equipment and specify the applicable Service Type, such as Preventive Maintenance, Corrective Maintenance, Inspection or Certification. For each mapping, the system should capture the provider's capabilities/description, location coverage and Active/Inactive status. Location coverage should support either All Locations or selected locations from the Asset360 Location Master. These mappings should subsequently control which service providers are available when creating Maintenance Plans and assigning Work Orders.
The Supported Services section should allow more detailed services to be configured underneath the selected category. For example, HVAC may contain AC Maintenance, Chiller Service and AHU Maintenance. Each service should have a unique Service Code, Service Name, default SLA/response time, indicative service rate and status. The Add Service action should open an entry panel for creating the service, while Edit should allow authorized changes. Services already referenced by contracts, maintenance plans or work orders should not be physically deleted; they should be made Inactive so historical transactions remain valid. When a Work Order is created for a particular asset and service requirement, Asset360 should use the Asset Category → Service Category → Supported Service → Service Provider relationship to identify suitable providers.
The Certifications & Licenses section should maintain qualifications required for the provider to perform specific services. The user should be able to record the Certification/License Name, Certificate Number, Issuing Authority, Issue Date, Valid Until, Status and supporting document. The system should automatically identify expired or approaching-expiry certifications and may warn users when assigning a provider whose mandatory certification has expired. This information should remain linked to the Service Provider and can be used during provider evaluation and maintenance assignment.
For screen maneuvering, selecting Add Category should clear and open the Add/Edit Service Category panel, where the user selects the Asset Category, Service Type, capabilities and coverage before saving. Selecting the Edit icon on an existing row should load that mapping back into the same panel. Add Service and Add Certification should work similarly through their respective entry forms. Save as Draft should preserve incomplete configuration without making it available for operational selection, while Save should validate the category, service type, location coverage and other mandatory information before activating the configuration. Cancel should discard unsaved changes.
From the developer perspective, these records should be maintained as linked master data rather than free-text values: Service Provider → Asset Category Mapping → Service Type → Supported Services → Location Coverage → Certifications → Contract/AMC → Maintenance Plan → Work Order. The backend should prevent duplicate category/service mappings for the same provider, validate that at least one location is selected when Specific Locations is chosen, and ensure that only Active providers, active services and valid applicable mappings are presented during Maintenance Plan and Work Order creation. This structure will allow Asset360 to automatically recommend or filter the correct service providers based on the asset being maintained, its location, required maintenance type and contractual coverage.
The Contracts / AMC screen should be developed as the contract-management workspace for maintaining all Annual Maintenance Contracts and service agreements associated with a Service Provider. The screen should display a searchable list of contracts with Contract No., Contract Name, Contract Type, Start Date, End Date, Contract Value, Status and Actions. Contract status should be automatically derived or validated against the contract dates and support states such as Draft, Active, Expiring, Expired, Suspended and Terminated. The FSD requires AMC/service-contract linkage with vendor, SLA, coverage dates, visit entitlement and cost, so these values should remain linked to maintenance plans and work orders.
When the user selects a contract, the Contract / AMC Details panel should load the complete record. It should capture Contract Number, Contract Name, Contract Type, Status, Start Date, End Date, Contract Value, Currency, Reference/PO Number, Payment Terms and Description. The backend should validate that the End Date is later than the Start Date and prevent duplicate contract numbers. Contract values should be stored with their applicable currency, while changes to an existing active contract should be audit logged rather than silently replacing historical information.
The Coverage Details section is particularly important because it determines when Asset360 considers an asset to be under AMC. Coverage should be configurable by Specific Assets, Asset Category, Location and Service Category, rather than requiring every covered asset to be entered individually. The Spare Parts screen should be developed as the central workspace for managing all spare parts, consumables, replaceable components and critical spares used during preventive and corrective maintenance in Asset360. The FSD requires spare parts to be properly catalogued, linked with assets and made available for maintenance activities without stock mismatches or maintenance delays. Each spare part should therefore have a unique Spare Part Code and Name, together with Barcode/QR/RFID identification where applicable and classification such as consumable, replaceable or critical spare. The screen should also integrate with the Warehouse Master so stock can be maintained across central, regional and site-level stores using the hierarchy Warehouse → Rack → Bin.
The upper portion of the Spare Parts screen should provide summary indicators such as Total Spare Parts, In Stock, Low Stock, Out of Stock and Total Inventory Value. These values should be dynamically calculated from inventory transactions rather than maintained manually. The developer should implement stock status based on the current quantity and configured reorder level; for example, an item with zero available quantity should appear as Out of Stock, while an item at or below its reorder threshold should appear as Low Stock. This is particularly important because the FSD positions spare-parts inventory as a mechanism for ensuring availability of critical components and supporting replenishment planning.
The Spare Parts List tab should be the primary working view and should display all registered parts in a paginated data grid. Recommended columns are Item Code, Item Name, Category, Unit of Measure, Current Stock, Reorder Level, Unit Cost, Stock Status and Actions. Where applicable, the part should also contain Barcode, QR or RFID Tag ID and alternate part codes, since these identifiers are specifically required for fast scanning, tracking and cross-referencing of equivalent parts. The developer should calculate values such as Current Stock and Total Value from transactions rather than allowing users to freely overwrite calculated quantities.

The row-level Action menu can provide functions such as View Details, Edit, Stock Receipt, Stock Issue, Transfer, Adjust Stock, View Transactions and Deactivate. A spare part that has already been referenced in a Work Order or inventory transaction should not be physically deleted; it should instead be made inactive so historical maintenance records remain intact. Import and Export actions can additionally support controlled bulk loading and extraction of the spare-parts master.
The Spare Parts List must also be integrated directly with maintenance operations. When a technician records a spare part against a Work Order, Asset360 should validate whether sufficient quantity exists at the selected warehouse/location before allowing consumption. On confirmation, the system should create a stock-issue transaction, reduce the available quantity and associate the consumption with the Work Order, Asset, Technician and Service Provider where applicable. This aligns with the FSD requirement that warehouse stock availability be mapped to maintenance usage and spare parts be linked to maintenance jobs. Returns, corrections and transfers should create separate inventory transactions rather than directly changing the Current Stock field, providing a complete auditable stock ledger.
From the developer perspective, the recommended processing relationship should be Spare Part Master → Category/UOM → Supplier → Warehouse/Rack/Bin → Opening/Received Stock → Available Stock → Maintenance Work Order → Part Issue/Consumption → Return/Adjustment → Current Balance → Reorder Alert. The Spare Part Master, Warehouse Stock Balance, Stock Transactions, Supplier Mapping and Work Order Consumption should be maintained as separate but linked database entities. This design will allow the Spare Parts List tab to always present the current inventory position while preserving the complete transactional history needed for stock control, maintenance costing and audit reporting.
The Stock Transactions screen should be developed as the complete transactional ledger for all spare-parts inventory movements within Asset360. Unlike the Spare Parts List, which represents the current stock position, this screen should show how and why the quantity changed. Every Receipt, Issue, Return, Transfer or Adjustment should create an individual stock transaction with a unique Transaction Number, Transaction Date/Time, Transaction Type, Item Code, Item Name, Quantity, From/To Location, Reference Number and User. The Warehouse Master supports multiple warehouses and a Warehouse → Rack → Bin hierarchy, so transactions should update stock against the appropriate storage location rather than maintaining only one global quantity.
The top of the screen should provide summary cards such as Total Transactions, Stock In, Stock Out, Transfers and Adjustments. These figures should be calculated dynamically according to the user's selected date range, warehouse/location and access permissions. Below this, the Transactions List should provide search and filtering by Transaction Number, Item Code/Name, Transaction Type, From Date, To Date and Location. Selecting a transaction should display the complete information in the Transaction Details panel on the right, allowing the user to review the movement without leaving the screen. Pagination should be implemented server-side because the transaction table can become very large over the operational life of the system.
The developer should support different transaction behaviors depending on the Transaction Type. A Receipt increases stock at the selected warehouse/bin and can reference a PO, GRN, supplier delivery or opening stock. An Issue reduces stock and should normally reference a Maintenance Work Order, asset, technician or other authorized consumption reason. A Return adds previously issued but unused material back into available stock. A Transfer should reduce stock from the source warehouse/location and increase stock at the destination, while retaining both locations under the same transfer reference. An Adjustment should be used for controlled corrections arising from physical counts, damaged stock, discrepancies or authorized stock corrections and should require an adjustment reason.
The New Transaction button should open the transaction-entry form and dynamically change the fields according to the selected transaction type. For example, selecting Issue should require Item, From Warehouse, Rack/Bin, Quantity, Work Order/Reference and Issued To, whereas Transfer should require From Warehouse/Bin and To Warehouse/Bin. The system must validate available stock before an Issue or Transfer is submitted and should prevent the transaction where the requested quantity exceeds available stock unless an authorized negative-stock policy has explicitly been configured. The FSD links warehouse stock availability directly to maintenance usage and spare-parts allocation, making this validation important for preventing maintenance delays and stock mismatches.
When a spare part is issued against a Work Order, the developer should create a relationship between the Stock Transaction, Spare Part, Work Order and Asset. The maintenance team should therefore not need to enter the same consumption information twice. For example, if five electrical breakers are issued for a corrective-maintenance Work Order, confirmation of the Issue should reduce the relevant warehouse stock by five and simultaneously make that consumption visible against the Work Order for maintenance history and costing. The FSD specifically defines spare parts as consumable or replaceable components used for preventive and corrective maintenance.
The Transaction Details panel should be read-only after posting and should display the complete audit information including Transaction Number, Date/Time, Type, Reference Number, Work Order where applicable, Item Code, Item Name, Category, UOM, Quantity, Unit Cost, Total Value, From Location, To Location, Issued To/Received From, Remarks, Created By and Created On. For a Transfer, both source and destination should be visible. For an Issue, the associated Work Order and technician should be shown. For an Adjustment, the adjustment reason and authorization reference should be displayed.
The View action should open the complete transaction details, while Print should produce a Stock Receipt, Issue Voucher, Transfer Note or Adjustment document according to transaction type. Export should export the currently filtered transaction history. Editing should be tightly controlled: once a stock transaction has been posted and has changed inventory, the developer should avoid allowing users to simply change its quantity or item. If an error is identified, Asset360 should preferably create a reversal/correction transaction linked to the original transaction. This provides a much stronger audit trail than modifying historical stock records.
The backend should maintain stock using a transaction-ledger approach. The recommended processing relationship is Spare Part → Warehouse → Rack/Bin → Stock Transaction → Reference/Work Order → Quantity Movement → Warehouse Balance → Overall Available Stock. Each posted transaction should execute within a database transaction so that the stock ledger, warehouse balance and Work Order consumption either update together successfully or roll back together if processing fails. UOM should be taken from the configured master because the FSD requires standardized measurement units for spare-parts consumption and inventory operations.
The overall screen maneuvering should therefore follow Stock Transactions → Search/Filter Existing Transactions → Select Transaction → Review Details, or for a new movement, New Transaction → Select Transaction Type → Select/Scan Spare Part → Select Warehouse/Bin → Enter Quantity → Select Reference/Work Order → Validate Available Stock → Review → Submit/Post → Update Stock Balance → Generate Transaction Number → Update Work Order/Inventory History. This design will make the Stock Transactions screen the auditable source of every quantity movement while the Spare Parts List continues to present the resulting real-time stock position.
The Reorder Planning screen should be developed as the inventory replenishment workspace for identifying spare parts that are approaching or have fallen below the configured reorder level. 32.The Asset360 AI Assistant 
should be developed as an intelligent interaction layer across the complete Asset360 platform rather than as a standalone chatbot. The assistant should understand natural-language questions and securely retrieve information from the Asset Register, Maintenance, Inventory, Verification & Audit, Auto-Discovery, Location, Contracts, Documents and reporting modules according to the logged-in user's permissions. The FSD specifically identifies AI-assisted data capture, normalization, duplicate detection, discovery matching and confidence scoring, as well as functions such as OCR of manufacturer labels, category suggestions, asset-history summaries, natural-language asset search and maintenance recommendations. The assistant should therefore be able to answer questions such as “Show HVAC assets due for maintenance this month,” “Which assets have the highest maintenance cost?”, or “Which spare parts may run out before the next preventive maintenance cycle?” using live Asset360 data rather than generating unsupported answers.
For Asset Search and Asset Intelligence, the AI Assistant should allow users to locate assets using conversational queries instead of manually building filters. A user should be able to ask for assets by category, location, custodian, department, status, age, warranty, purchase value, maintenance condition or combinations of these parameters. For example, “Show laptops assigned to Finance at Dubai HQ that are more than four years old” should be converted by the AI layer into structured search criteria and executed against Asset360 APIs. When an individual asset is selected, the assistant should be capable of producing an Asset 360° summary covering identification, current location/custodian, acquisition information, maintenance history, movements, verification results, warranty/AMC, documents and relevant exceptions. The FSD already requires AI to support natural-language asset search and asset-history summarization.
The assistant should provide AI-assisted Asset Registration and Smart Capture. When a mobile or web user photographs a manufacturer's label, the AI service should perform OCR and extract potential values such as manufacturer, model, serial number and product information. The extracted information should be presented as suggestions that the user can confirm or correct rather than being written directly into the Asset Master. Based on the extracted values and existing master data, AI can recommend the most likely Asset Group, Class, Category and Subcategory and indicate a confidence score. The FSD explicitly envisages photographing manufacturer labels, OCR of serial/model information and recommendations for manufacturer and category/subcategory.
A major AI function should be duplicate detection and data-quality improvement. During asset registration, receiving, discovery reconciliation or bulk imports, the AI engine should compare Serial Number, Manufacturer, Model, Asset Tag, hostname, MAC address, purchase information and other identifying fields against existing records. Where a possible duplicate is found, the assistant should present the matching records together with the reason and confidence level—for example, “92% potential duplicate: same serial number and manufacturer.” The user should then choose whether to open the existing asset, continue creating the new asset or route the case for review. The FSD explicitly includes possible-duplicate detection as part of AI-assisted processing.
Within Maintenance, the AI Assistant should analyze asset age, previous breakdowns, preventive-maintenance history, downtime, failure codes, costs, meter readings and other available condition information to identify assets needing attention. It should answer queries such as “Which assets repeatedly fail?”, “Show the top ten assets by maintenance cost,” and “Why is Chiller CH-002 receiving frequent work orders?”. Based on available historical information, it can recommend actions such as inspection, preventive maintenance, component replacement or further technical investigation. This aligns directly with the FSD requirement for AI to recommend maintenance actions.
Where sufficient historical and condition data exists, Asset360 can extend this into predictive maintenance, but the developer should clearly distinguish prediction from confirmed facts. The AI may calculate a risk score such as Low, Medium or High and provide the factors contributing to that assessment—for example repeated failures, increasing downtime or abnormal sensor values. Any probability displayed to the user must come from an implemented predictive model and supporting data; the application should not invent arbitrary percentages. Recommended actions should always identify the source information used so that a maintenance manager can make the final operational decision.
The AI Assistant should also perform Inventory and Spare Parts intelligence. It should combine current warehouse balances, reorder levels, stock transactions, consumption against Work Orders, supplier lead times and open procurement quantities to identify shortages, slow-moving items or abnormal consumption patterns. Queries such as “Which critical parts are below reorder level?”, “Which spare parts have not moved for 12 months?” or “Will we have enough filters for next month's HVAC PM schedule?” should be supported. Recommendations can include internal warehouse transfer, reorder quantity suggestions or review of slow-moving stock. The recommendation should link the user directly to the relevant Spare Part, Reorder Planning or Stock Transaction screen for review before any transaction is created.
For Auto-Discovery reconciliation, AI should assist IT teams with matching discovered network devices to registered assets. The assistant can use values such as hostname, serial number, manufacturer, model, MAC address and other discovered attributes to propose possible Asset360 matches and return confidence scores and reasons. Users should be able to ask “Show discovered devices that are not matched to the Asset Register” or “Why does the system think this device belongs to Asset AS-002134?”. The FSD specifically identifies suggested discovery matching and AI-supported discovery reconciliation.
For Verification and Audit, the AI Assistant should help users analyze verification results rather than replace the controlled audit process. It should summarize findings such as Not Found assets, Wrong Location, Wrong Custodian, damaged assets and unregistered assets and identify recurring patterns by site, department or category. A manager could ask “Summarize the Dubai HQ audit exceptions” or “Which locations have the highest number of missing assets?”. AI should retrieve the actual audit transactions and generate a concise management explanation while allowing the user to drill down to the underlying evidence. It must not automatically modify Asset Master data based on an AI conclusion.
The assistant should provide Management Analytics and Natural-Language Reporting. Instead of requiring users to navigate through multiple reports, they should be able to ask questions such as “What was the maintenance cost by category during the last six months?”, “Show assets due for warranty expiry in the next 90 days,”, “Compare asset verification performance between Site A and Site B,” or “Show maintenance work orders that exceeded SLA.” The AI layer should translate the request into approved report queries, retrieve the actual information and return tables, summaries or charts. Where appropriate, the result should offer View Records, Open Report or Export so the user can verify the underlying dataset.
The Recommended Actions area should convert AI findings into reviewable recommendations. Examples include Reorder Spare Part, Schedule Maintenance, Review Overdue Work Orders, Investigate an Asset, Review Discovery Match, Review Audit Exception or Review Contract Expiry. Critically, there should be a distinction between recommendation and execution. Clicking a recommendation should open the appropriate Asset360 transaction screen with relevant information pre-populated; the user should review and submit the transaction through the normal workflow. AI should not independently transfer assets, close audits, dispose assets, approve transactions or post inventory adjustments.
The AI Assistant should also provide contextual screen assistance. When launched from an Asset record, it should automatically understand the selected asset context; when launched from a Work Order, it should understand the Work Order; and when launched from Reorder Planning, it should understand the selected spare part. This would allow questions such as “Summarize this asset,” “Why was this work order raised?”, or “Show the consumption history for this spare part” without the user repeatedly entering IDs. Context should be passed as secure internal identifiers rather than by copying entire application records into the conversation.
The developer should implement Quick Actions / Suggested Prompts to guide users. Examples can include Show PM Due This Week, Check Low-Stock Spare Parts, Find Unverified Assets, Show Overdue Work Orders, Generate Asset Health Summary, Find Warranty Expiry, Summarize Audit Exceptions and Review Discovery Conflicts. These are effectively predefined AI intents that invoke controlled backend functions, making common AI functions faster and more predictable than purely free-text interaction.
The assistant should support a confidence and explanation model. When AI performs classification, duplicate detection, discovery matching or prediction, the result should include a confidence level and a short explanation of the evidence used. For example: “Suggested match: AS-00248 — High confidence — serial number exact match, manufacturer match and hostname similarity.” This is especially important because the FSD specifically calls for confidence scoring as part of AI-assisted processing. Low-confidence results should always require user review.
From the security perspective, the AI Assistant must use the same RBAC and data-scope permissions as the rest of Asset360. A user should never be able to retrieve an asset, financial value, employee-related information, location or document through the AI interface if they could not view that information through the standard application. The FSD requires role-based access supplemented by company, business unit, cost center, site, department and asset-class scopes, including field-level restrictions for sensitive information. Therefore every AI request should first resolve the user's identity and permissions and then query only authorized data.
Technically, the AI Assistant should not be given unrestricted direct access to production database tables. A safer architecture is User Question → AI Orchestrator → Intent/Entity Recognition → Asset360 Authorized APIs → Data Retrieval → AI Reasoning/Summarization → Response → Optional Recommended Action. Actions should follow AI Recommendation → User Review → Existing Asset360 Screen → Business Validation → Approval Workflow → Transaction Commit. This ensures the AI layer enhances the existing application rather than bypassing its business rules.
Every important AI interaction should also be auditable. Asset360 should maintain the user, date/time, question or intent, records accessed where appropriate, recommendation generated, confidence/model information where relevant and whether the user accepted, ignored or rejected the recommendation. This will allow administrators to evaluate AI usefulness, investigate incorrect recommendations and improve models over time.
The overall objective should therefore be to make the AI Assistant an intelligent navigation, search, analytics, recommendation and data-quality layer across Asset360. It should reduce the time required to locate information, understand asset history, analyze maintenance, reconcile discovery results, detect duplicates, manage inventory and interpret audits—while keeping all controlled transactions, approvals and final business decisions inside the existing Asset360 workflows.
The Master Data – Asset Groups screen should be developed as the primary configuration screen for defining the highest level of the Asset360 asset-classification hierarchy. The screen should allow authorized administrators to create and maintain Asset Groups such as Information Technology, Buildings & Facilities, Plant & Machinery, Vehicles, Furniture & Fixtures, Medical Equipment, Tools, Software Assets and Licenses. These groups should subsequently drive the hierarchy Asset Group → Asset Class → Category → Subcategory → Asset. Asset Group Code should be unique and should act as the stable system reference, while Group Name and Description provide the user-facing definition. The screen should also support an Asset Type classification such as Physical, Intangible or Both and an Active/Inactive status. Once an Asset Group has been referenced by assets or lower-level master records, it should not be physically deleted; it should instead be made inactive to preserve historical relationships.
The main Asset Groups List should be displayed as a server-side paginated grid containing Group Code, Group Name, Description, Asset Type, Total Assets, Status and Actions. The Total Assets value should be calculated dynamically from assets associated with the group and should not be editable. Clicking a row should select it and populate the Asset Group Details panel on the right without navigating away from the page. The details panel should display Group Code, Group Name, Description, Asset Type, Status, Total Assets, Created By, Created On, Last Modified By and Last Modified On. A Related Information section should additionally show the number of Asset Classes, Categories, Subcategories and Assets associated with the selected group, with each count acting as a drill-down link to the corresponding filtered records.
The screen should provide a global search field supporting partial searches against Group Code, Group Name and Description. Separate filters should be provided for Status and Asset Type. Status should allow values such as All, Active and Inactive, while Asset Type should allow All, Physical, Intangible and Both. The Filter button should apply the selected criteria, while Reset should clear all search and filter conditions and reload the complete list. Filtering, sorting and pagination should preferably be performed server-side so that the screen remains responsive when the master hierarchy and related asset volumes become large.
The Add Asset Group button should open a Create mode form containing Group Code, Group Name, Description, Asset Type and Status. Mandatory-field validation should occur both in the UI and API layer. Group Code must be unique and should preferably become non-editable after the group is used operationally. Group Name should also be checked for possible duplicates. Save should validate and commit the record, Save & New can save the current record and immediately prepare another blank form, and Cancel should close the entry form without committing unsaved changes. All successful changes should record Created/Modified user and timestamps automatically.
Each row should provide View, Edit and More Actions. View should open the selected master in read-only mode. Edit should allow authorized users to modify fields such as Group Name, Description, Asset Type where business rules permit, and Status. The More Actions menu can provide View Classes, View Categories, View Assets, Duplicate/Copy, Activate/Deactivate and View Audit History. Delete should only be offered when a newly created group has no dependent records. If classes, categories, subcategories or assets already reference the group, the API should reject deletion and instruct the user to deactivate it instead. Before deactivation, Asset360 should warn the user about the number of dependent active records.
The top-level tabs should allow users to maneuver between related Master Data components such as Asset Groups, Classes, Categories, Subcategories, Locations, Departments, Cost Centers and Suppliers, with additional masters available through More. Moving between these tabs should retain the same overall Master Data layout and permission model. More can contain additional masters such as Manufacturers, UOM, Status Codes and other configurable reference masters. The classification screens should follow the hierarchy so that, for example, when creating an Asset Class, the user must select its parent Asset Group; when creating a Category, the applicable Group/Class relationship should be selected; and Subcategory should similarly inherit its parent classification.
The Import action should support bulk creation or update of Asset Groups through a predefined Excel/CSV template. The developer should implement this as a controlled process: Download Template → Upload File → Validate Records → Display Validation Results → Correct/Reject Invalid Rows → Confirm Import → Commit Valid Records. Duplicate codes, missing mandatory information and invalid Asset Types should be detected before posting. The system should provide an import result showing successful, failed and skipped records rather than silently ignoring errors. The Export action should export either all Asset Groups or the currently filtered dataset, depending on the selected export option.
The developer should implement comprehensive role-based security for the screen. Users with View permission should only be able to search, filter and inspect master data; Master Data Editors can create and modify records; and only appropriately authorized administrators should be able to activate/deactivate or perform bulk imports. Every creation, modification, status change, import and permitted deletion should be written to the system audit trail with User, Date/Time, Previous Value, New Value and Action Type.
From the database and API perspective, Asset Group should remain a separate master entity with a stable AssetGroupID as the internal primary key and Group Code as the business identifier. Related Asset Classes, Categories and Assets should reference the internal ID rather than storing Group Name as free text. The recommended hierarchy is AssetGroup → AssetClass → Category → Subcategory → AssetMaster. This prevents duplicated classification information and ensures that renaming a group does not require updating every asset record.
The overall screen maneuvering should therefore follow Master Data → Asset Groups → Search/Filter → Select Group → View Details & Related Information, or for maintenance of master information, Add/Edit Asset Group → Validate → Save → Refresh List → Update Related Counts → Record Audit History. The developer should treat this screen as a core configuration component because the classification hierarchy created here will subsequently control asset registration, searching, reporting, maintenance configuration, audit segmentation, inventory relationships and AI-assisted asset categorization throughout Asset360.
The Reports & Analytics screen should be developed as the centralized reporting and management intelligence workspace of Asset360. It should consolidate operational information from the Asset Register, Maintenance, Inventory, Verification & Audit, Receiving & Tagging, Tracking & Location, Contracts/AMC, Suppliers and financial/asset-value information and present it according to the logged-in user's role and data-access scope. The screen should not maintain separate manually entered reporting data; all KPIs, charts and reports should be generated from live or appropriately refreshed Asset360 transactional data. The developer should design the reporting layer so that clicking a KPI, chart segment or report value can drill down to the actual records responsible for that value.
The upper section should provide report-category navigation such as Asset Reports, Maintenance Reports, Inventory Reports, Financial Reports, Compliance/Audit Reports and Custom Reports. Selecting a category should either display the relevant analytical dashboard or open the available reports within that category. The screen should provide common filters including Report Category, Report Type, Date Range, Company, Location, Department, Cost Center, Asset Group/Class/Category and Status, with additional report-specific filters displayed dynamically. For example, Maintenance Reports may require Work Order Type, Priority, Technician and Service Provider, whereas Inventory Reports may require Warehouse, Spare Part Category and Stock Status. Apply Filters should refresh all KPIs, charts and report datasets simultaneously, while Reset should restore the user's default reporting scope.
The dashboard KPI cards should provide management-level information such as Total Assets, Active Assets, Assets Under Maintenance, Active/Overdue Work Orders, Maintenance Cost, Asset Locations, Inventory Value, Low-Stock Items, Audit Compliance Rate and Missing/Unverified Assets depending on the selected report category. Each KPI should be calculated by the backend reporting service and should display the reporting period used. Where comparison information is available, the card can show movement against the previous equivalent period. Clicking a KPI should open the supporting report or filtered transaction list—for example, selecting Active Work Orders should show the Work Orders contributing to that count rather than simply displaying a static number.
The analytical section should support interactive bar charts, line charts, donut/pie charts and trend charts. Asset analytics can include Assets by Category, Assets by Location, Assets by Department, Asset Status, Asset Age, Acquisition Trend and Asset Lifecycle Status. Maintenance analytics can include Work Orders by Status/Priority, Preventive vs Corrective Maintenance, Maintenance Cost Trend, Asset Downtime, Repeat Failures, SLA Performance and Top Maintenance-Cost Assets. Inventory analytics should cover Current Stock, Inventory Valuation, Low/Out-of-Stock Parts, Spare-Part Consumption, Stock Movement and Slow/Non-Moving Stock, while audit analytics should show Verified, Not Found, Wrong Location, Wrong Custodian, Damaged and Unregistered Asset exceptions.
Charts should be interactive rather than decorative. If a user clicks the In Maintenance segment of an Asset Status chart, for example, the application should open or populate a detailed grid containing only assets currently under maintenance. Similarly, clicking a location bar should filter the dataset to that location. The developer should implement tooltips showing the value, percentage and relevant context, and users should be able to move from Summary → Chart → Detailed Records → Individual Asset/Work Order/Transaction without losing the selected reporting filters.
The Recent Reports section should maintain reports recently generated by the user or available within their permission scope. Recommended columns are Report Name, Category, Date Generated, Generated By, Format and Actions. Actions should include View, Download, Regenerate and More Options. The More menu can contain Schedule Report, Duplicate Report Configuration, Share/Distribute where permitted and View Generation History. Generated reports should retain the parameters used so that Regenerate can execute the same report using either current data or the originally selected period.
The Create Report button should provide options for Standard Report, Custom Report, Scheduled Report and Export Data. Standard Report should allow selection from predefined Asset360 reports. Custom Report should launch a report builder where authorized users select the data domain, fields/columns, filters, grouping, sorting, aggregation and output format. The developer should avoid exposing physical database tables directly to users; the custom-report builder should work against approved reporting datasets or API models so security rules and business definitions remain consistent.
The Scheduled Reports functionality should allow authorized users to configure automatic report generation. The user should select the report, reporting parameters, output format such as PDF, Excel or CSV, frequency such as Daily, Weekly, Monthly or Quarterly, execution date/time and authorized recipients or distribution mechanism. The Scheduled Reports grid should display Report Name, Frequency, Next Run, Last Run, Status and Actions. Actions should support Edit Schedule, Run Now, Pause/Resume, View History and Delete Schedule. Report execution should preferably be handled by a background job service rather than keeping the user's browser session open.
Financial and lifecycle reporting should provide information such as asset acquisition value, current/book value where available, depreciation information, maintenance expenditure, total cost of ownership and replacement candidates. These reports should use authoritative Asset360 financial information or integrated ERP data where configured. The developer should not calculate accounting values using arbitrary assumptions; depreciation methods, useful life, residual values and other financial parameters must come from configured asset/finance data.
The screen should also support AI-assisted analytics. A user could ask the Asset360 AI Assistant questions such as “Show the ten assets with the highest maintenance cost this year,” “Which locations have the most audit exceptions?” or “Show spare parts likely to fall below reorder level.” The AI should convert the natural-language request into approved reporting parameters, query the authorized Asset360 reporting APIs and present the resulting analysis. AI-generated explanations should remain linked to the actual underlying records so users can verify the result rather than receiving unsupported narrative conclusions.
From a technical perspective, reporting should follow a structure such as Operational Modules → Reporting APIs/Data Model → Permission & Scope Validation → Aggregation/Calculation Service → Filters → KPI/Chart/Grid → Drill-Down → Export/Scheduling. For larger implementations, the developer may introduce optimized reporting views, cached aggregates or a reporting database to prevent complex analytics from affecting normal Asset360 transactions. Heavy exports and large reports should execute asynchronously with a progress/status notification when completed.
Security is particularly important because reporting can aggregate information that a user might otherwise not be permitted to see. Every report request must apply the same RBAC and organizational data scope as the operational modules. A user authorized only for Dubai HQ, for example, should not obtain information about another location simply by creating a custom report or using AI. Export permissions should also be independently controlled because downloading data creates an additional information-security risk.
Finally, the developer should implement a consistent maneuvering flow of Reports & Analytics → Select Report Category → Select Report/Analytics View → Apply Filters → Review KPIs and Charts → Click KPI/Chart for Drill-Down → Review Detailed Records → Open Source Transaction if required → Export/Save/Schedule Report. The objective is to make this screen more than a collection of static charts: it should operate as an interactive management-analysis layer where every summarized number can be traced back to the underlying Asset360 asset, maintenance, inventory or audit transaction.
The Administration Module should be developed as the centralized control and configuration area of Asset360. It should allow authorized administrators to manage users, roles, organizational hierarchy, system parameters, master-data configuration, integrations, audit logs, notifications, and backup/scheduling functions without changing application code. Administration functions must be controlled through role-based access and organizational data scope so that only authorized users can view or modify configuration information. The Administration menu should contain the major functions User Management, Roles & Permissions, Company & Organization, System Configuration, Master Data Setup, Integrations, Audit Logs, Email Notifications, and Backup & Scheduler. The user interface should follow the agreed Asset360 standard: white background, Arial font, black text, purple icons/highlights/buttons, light-grey borders, and light-purple selected states.
User Management
The User Management screen should maintain all users who can access the Asset360 web and mobile applications. The primary list should display User ID, Employee ID where applicable, User Name, Full Name, Email, Mobile Number, Company, Business Unit, Department, Location, Role, User Type, Status, Last Login and Actions. The screen should provide search and filters for Company, Business Unit, Department, Location, Role, User Type and Status. Administrators should be able to create a user, edit user information, assign one or multiple roles, allocate organizational and location access, activate/deactivate an account and review user activity. Password-related functions should follow the configured authentication model; where SSO/identity-provider authentication is used, Asset360 should not attempt to manage the external password itself.
The Add/Edit User form should capture the user's identity and organizational association and allow the administrator to define exactly what areas of the organization the user is permitted to access. A user may, for example, have access to only Dubai HQ or to multiple companies and locations. These assignments must be enforced by backend APIs and not merely by hiding records in the UI. Deactivation should immediately prevent new access while retaining historical transactions created or approved by that user.
Roles & Permissions
The Roles & Permissions screen should implement configurable Role-Based Access Control (RBAC). Administrators should be able to define roles such as System Administrator, Asset Manager, Asset Custodian, Maintenance Manager, Technician, Inventory Controller, Auditor, Approver, Finance User and Read-Only User. Each role should have configurable permissions against individual Asset360 modules and functions.
Permissions should be configurable at action level rather than only module level. For each module or screen, the administrator should be able to define permissions such as View, Create, Edit, Delete, Approve, Reject, Assign, Transfer, Verify, Execute, Export, Import and Administer, depending on the function. The permission screen should use an expandable matrix such as Module → Submodule → Screen/Function → Permission. A Select All option can simplify role configuration, while sensitive permissions such as Delete, Approval, Administration and Export should remain clearly identifiable.
The role screen should also allow administrators to view which users are assigned to a role, duplicate an existing role as the basis for a new one, activate/deactivate roles and review permission-change history. Changes to role permissions must be audited. Where practical, the system should warn the administrator if a permission change will affect currently active users.
Company & Organization
The Company & Organization section should maintain the organizational hierarchy used throughout Asset360. Based on the screens designed for this module, it should contain Companies, Business Units, Departments, Locations and Cost Centers. These records should be relational rather than independent text values. The expected structure should support relationships such as Company → Business Unit → Department, while Locations and Cost Centers can be associated with the relevant company, business unit and/or department according to configuration.
The Companies screen should maintain the highest organizational entity and capture Company Code, Company Name, legal/business information, region, country, currency and status as applicable. Business Units should subsequently be linked to their parent Company. The Business Units screen should maintain Business Unit Code, Name, Company, responsible person and status, while the Departments screen should maintain Department Code, Department Name, Business Unit, Company, Department Head, Location, Cost Center and status.
The Locations screen should define physical operating locations such as head offices, offices, warehouses, plants, stores, service centers and sites. Location information should include Location Code, Name, Company, Business Unit, Country, City, Address, Location Type and Status, with provision for hierarchical locations where necessary. Actions should include View Details, Edit Location, Manage Departments, Assign Cost Center, Assign Users, Activate/Deactivate and Delete where dependency rules permit.
The Cost Centers screen should maintain Cost Center Code, Cost Center Name, Company, Business Unit, Department, Location, Cost Center Type, Currency and Status. Cost centers should subsequently be selectable during asset registration, maintenance transactions and financial reporting. The system should prevent uncontrolled deletion of organizational masters already referenced by assets or transactions; administrators should normally Deactivate such records instead.
System Configuration
The System Configuration screen should provide a configurable parameter framework so administrators can control application behaviour without source-code modification. As reflected in the proposed screen structure, configuration should be separated into General Settings, Asset Settings, Inventory Settings, Maintenance Settings, Workflow & Approvals, Numbering & Codes, and Lookups & Lists.
Each configuration parameter should maintain a Parameter Name, Module, Category, Current Value, Default Value, Parameter Type, Status and Description. Parameter types should support Text, Number, Boolean, Date, Lookup and other controlled values where required. The developer should avoid hard-coding configurable business rules into individual screens when they can reasonably be represented through these configuration parameters.
Asset Settings
The Asset Settings area should control asset-specific behaviour. Examples include Default Asset Status, Asset Code Prefix, Auto Generate Asset Code, Asset Code Format, Default Asset Classification, Mandatory Asset Fields, Enable Asset Images, Default Warranty Period, Depreciation Method where applicable, and QR/Barcode/RFID-related settings. Configuration should determine how the Asset Registration screens behave.
For example, if Auto Generate Asset Code = Yes, the asset creation API should automatically generate the next identifier using the configured numbering format. If a field such as Serial Number or Location is configured as mandatory, both the web/mobile UI and server API must validate it before allowing the transaction to complete. Configuration therefore needs to be consumed dynamically by operational modules rather than simply displayed as administrative reference data.
Inventory and Maintenance Settings
The Inventory Settings area should provide configuration controlling spare parts, stock transactions, warehouses/stores, reorder parameters, units of measure and other inventory behaviour defined in the functional design. Configuration may include defaults used for stock transactions, reorder calculations and inventory controls. These parameters should integrate directly with the Inventory and Spare Parts modules.
The Maintenance Settings section should control Work Order and Preventive Maintenance behaviour. It should support configurable defaults such as Work Order numbering, priorities, statuses, maintenance types, SLA-related parameters and other maintenance controls. Where the FSD requires approval or escalation of maintenance activities, these rules should reference Workflow & Approvals rather than being embedded independently inside the Work Order screen.
Workflow & Approvals
The Workflow & Approvals configuration should allow administrators to define approval rules for business processes such as Asset Movement/Transfer, Asset Disposal, Asset Verification exceptions, Work Orders, Inventory transactions and other transactions requiring authorization. A workflow should define Transaction Type, triggering condition, approval level, approver role/user, sequence, escalation conditions and status.
The developer should support multi-level approvals where required. A transaction might follow Requester → Department Manager → Asset Manager → Final Approval, with the exact routing driven by configuration. Approval actions must record Approver, Date/Time, Comments and Decision. Rejected transactions should capture a mandatory rejection reason. Workflow changes should affect new transactions while maintaining the approval history and rule context of transactions already processed.
Numbering & Codes
The Numbering & Codes screen should centrally configure identifiers used across Asset360. Numbering schemes may be required for Asset IDs, Work Orders, Maintenance Plans, Audit Numbers, Movement Requests, Stock Transactions and other business documents.
The configuration should support elements such as Prefix, Sequence Length, Starting Number, Current/Next Number, Year/Month component, Separator and Reset Rule. For example, an asset numbering structure could produce a controlled value based on a configured pattern rather than allowing users to manually create inconsistent codes. Sequence generation must occur server-side and should be concurrency-safe to prevent duplicate numbers when multiple users create transactions simultaneously.
Lookups & Lists
The Lookups & Lists section should provide centrally maintained dropdown values used throughout Asset360. Instead of developers hard-coding values such as statuses, priorities, condition codes or transaction reasons into screens, authorized administrators should be able to maintain configurable lists where the FSD permits.
Each lookup should contain a Lookup Type, Code, Display Value, Sequence/Display Order, Status and possibly Description. Existing lookup values referenced by historical transactions should normally be deactivated rather than deleted. The application should return only applicable active lookup values for new transactions while continuing to display inactive historical values against existing records.
Master Data Setup
The Master Data Setup module should provide administrative control over common business masters required by Asset360. This should include the asset classification structure already defined as Asset Group → Asset Class → Category → Subcategory, together with applicable supporting masters such as Suppliers, Manufacturers, UOM and other reference data defined by the FSD.
Master-data screens should follow a common design pattern: Search → Filters → Master List → Add/Edit → Status → Actions → Import/Export. Every master record should have an internal immutable ID, business code, name/description, status and audit information. Relationships should use IDs rather than duplicated free-text descriptions. The system must enforce uniqueness, mandatory fields, dependency validation and parent-child relationships at API/database level.
Bulk master-data import should follow a controlled workflow of Download Template → Upload → Validate → Preview → Display Errors → Confirm Import → Commit → Generate Import Summary. The application should never silently import invalid records. Export should respect the user's security scope and currently applied filters.
Integrations
The Integrations administration screen should manage interfaces between Asset360 and external enterprise applications where required. Each integration configuration should identify the Integration Name, External System, Integration Type, Direction, Endpoint/reference configuration, authentication method, frequency, status and last synchronization information.
The screen should provide operational visibility such as Last Successful Sync, Last Failed Sync, Records Processed, Error Count and Current Status. Authorized administrators should be able to View Configuration, Test Connection, Enable/Disable Integration, Run/Retry Sync where permitted and View Integration Logs. Credentials, API keys and secrets must never be displayed as plain text and should be stored using an appropriate secrets-management mechanism.
Audit Logs
The Audit Logs screen should provide a tamper-resistant history of important user and system activity. Asset360 should record actions such as Login, Logout, Create, Edit, Delete where permitted, Activate/Deactivate, Approval, Rejection, Import, Export, Configuration Change and administrative security changes.
The audit screen should provide filters for Date Range, User, Module, Action Type, Record/Reference ID, Company, Location and Result/Status. Each log entry should capture sufficient information to identify Who performed the action, What changed, When it occurred and, where relevant, Previous Value and New Value. Administrators should be able to open a log record for detailed inspection, but normal application users should not be able to modify audit history.
Email Notifications
The Email Notifications section should allow administrators to configure application-generated communications. Notification templates should be available for events such as Work Order assignment, Approval required, Approval/Reject result, Asset Transfer, Audit assignment, Maintenance due, Contract/AMC expiry, Warranty expiry, Low Stock/Reorder and other events defined in the FSD.
Each template should contain Template Name, Event, Subject, Message Body, Recipient Rule, CC/BCC where permitted, Status and Delivery Channel. Placeholders should allow controlled insertion of transaction information such as Asset Number, Work Order Number, Approver, Due Date and Location. The developer should provide preview/test functionality before a template is activated.
Backup & Scheduler
The Backup & Scheduler area should provide administrative visibility and control over scheduled application jobs where applicable. It should show Job Name, Job Type, Frequency, Last Run, Next Run, Status and Result. Jobs can include configured report generation, synchronization tasks, notification processing and supported backup activities.
Administrators should be able to View Schedule, Edit Schedule, Run Now, Pause/Resume and View Execution History, subject to permissions. Long-running operations should execute as background services rather than depending on an active browser session. Failures should be logged and surfaced to appropriate administrators.
Common Filters, Actions and Screen Behaviour
All Administration screens should use a consistent interaction pattern. The upper portion should provide contextual filters and search, while the main portion displays a paginated data grid. Filters should use white dropdowns with black Arial text and purple focus indicators. Typical buttons should be Reset and Apply Filters, with Advanced Filters available when the module has additional criteria. Tables should support server-side sorting, filtering and pagination for large data volumes.
Each record should have an Actions (…) menu containing only operations permitted for the current user and relevant to the record's state. Common actions should include View Details, Edit, Assign, Activate, Deactivate, View History and Delete, with module-specific options added where necessary. The application should not rely solely on hiding an action button for security—the corresponding backend API must independently validate permission before executing the operation.
Validation, Security and Audit Requirements
All administrative changes must be validated at both UI and API levels. Mandatory fields, unique codes, valid parent-child relationships, duplicate records and dependent records should be checked before committing changes. Where an administrator attempts to deactivate or modify a record already used operationally, the application should display the impact and request confirmation where appropriate.
Every sensitive administrative transaction should record User ID, Action, Module, Record ID, Date/Time, Previous Value, New Value and transaction result. Role changes, user-access changes, workflow changes and system-configuration changes are particularly important and should always be auditable. The application should apply least-privilege principles and enforce organizational scope at every API endpoint.
Overall Administration Navigation
From a developer perspective, the intended maneuvering should be Administration → Select Administrative Function → Search/Filter → Select Record → View/Edit/Perform Action → Validate → Save → Refresh → Audit Change. Related entities should support contextual navigation—for example, Company → Business Unit → Department → Location/Cost Center → Users/Assets—so administrators can understand dependencies without repeatedly navigating back to separate screens.
The Administration module should ultimately function as the configuration and governance layer of Asset360. Changes made here should dynamically influence the Asset Management, Maintenance, Inventory, Receiving & Tagging, Tracking & Location, Verification & Audit, Reports & Analytics, mobile application and AI-assisted functionality wherever applicable. This architecture will allow Asset360 to support different customers and organizational structures through configuration rather than customer-specific source-code changes.
Asset360 – Integrations Screen: Developer Functional Description
The Integrations screen should be developed as the central administration workspace for configuring, managing, monitoring, and troubleshooting all interfaces between Asset360 and external systems. The FSD positions Asset360 as an enterprise platform capable of exchanging information with ERP, procurement, HR, directory, service desk, CMDB, IoT/RTLS and other enterprise systems through secure APIs. The screen should therefore not function merely as a static list of interfaces; it should provide administrators with operational control over integration configuration, synchronization, connectivity, status, errors, and execution history.
The screen should follow the established Asset360 UI convention: white background, Arial font, black text, purple as the primary accent, purple/black icons, white tables with light-grey borders, and light-purple highlighting for selected tabs. The main screen should contain the tabs All Integrations, ERP Systems, HR Systems, IT Service Management, Identity & Security, IoT & Devices, and Other Systems. Selecting a tab should filter the same underlying integration repository rather than loading unrelated screens, allowing administrators to quickly navigate to the relevant integration category.
All Integrations Tab
The All Integrations tab should be the default landing view and provide a consolidated register of every external interface configured in Asset360. Each integration record should display information such as Integration Name, External System, System Type, Direction, Frequency, Last Synchronization Date/Time, Status and Actions. Direction should support values such as Inbound, Outbound and Bi-directional, while synchronization may be configured as real-time, scheduled or on-demand depending on the interface.
The list should support sorting, pagination and configurable columns. The developer should make the integration name clickable so that selecting it opens the detailed integration configuration. Status should be clearly identifiable as values such as Active, Inactive, Running, Success, Failed, Warning or Connection Error. Status colors may be used as functional indicators, but normal text throughout the application should remain black in accordance with the Asset360 design standard.
ERP Systems Tab
The ERP Systems tab should display integrations associated with enterprise applications such as ERP, procurement and finance platforms. The FSD specifically requires secure integration capability for ERP and procurement systems. This tab should therefore support interfaces involving asset masters, purchase orders, goods receipt information, capitalization information, financial references, suppliers, cost centers and other approved enterprise data according to the actual integration implemented for each customer.
The configuration should not assume that every ERP uses the same interface. An administrator should be able to define the integration mechanism and associated endpoint/configuration independently for each integration. The detail screen should provide sections for Connection, Authentication, Data Mapping, Synchronization, Transformation Rules, Error Handling and Logs. For example, an ERP integration could be configured to receive approved asset or purchase information into Asset360 while returning Asset ID or lifecycle transaction information to the ERP where the customer's interface requires it.
HR Systems Tab
The HR Systems tab should manage interfaces with employee and organizational-data sources. The FSD identifies HR as one of the external enterprise systems to which Asset360 should expose secure integration APIs. The developer should therefore allow HR integrations to support applicable information such as employee identity, employee number, department, business unit, designation, manager and employment status where provided by the connected system.
This integration becomes important for asset assignment and custodianship because Asset360 maintains accountability through custodianship and location history. Synchronization should therefore be able to create/update permitted employee master information while preserving references to historical employees associated with previous asset transactions. An employee becoming inactive in the HR system should not result in deletion of the employee's historical asset transactions.
IT Service Management Tab
The IT Service Management tab should handle connections to service desk and ITSM platforms. The FSD explicitly identifies service desk systems among the external systems Asset360 should support through secure APIs. Depending on the configured interface, this can support exchange of asset information, maintenance/service references and other approved records between Asset360 and the external service-management platform.
The developer should allow administrators to configure which entities and events are synchronized rather than hard-coding a single workflow. Each configured interface should define its data direction, endpoint, mapping and trigger. Failed transactions must remain available for investigation and retry rather than being silently discarded.
Identity & Security Tab
The Identity & Security tab should be used for integrations involving enterprise identity and directory services. The FSD identifies directory systems as a required integration category. This area should be separated logically from normal business-data integrations because authentication and user provisioning involve security-sensitive configuration.
Configuration should allow the relevant authentication/integration parameters to be maintained securely. Secrets, passwords, certificates, tokens and API credentials must never be displayed as readable values after they have been stored. The UI can display masked values and provide Replace/Update Credential actions. Access to this configuration should require specific administrative permissions and all changes must be recorded in the system audit trail.
IoT & Devices Tab
The IoT & Devices tab should manage integrations with device-based systems. The FSD explicitly identifies IoT/RTLS as supported external systems and also requires physical visibility through barcode/QR, optional UHF RFID, mobile scanning and map-based positioning. This tab can therefore contain integrations for RFID infrastructure, RTLS platforms and other approved tracking/device services.
Device integrations may generate significantly more transactions than conventional master-data integrations. The developer should therefore design these integrations to process events through backend services rather than requiring the browser screen to remain open. The screen should show operational information such as Last Event Received, Last Successful Processing Time, Device/Source, Records Processed and Error Count, where available from the configured integration.
Other Systems Tab
The Other Systems tab should provide an extensible area for integrations that do not fall into the predefined categories. This is important because the FSD requires Asset360 to expose secure APIs to other enterprise systems beyond the specifically named ERP, procurement, HR, directory, service desk, CMDB and IoT/RTLS categories.
Administrators should therefore be able to create an integration with an appropriate system category without requiring a developer to add a completely new UI screen. The integration framework should reuse the common connection, authentication, mapping, scheduling, logging and monitoring components.
Filters and Search Behaviour
The upper portion of the screen should provide a collapsible Filters section. Standard filters should include System Type, External System, Integration Status, Direction and Company, together with a global search box. Search should support partial matching against Integration Name, External System and relevant descriptions. Apply Filters should retrieve matching records from the backend, while Reset should clear the filters and restore the default list.
Advanced Filters can provide additional criteria such as synchronization method, frequency, last synchronization result, date range, created by and modified date. Filters should operate server-side where the number of integration records or logs can become large.
Add Integration
The + Add Integration button should open a guided configuration workflow. The recommended flow is Basic Information → Connection → Authentication → Data Mapping → Schedule/Trigger → Testing → Review & Activate. Basic Information should capture Integration Name, External System, System Type, Company/Scope, Description and Direction.
Connection configuration should capture only parameters appropriate to the chosen integration type. Authentication configuration should similarly change according to the selected authentication mechanism. Sensitive values must be encrypted or stored using an appropriate secrets-management mechanism rather than being stored as ordinary application configuration.
Data Mapping
The Data Mapping section is critical because Asset360 and an external system may use different fields, codes and structures. The screen should allow a developer/authorized integration administrator to map Source Field → Asset360 Field, together with transformation rules where required. Mandatory Asset360 fields should be identified, and the system should prevent activation where essential mappings are missing.
The configuration should support mappings for the applicable business entity rather than providing one universal mapping table. Asset Master, Employee, Location, Supplier and other integrated objects may each require different mappings.
Synchronization and Scheduling
Each integration should support an appropriate execution model such as Real-Time, Scheduled or On Demand. Scheduled integrations should allow administrators to configure permitted frequencies and execution windows. Real-time interfaces should be triggered through the configured API/event architecture rather than by repeatedly refreshing the UI.
The Run Sync button should manually initiate synchronization only where manual execution is permitted. Before execution, the system should identify the selected integration and, where appropriate, ask for confirmation. The job should then run asynchronously on the server. The user should be able to leave the screen without terminating the synchronization.
Test Connection
The Test Connection action should validate whether Asset360 can successfully communicate with the configured external endpoint using the saved connection and authentication configuration. The test should not perform a production business-data synchronization unless explicitly designed to do so.
The UI should return a meaningful result such as Connection Successful or a controlled failure message. Detailed technical information should be available to authorized technical administrators in logs without exposing credentials or other secrets.
Row-Level Actions
Every integration row should have an Actions (…) dropdown. Depending on permission and integration status, this should provide actions such as View Details, Edit Configuration, Test Connection, Run Sync, View Data Mapping, View Logs, View Sync History, Activate/Deactivate and Delete. Delete should normally be restricted where execution history exists; deactivation is preferable because it preserves historical records.
The backend must validate permission independently for every action. Hiding an action in the UI is not sufficient security.
Integration Logs and Sync History
Each integration should maintain detailed execution history. The Sync History screen or tab should show Execution ID, Integration Name, Start Time, End Time, Direction, Records Received, Records Processed, Successful Records, Failed Records, Execution Status and Triggered By.
Selecting an execution should open detailed transaction information. Failed records should identify the affected object/reference, failure stage and a meaningful error message. Where safe and appropriate, authorized administrators should be able to correct the underlying issue and use Retry Failed Records rather than rerunning the entire batch.
The FSD requires complete accountability through audit trails and history. Integration configuration changes and administrative execution actions should therefore be captured in the Asset360 audit trail as well.
Error Handling and Notifications
Integration failures should never disappear silently. The backend should classify errors into useful categories such as Connection Failure, Authentication Failure, Validation Failure, Mapping Error, External System Error and Internal Processing Error. Errors should be written to structured logs with correlation/execution IDs so support teams can trace a transaction from initiation through completion.
Where notification functionality is configured, significant failures can trigger notifications to designated administrators. Repeated errors should not create uncontrolled duplicate alerts; notification and retry policies should be configurable.
Overall Developer Navigation Flow
From the user's perspective, the normal navigation should be:
Administration → Integrations → Select Integration Category → Search/Filter → Select Integration → View Configuration/Status → Test or Run → Monitor Execution → Review Logs/Errors.
For creation, the sequence should be:
Add Integration → Define System → Configure Connection → Configure Authentication → Map Data → Configure Trigger/Schedule → Test Connection → Validate Configuration → Activate → Monitor.
Architecturally, the developer should treat the Integrations screen as the management UI over a reusable integration framework, not build separate integration logic directly into every screen. The FSD calls for secure APIs supporting ERP, procurement, HR, directory, service desk, CMDB, IoT/RTLS and other enterprise systems. A centralized framework for connection configuration, mappings, scheduling, execution, retries, logging and security will therefore make Asset360 substantially easier to deploy across different customers and enterprise environments.
Asset360 – Audit Logs Screen Functional Description
The Audit Logs screen should be developed as a centralized, read-only administrative screen that records and displays all significant activities performed by users, system processes, integrations, mobile applications and background jobs within Asset360. Its primary purpose is to provide complete traceability of who performed an action, what was changed, when it happened, where it originated, which business record was affected, and whether the transaction succeeded or failed. The audit log should cover all major modules including Assets, Inventory, Maintenance, Receiving & Tagging, Tracking & Location, Verification & Audit, Reports & Analytics, Administration, Master Data, Integrations, User Management, Roles & Permissions and System Configuration. Audit records must be generated automatically by backend services and must not depend on the user manually creating a log entry.
Main Audit Logs View
When the administrator opens Administration → Audit Logs, the system should display the Audit Logs list as the default view. The grid should contain Date & Time, User, Module, Action, Record ID/Reference, Status and an option to open the detailed record. Typical actions should include Login, Logout, View where required, Create, Update, Delete, Activate, Deactivate, Approve, Reject, Assign, Transfer, Issue, Return, Sync, Import, Export, Upload, Download and Configuration Change. System-generated transactions should identify the user as System, Integration Service, Scheduler or the applicable service account instead of leaving the User field blank.
Each record should receive a unique Audit Log ID generated by the backend. The date and time should be captured from the server and stored consistently, preferably in UTC with conversion to the configured Asset360/user timezone for display. The audit record should be written even when the underlying transaction fails where the event is security- or operationally relevant. For example, a failed login, failed integration synchronization or rejected transaction should still be traceable.
Filters and Search
The top section should contain comprehensive filters so administrators can investigate large volumes of records. The primary filters should include Date Range, User, Module, Action Type, Status, Company, Location, Record ID and Keyword Search. Date Range should allow predefined periods such as Today, Yesterday, Last 7 Days, Last 30 Days and Custom Range. User should be searchable because large implementations may contain hundreds or thousands of users.
The Module dropdown should contain the Asset360 modules available to the logged-in administrator. The Action Type dropdown should allow filtering for actions such as Create, Update, Delete, Approve, Reject, Login, Logout, Import, Export and Sync. Status should support Success, Failed and other applicable outcomes. Apply Filters should perform server-side retrieval, while Reset clears the selected criteria. Advanced Filters can additionally include IP Address, User Type, Device Type, Source Application, Integration Name and transaction/correlation ID.
Audit Log Details
Selecting an audit record should open a Log Details panel or drawer without losing the user's current filters and position in the list. The detail view should display Audit Log ID, Date & Time, User Name, User ID, User Type, Module, Submodule, Action, Record Type, Record ID, Status, Company, Business Unit, Location, IP Address, Device/Browser, Source Application and Description, where those values apply.
The description should be human-readable. Instead of displaying only technical information such as UPDATE RECORD 1256, the application should show a meaningful description such as “Asset AST-0001256 location changed from Old Warehouse to Main Store.” Technical information can be retained separately for troubleshooting.
Old Value and New Value
For update transactions, the system should maintain Old Value and New Value information so an administrator can determine exactly what changed. The developer should ideally capture changed fields rather than duplicating the complete database object unnecessarily. For example, if an asset's location changes, the audit detail could show Location: Old Warehouse → Main Store. If multiple attributes are changed, each affected field should be displayed separately.
This capability is particularly important for sensitive administrative changes. Changes to roles, permissions, users, workflow rules, system configuration, asset information, cost centers, organizational structure, maintenance settings and integration configuration should always retain meaningful before-and-after values. Passwords, API keys, tokens and other secrets must never be stored in readable form in the audit record.
User Activity
The audit screen should support a User Activity perspective, either through a tab or through filtering from the main screen. This view should allow an administrator to select a user and review that user's activity chronologically. It should show login/logout events and significant business and administrative transactions performed by the user.
This is useful for investigating questions such as who changed an asset, who approved a disposal, who modified a role, who exported information, or which administrator changed a system setting. Clicking an activity should open the same Audit Log Details component rather than creating a separate implementation.
Asset & Transaction History
The screen should also support viewing logs by Record ID. For example, searching for an Asset ID should return all relevant logged activities associated with that asset. The same principle should apply to Work Order IDs, Audit IDs, Stock Transaction IDs, Transfer IDs, User IDs and other supported business references.
Where appropriate, operational screens should also be able to call this audit service contextually. An Asset Details screen, for example, could provide View History, which opens or retrieves audit records already filtered for that Asset ID. This avoids developing separate history mechanisms in every module.
System Activity
A System Activity view should display automated actions not directly initiated by a normal user. Examples include scheduled preventive-maintenance generation, automatic notifications, scheduled reports, data synchronization, background processing and automated status updates. The originating service should be clearly identified.
This distinction is important because administrators need to know whether a change was performed manually or automatically. The audit model should therefore include a Source Type such as Web Application, Mobile Application, API, Integration, Scheduler, Background Service or System Process.
Security & Access Logs
Security-sensitive events should be available through a Security Activity view or filter. This should include successful and failed login attempts, logout, password-related administrative actions where applicable, role assignment, permission changes, account activation/deactivation and other security-relevant administrative events.
Security logs should contain sufficient context for investigation but must not capture sensitive authentication information. Passwords, OTP values, access tokens, refresh tokens, API secrets and session credentials must never be written into the audit database.
Integration Audit Logs
Integration-related audit records should provide visibility into data exchanges with external systems. The system should record the Integration Name, External System, Direction, Execution/Correlation ID, Start Time, End Time, Records Processed, Success Count, Failure Count and Result, where relevant.
Selecting an integration event should allow the administrator to navigate to its integration execution history when permitted. This creates a connection between Administration → Audit Logs and Administration → Integrations while avoiding duplicate log storage.
Failed Activities and Errors
Failed transactions should be retained and identifiable through Status = Failed. The details should contain a meaningful error summary and a technical reference or correlation ID where appropriate. Developers should avoid exposing raw stack traces or sensitive server information to ordinary administrators. Detailed technical diagnostics can be restricted to authorized technical/support roles.
For example, if an integration fails because an external endpoint is unavailable, the administrator could see “Synchronization failed – external service unavailable”, while the technical log maintains the detailed diagnostic information.
Related Logs
The Related Logs section should identify other audit events connected to the selected transaction through a common Record ID, Parent Transaction ID or Correlation ID. For example, an asset transfer may produce Request Created → Submitted → Approved → Asset Location Updated → Custodian Updated → Notification Sent. These related events should be available as a chronological sequence.
This makes it possible to reconstruct an end-to-end business transaction rather than forcing the administrator to manually search for every individual event.
Export Logs
The Export Logs action should allow authorized users to export the currently filtered audit records to Excel/CSV and, where required, PDF. Export must respect both the active filters and the logged-in user's security scope. The system should not allow a user with access to one company or business unit to export audit records belonging to another organization.
Large exports should be processed through a background job rather than loading the entire audit dataset into the browser. The export itself should also generate an audit event recording who exported the information, when, what filters were used and approximately how many records were exported.
Refresh and Pagination
The screen should provide Refresh to retrieve the latest records without resetting the selected filters. Pagination should be server-side and support configurable page sizes such as 25, 50 and 100 records per page. Sorting should be available for Date & Time, User, Module, Action, Record ID and Status. The default sort should normally be Date & Time descending, showing the latest activities first.
The developer should not load the complete audit table into the browser and then filter it locally. Audit data can become very large over the life of an enterprise system, so filtering, sorting and pagination must be performed by the backend/database.
Audit Log Security and Immutability
Audit records should be treated as immutable records. The Audit Logs screen must therefore have no Edit or Delete button for normal administrators. Users may search, filter, view and—where authorized—export logs, but they should not be able to alter their content. Audit-retention or archival policies should be handled by controlled system administration/database policies rather than manual deletion from this screen.
Role-based permissions should determine who can access audit information. A System Administrator may have enterprise-wide visibility, while another administrative user may only be permitted to view records for assigned companies, business units or locations.
Backend Audit Architecture
The audit functionality should be implemented as a common backend service/middleware capability, not separately coded inside every UI screen. Business services should send structured audit events containing the actor, action, module, entity, record ID, outcome and applicable before/after information. This will provide consistent logging across web, mobile, APIs, integrations and scheduled processes.
The recommended logical audit structure should include AuditLogID, Timestamp, UserID, UserName, SourceType, Module, Submodule, ActionType, EntityType, RecordID, Parent/CorrelationID, CompanyID, LocationID, OldValue, NewValue, Description, IPAddress, DeviceInformation and Status. Large before/after payloads should be handled carefully so that the audit mechanism does not significantly degrade transaction performance.
Overall Screen Maneuvering
The intended developer flow should be Administration → Audit Logs → Select Date/User/Module/Action Filters → Apply Filters → Review Results → Select Record → View Log Details → Review Old/New Values → Review Additional Information → Open Related Logs. The administrator should be able to close the details panel and return to exactly the same filtered list, page and scroll position.
The Audit Logs screen should therefore act as the central traceability and accountability console for Asset360, covering both business transactions and administrative/security activities. It should enable an authorized administrator or auditor to reconstruct the history of an asset, user, configuration or transaction without allowing the historical evidence itself to be modified.
Asset360 – Email Notifications Screen Functional Description
The Email Notifications screen should be developed as the centralized administration area for configuring and controlling all automated email communications generated by Asset360. The screen should allow authorized administrators to create reusable email templates, associate them with application events, determine recipients, configure notification rules, manage mail-server settings, test notifications, and monitor delivery results. The developer should design this as a configuration-driven notification framework so that individual Asset, Maintenance, Inventory, Audit, Contract, Workflow and Administration screens do not contain hard-coded email logic.
Email Templates Tab
The Email Templates tab should be the default landing tab and display all notification templates configured in Asset360. The table should contain Template Name, Module, Event Type, Status, Last Modified and Actions. Examples can include Work Order Assignment, Work Order Completion, Preventive Maintenance Due, PM Overdue, Asset Transfer Approval, Asset Transfer Completed, Asset Custodian Change, Low Stock Alert, Stock Received, Asset Warranty Expiry, Contract/AMC Expiry and Asset Verification Assignment. Each template must be associated with a specific application event so the notification engine knows when it should be invoked.
The screen should provide Search, Module, Event Type and Status filters. Module values should dynamically represent applicable Asset360 modules such as Assets, Maintenance, Inventory, Verification & Audit and Administration. Event Type should be dependent on the selected module. For example, selecting Maintenance should make relevant events such as Work Order Created, Work Order Assigned, Work Order Completed, Preventive Maintenance Due and Maintenance Overdue available. Status should allow Active and Inactive templates. The Apply Filters action should retrieve matching records, while Reset should return the screen to its default state.
Create Template
The Create Template button should open a new template configuration form. Mandatory fields should include Template Name, Module, Event Type and Subject. Additional fields should include Description and Status. Template Name should be unique or validated according to the combination of module/event rules established by the application. The Module and Event Type relationship is important because it determines which business information and placeholders are available to the template.
When an Event Type is selected, the application should dynamically load the placeholders supported by that event. For example, a Work Order event may provide placeholders such as {{WO_No}}, {{Asset_Name}}, {{Priority}}, {{Due_Date}}, {{Location}} and {{Assigned_To}}. An Asset Transfer event would have a different set of fields. The developer should not maintain a single uncontrolled list of placeholders for every notification.
Template Details
Selecting a template from the list should display its Template Details on the right side or open the template in a detailed view. The upper section should show Template Name, Module, Event Type, Status, Subject and Description. The screen should clearly identify whether the template is Active or Inactive.
An authorized administrator should be able to edit the template and save changes. Changes should be validated before saving, and modifications should be recorded in the audit trail. Existing notifications already sent using an older version of a template should not be retrospectively altered when the template is subsequently changed.
Email Content Tab
The Email Content tab should contain the actual message design. It should support both an HTML Editor and a Text Editor. The HTML editor should provide standard formatting functions such as font formatting, bold, italic, underline, paragraphs, alignment, lists, hyperlinks and permitted images or branding elements. The developer should sanitize HTML content before storage and delivery to prevent unsafe HTML or executable content from being introduced through administrative templates.
The Text Editor should provide a plain-text version for environments where HTML email cannot be displayed. The administrator should be able to switch between HTML and text views without losing unsaved content. A standard Asset360 header/footer can optionally be managed as part of the notification framework rather than manually duplicated in every template.
Dynamic Placeholders
The Available Placeholders panel should dynamically display the variables that can be inserted into the selected template. Typical placeholders can include User Name, Work Order Number, Asset Number, Asset Name, Priority, Due Date, Location, Assigned To, Created By, Company and a transaction link. The exact list should depend upon the Module and Event Type.
The administrator should be able to search for a placeholder and either click it to insert it at the current cursor position or use a Copy function. When an email is generated, the notification service must replace these placeholders with actual transaction data. If a mandatory placeholder cannot be resolved, the system should log the issue rather than sending malformed template syntax to the recipient.
Recipients Tab
The Recipients tab should define who receives the notification. Recipients should preferably be rule-based instead of requiring administrators to enter fixed email addresses for every transaction. The screen should support recipient types such as Transaction User, Assigned User, Asset Custodian, Requester, Approver, Technician, Department Manager, Maintenance Manager, Asset Manager, Inventory Controller, Role, User, Recipient Group and specific Email Address, depending on the relevant event.
The screen should separately support To, CC and BCC recipients. For example, a Work Order Assignment notification may send To = Assigned Technician and CC = Maintenance Manager. The notification engine should resolve the actual email addresses when the event occurs. Duplicate addresses should automatically be removed before sending.
Notification Rules Tab
The main Notification Rules tab should define when notifications are generated. A rule should connect an application event to a template and its triggering condition. Each rule should contain Rule Name, Module, Event, Template, Trigger Type, Conditions, Frequency and Status.
The system should support event-driven rules such as when a Work Order is assigned, as well as time-based rules such as 30 days before Contract Expiry, 7 days before Warranty Expiry, or 1 day before Preventive Maintenance Due Date. Where applicable, administrators should be able to configure multiple reminders—for example, 30 days, 15 days and 7 days before AMC expiry—without creating custom code.
Rules should also support conditions where required. A notification could, for example, be generated only when Work Order Priority = Critical or when Spare Part Stock Level <= Reorder Level. The backend notification engine should evaluate these rules rather than the browser.
Recipient Groups Tab
The Recipient Groups tab should allow administrators to create reusable distribution groups such as Asset Managers, Maintenance Supervisors, Inventory Controllers, Audit Team or System Administrators. A recipient group should have Group Name, Description, Members, Applicable Company/Business Unit/Location and Status.
Members may be individual users, roles or approved email recipients depending on system configuration. If a group is used by several notification rules, changing group membership should automatically affect future notifications without requiring each template to be edited.
Advanced Settings Tab
Within an individual template, Advanced Settings should control additional delivery behaviour. This can include notification priority, reply-to configuration, attachment rules, duplicate-notification prevention, retry behaviour and other permitted parameters.
The developer should also provide a mechanism for controlling reminder frequency so that a scheduled process does not repeatedly send the same notification unintentionally. Each generated notification should have a transaction/reference key that allows the engine to determine whether the same event has already been processed.
Email Settings Tab
The main Email Settings tab should contain the technical configuration required for Asset360 to send email. Depending upon deployment architecture, this can support SMTP or another approved enterprise email service. Configuration fields may include Sender Name, Sender Email, Mail Server, Port, Security/Encryption Mode, Authentication Type and connection parameters.
Passwords, tokens and application secrets must be encrypted or maintained through an appropriate secrets-management mechanism and should never be displayed in readable form after saving. The screen should provide Test Connection and preferably Send Test Email functions. Only users with specific System Administration permission should be allowed to modify mail configuration.
Send Test Email Action
The Send Test Email button should allow an administrator to verify a template before activation. The user should enter or select a permitted test recipient, and the system should generate the email using sample/test values for placeholders. The test email should be clearly distinguishable from a production transaction notification.
The system should return a clear result such as Test Email Sent Successfully or a controlled error message. Technical delivery errors should be available through logs while avoiding exposure of credentials or sensitive server configuration.
Preview Action
The Preview action should render the email exactly as the recipient is expected to see it, including branding, formatting, subject and representative placeholder values. Preview must not send an email. It should allow administrators to switch between desktop-style HTML preview and plain-text representation where useful.
The preview is particularly important before activating new templates or after significant changes to an existing template.
Clone Action
The Clone action should create a copy of an existing template so administrators can quickly create a similar notification. The copied template should receive a new internal ID and should initially be saved as Draft or Inactive to prevent accidental notification delivery.
The administrator can then change the Template Name, Event Type, Subject, content, recipients and rules before activation.
Activate and Deactivate Actions
The Activate/Deactivate action should control whether a template is available for notification processing. Deactivating a template should not delete it or remove historical delivery information. If an active notification rule references a template that is being deactivated, the system should warn the administrator and identify the affected rule before confirmation.
Deleting templates already referenced historically should generally be avoided. Deactivation provides better traceability.
Save Changes and Cancel
The Save Changes action should validate all mandatory configuration before committing the template. The system should validate required fields, valid event/template relationships, subject content, recipient configuration and placeholder syntax. Once successfully saved, the Last Modified Date and Modified By information should update and an audit event should be generated.
Cancel should discard unsaved changes after confirmation if the user has modified information. It should return the user to the previous state without overwriting the stored template.
Audit Trail Tab
Each template should contain an Audit Trail tab showing its configuration history. The audit trail should identify Date & Time, User, Action, Field Changed, Previous Value and New Value where applicable. Events such as Template Created, Content Changed, Recipient Rule Changed, Activated, Deactivated and Test Email Sent should be traceable.
The audit information should be read-only and retrieved from the common Asset360 Audit Log service rather than maintaining a separate editable history specifically for email templates.
Delivery Logs Tab
The Delivery Logs tab should provide operational visibility of emails generated by Asset360. It should display information such as Date & Time, Notification/Message ID, Template, Module, Event, Business Reference, Recipient, Subject, Delivery Status and Retry Count. Status values can include Queued, Processing, Sent, Delivered where supported, Failed and Retry Pending.
Selecting a delivery record should show additional information such as transaction reference, recipient addresses, generation time, send time and controlled error information. Failed notifications should display a meaningful failure reason and, where appropriate, an authorized Retry action.
Actions Dropdown
The Actions (…) menu against each template should provide contextual options such as View, Edit, Preview, Send Test Email, Clone, View Notification Rules, View Delivery History, Activate/Deactivate and View Audit Trail. Only actions applicable to the current template state and permitted by the user's role should appear.
Permission checks must also be performed by the backend. Hiding an action button in the UI must not be considered sufficient authorization.
Notification Processing Architecture
From the development perspective, email delivery should run through a central Notification Service rather than sending emails directly from individual business screens. For example, when a Work Order is assigned, the Maintenance service should publish or register a WorkOrderAssigned event. The Notification Service should identify the applicable active rule, retrieve the configured template, resolve recipients and placeholders, create the notification, queue it for delivery and record the result.
The processing sequence should therefore be:
Business Event → Notification Rule → Template → Resolve Recipients → Resolve Placeholders → Generate Email → Queue → Send → Record Delivery Status → Retry/Exception Handling.
This architecture will allow Asset360 to add new notification events and templates through configuration rather than requiring email-sending code to be repeatedly developed inside every module.
Overall Screen Navigation
The intended user maneuvering should be Administration → Email Notifications → Email Templates / Notification Rules / Recipient Groups / Email Settings / Delivery Logs. Within Email Templates, the administrator should Search/Filter → Select Template → Review Template Details → Email Content → Recipients → Advanced Settings → Preview/Test → Save/Activate.
The overall Email Notifications module should therefore function as a complete notification-management console, not just an email-template editor. It should control what notification is sent, which business event triggers it, who receives it, what dynamic transaction information appears in it, when reminders are generated, whether delivery succeeds, and provide a complete history of both configuration changes and notification delivery.
Asset360 – Backup & Scheduler Screen Functional Description
The Backup & Scheduler screen should be developed as the centralized administration area for managing Asset360 backup operations and automated background jobs. The module should allow authorized administrators to review backup health, configure backup schedules, initiate approved manual backups, monitor scheduled jobs, verify backup integrity, review execution history, and control retention. The screen should be divided into the main tabs Backup Management and Scheduler, with supporting detail sections for Backup Details, Schedule Information, Backup Logs, Job History and Recent Activities. All operations must be permission-controlled and fully recorded in the Asset360 Audit Logs.
Backup Management Tab
The Backup Management tab should be the default landing screen and provide an immediate overview of backup health. At the top, summary cards should display Last Successful Backup, Total Backups for the selected period, Successful/Failed Backup Count, Storage Used, Storage Capacity and Next Scheduled Backup. These values should come from the actual backup service or infrastructure integration rather than being manually entered. The Last Successful Backup card should display the date/time and backup type, while Next Scheduled Backup should show when the next automated job is expected to execute.
Below the summary, the Backups List should display individual backup records with columns such as Backup Name, Backup Type, Size, Start Time, End Time/Duration, Status and Actions. Backup types should support the deployment's approved methods, such as Full and Incremental where technically supported. Status should include values such as Queued, In Progress, Success, Failed, Cancelled, Verification Pending and Verification Failed. The default sorting should show the latest backup first.
Create Backup Now
The Create Backup Now action should allow an authorized administrator to manually initiate a backup outside the normal schedule. Selecting the button should open a confirmation/configuration window showing the available Backup Type, scope where applicable, description/notes and estimated storage requirements if available. The administrator should confirm the operation before it starts.
The backup must execute as a server-side/background process. Closing the browser or navigating to another Asset360 module must not terminate it. Once initiated, the system should create a job record, show the backup as In Progress and update its status when processing completes. Manual backup initiation must also create an Audit Log entry identifying who initiated it and when.
Backup Details
Selecting a backup record should open the Backup Details section. This should display Backup Name/ID, Backup Type, Status, Start Time, End Time, Duration, Size, Storage Location Reference, Checksum/Integrity Result, Created By/Triggered By and Notes. For scheduled backups, the screen should also identify the schedule responsible for creating it.
The administrator should not be permitted to edit technical backup metadata after creation. Backup Details represents a historical system record and should therefore remain read-only.
Backup Actions
Available backup actions should include Download, Restore, Verify and Delete only where supported by the actual deployment architecture and the logged-in user's permission. These operations must not simply appear because they were included in the UI mock-up; the developer should expose them only when the corresponding infrastructure capability is configured.
Verify should perform an integrity check and update the verification status. Download should securely retrieve the approved backup artifact when permitted. Delete should be restricted to highly privileged administrators and should enforce retention rules before allowing removal. Every sensitive action must require confirmation and generate an audit entry.
Restore Functionality
The Restore action is a high-risk administrative operation and should therefore use a controlled workflow rather than immediately restoring data when the button is clicked. The system should display the selected Backup ID, Date, Type, Verification Status and applicable restore scope and require explicit confirmation.
Where the infrastructure requires application downtime, database maintenance mode or external infrastructure intervention, Asset360 should display this requirement rather than pretending restoration can always occur directly through the application. Restore execution should be restricted to specifically authorized roles. The system should maintain Requested By, Approved By where required, Restore Start Time, End Time, Backup Used and Result.
Schedule Information
The Schedule Information section should display which schedule generated the selected backup. It should contain Schedule Name, Backup Type, Frequency, Execution Time, Retention Period, Storage Target, Last Run, Next Run and Status.
From this section, an authorized administrator should be able to navigate directly to the corresponding Scheduler configuration. This creates a logical relationship between historical backup records and the configuration responsible for producing them.
Scheduler Tab
The Scheduler tab should manage automated jobs executed by Asset360. It should not be limited to backups. The scheduler architecture should support system jobs such as Backup Jobs, Preventive Maintenance Generation, Contract/AMC Expiry Checks, Warranty Expiry Checks, Notification Processing, Scheduled Reports, Integration Synchronization, Data Archival and other FSD-approved background operations.
The Scheduler list should display Job Name, Job Type, Module, Frequency, Last Run, Next Run, Last Result, Status and Actions. Status should distinguish between Active, Paused, Running, Completed and Failed where appropriate.
Create Schedule
The Create Schedule action should open a schedule configuration form. The administrator should define Schedule Name, Job Type, Module/Process, Frequency, Start Date, Execution Time, Time Zone and Status. Depending on the job type, additional configuration should appear dynamically.
Frequency should support applicable options such as Daily, Weekly, Monthly or Custom, while the developer may implement cron-style scheduling internally if appropriate. Administrators should interact with understandable scheduling controls rather than having to enter cron expressions manually.
Backup Schedule Configuration
When Job Type = Backup, the scheduler should additionally allow the administrator to configure the supported Backup Type, Execution Frequency, Execution Time, Retention Policy and Storage Target. The scheduler should calculate and display the Next Run based on this configuration.
The system must prevent conflicting schedules or unsupported backup combinations. If an administrator attempts to schedule another backup during an existing backup window, the application should either prevent the configuration or apply a defined queueing rule.
Scheduled Job Actions
The Actions (…) menu for a scheduled job should provide contextual options such as View, Edit Schedule, Run Now, Pause, Resume, View Execution History and Deactivate. Actions should vary depending on job status. For example, an Active schedule should show Pause, while a Paused schedule should show Resume.
Run Now should trigger the selected scheduled process immediately without changing its future schedule. This action should require confirmation for resource-intensive or sensitive jobs.
Pause and Resume
The Pause action should temporarily stop future executions without deleting the schedule. Existing historical runs must remain visible. The Next Run should display an appropriate paused indication rather than a misleading date.
Resume should reactivate the schedule and recalculate the next execution time according to its configuration. Both actions must be audited.
Job Execution History
Each scheduler entry should provide a Job History/Execution History view containing Execution ID, Job Name, Scheduled Time, Actual Start Time, End Time, Duration, Trigger Type, Triggered By, Result and Status.
Trigger Type should differentiate between Scheduled, Manual and System-triggered execution. This is useful when administrators use Run Now because the resulting execution should remain distinguishable from the normal automated schedule.
Backup Logs
The Backup Logs section should provide technical and operational history for the selected backup. The log should identify significant stages such as Backup Queued, Backup Started, Database Backup Completed, File/Document Backup Completed where applicable, Integrity Verification Completed, Storage Transfer Completed and Backup Completed/Failed.
The normal administrator should see meaningful messages rather than raw system exceptions. Technical diagnostic information may be accessible to authorized technical roles through an expanded detail view. Secrets, credentials, connection strings and sensitive infrastructure information must never be exposed in logs.
Failed Backup and Retry Handling
If a backup fails, the system should display the failure clearly and retain the failed execution record. The administrator should be able to review the failure reason and, where technically supported, initiate Retry Backup.
A retry should create a new execution record referencing the original failed backup rather than overwriting the failure history. This preserves an accurate operational audit trail.
Recent Activities
The Recent Activities section should provide a chronological summary of important backup and scheduler events. Examples include Backup Started, Backup Completed, Backup Failed, Backup Verified, Restore Requested, Restore Completed, Schedule Created, Schedule Modified, Job Paused, Job Resumed and Job Executed Manually.
Each record should display Date & Time, Activity, Status and Message, with an option to navigate to the related backup, job or Audit Log. The screen should show only a manageable number of recent records and provide View All Logs for complete history.
Search, Filters and Pagination
Both Backup Management and Scheduler should provide search and filters. Backup filters should support Date Range, Backup Type, Status, Trigger Type and Created/Triggered By. Scheduler filters should support Job Type, Module, Frequency and Status.
All filtering, sorting and pagination should be performed server-side. Backup and scheduler history can grow considerably, so the developer should not load the complete dataset into the browser.
Retention Management
Backup retention should be configurable according to the organization's infrastructure and governance requirements. The system should support policies such as retaining backups for a specified number of days or retaining a defined number of generations, subject to the capabilities of the configured backup platform.
Expired backups should be handled through the configured retention process rather than manually deleted by ordinary administrators. Retention-policy changes should be audited because they can materially affect recovery capability.
Storage Monitoring
The Storage Used indicator should display the amount of configured backup storage consumed compared with available capacity where this information is available from the infrastructure. The screen should provide warnings when configured thresholds are reached.
For example, administrators could receive warning and critical notifications based on configurable storage thresholds. Storage alerts should integrate with the Asset360 notification framework rather than implementing a separate email mechanism specifically for backup.
Security and Permissions
Backup and Scheduler functionality should have granular permissions such as View Backup, Create Backup, Download Backup, Verify Backup, Restore Backup, Delete Backup, Manage Schedule, Run Job, Pause/Resume Job and View Logs. Restore and Delete should be treated as especially sensitive permissions.
The backend must enforce these permissions independently of the UI. Removing a button from the screen is not sufficient protection.
Audit Trail
Every configuration change and administrative action must be sent to the common Asset360 Audit Logs service. This should include schedule creation/modification, manual backup initiation, verification, download where required by policy, restore requests, restore execution, deletion, pause/resume and manual job execution.
The audit record should capture User, Date & Time, Action, Backup/Job Reference, Previous Value, New Value and Result where applicable.
Developer Architecture
The developer should separate the Backup Service from the Scheduler Service. The Backup Service should manage backup requests, status, metadata, verification and recovery interaction with the configured infrastructure. The Scheduler Service should manage timed/background execution for backup and other Asset360 processes. This avoids coupling all scheduled operations directly to the backup implementation.
The recommended processing pattern should be Scheduler → Job Queue → Background Worker/Service → Target Business Service → Execution Result → Job History → Notification/Audit Log. Jobs must run independently of browser sessions and should use locking or equivalent concurrency controls to prevent the same scheduled job from accidentally executing multiple times simultaneously.
Overall Screen Maneuvering
The normal backup flow should be Administration → Backup & Scheduler → Backup Management → Review Backup Health → Search/Select Backup → View Details → Verify/Download/Restore where authorized → Review Logs. The scheduler flow should be Administration → Backup & Scheduler → Scheduler → Search/Select Job → View Schedule → Edit/Run/Pause/Resume → Review Execution History.
The result should be a central operational console for Asset360 background processing and recoverability, while the actual database, application-file and infrastructure backup mechanisms remain appropriately separated from the UI. This distinction is important: Asset360 should manage and monitor supported backup operations, but the screen should not imply capabilities such as full infrastructure recovery unless those capabilities are actually provided by the deployed hosting and backup architecture.
Asset360 Mobile Application – Developer Functional Description
The Asset360 Mobile Application should be developed as the field-operational component of the Asset360 platform. It should provide a simplified, task-oriented interface for users who receive, tag, locate, transfer, audit, maintain, and verify physical assets. The mobile application should not duplicate the complete Web Administration functionality; configuration, master data, permissions, workflows, reporting configuration, integrations, and system settings should primarily remain in the Asset360 Web Application.
The mobile UI should follow the approved Asset360 design standard: white background, Arial font, all normal text in black, purple as the primary accent, purple icons, purple primary action buttons, white secondary buttons with purple borders, light-purple selected states, and light-grey card/table borders. The same visual convention should be maintained across Android and iOS implementations.
Login and Authentication
The Login screen should be the entry point into the application. It should support Username and Password authentication and, where configured for a customer, enterprise authentication/SSO. Password visibility, Forgot Password, language selection, and Remember Me can be provided according to the deployed authentication model.
After authentication, the server must return the user's identity, roles, permissions, organizational scope, accessible locations, and mobile configuration. The application should then dynamically determine which modules and actions the user can access. For example, an Auditor may see Asset Search and Audit but should not automatically receive Maintenance or Stock Management functionality.
Authentication and authorization must be enforced by the Asset360 backend APIs rather than only by hiding mobile buttons.
Mobile Landing Page
After successful authentication, the user should reach the Mobile Module Landing Page. This should act as the operational dashboard and provide immediate access to the functions most frequently used in the field.
The header should contain the Asset360 logo, user information, notification icon and menu. Below it, provide a universal Asset Search field supporting Asset ID, Tag Number and Serial Number, together with a scan icon for Barcode/QR scanning. Where RFID hardware is supported, RFID lookup should also be available through the appropriate scanning workflow.
The primary module cards should include the following based on user permission:
Assets | Receive | Transfer | Maintenance | Audit | Stock Take | Requests | Tasks | Sync | Settings | More
The landing page should also contain a My Tasks summary displaying Pending, In Progress and Completed activities. These values should be retrieved from the server for online users and from the latest synchronized assignment dataset when offline.
Assets Module
The Assets module should provide mobile access to the organization's permitted asset records. Users should be able to search by Asset ID, Asset Name, Serial Number, Barcode/QR Tag and RFID Tag where applicable. Filters can include Company, Department, Location, Asset Group, Class, Category, Subcategory, Status, Condition, Criticality and Custodian.
Selecting an asset should open the Asset 360° Mobile View, which provides the consolidated asset record discussed earlier. It should contain Asset Image, Asset ID/Tag, Serial Number, Manufacturer, Brand, Model, Group/Class/Category/Subcategory, Status, Condition, Criticality, Custodian, organizational information, current location, floor-map position, warranty, maintenance status, financial information where permitted, IT discovery information, documents and complete movement/history timeline.
This screen should also become the common starting point for asset-specific actions. Instead of developing separate copies of the asset information in every module, Transfer, Maintenance, Audit and other modules should navigate back to the same Asset 360° component.
Receive Asset Module
The Receive module should support the two primary workflows:
Receive Asset – With PO and Receive Asset – Without PO.
For With PO, the workflow should follow:
Select/Scan PO → View PO Lines → Select Line → Review Supplier & Expected Quantity → Enter Received Quantity → Partial/Full Receipt → Scan Manufacturer Serial → Scan Product/Model Barcode → Record Condition → Capture Photos → Select Staging Location → Create Serialized Asset → Associate Asset360 Tag → Print Barcode/QR/RFID Label → Preview → Submit Receipt.
For serialized items, each physical item must result in an individual asset record. If a PO line contains ten laptops and five are received, the system should create five individual serialized assets while maintaining the remaining quantity against the PO line.
The Without PO workflow should collect the necessary asset information manually or from approved master data and should be governed by the relevant permissions and approval workflow.
Scan Module
Scanning should be treated as a common mobile service, not independently developed inside every module. The application should provide a common scanning component supporting the device camera for Barcode/QR and supported integrated or Bluetooth RFID hardware where applicable.
The scan service should be callable from Asset Search, Receiving, Transfer, Audit, Stock Take, Maintenance and Tag Association.
For example:
Scan → Identify Tag Type → Resolve Asset/PO/Item → Validate → Return Result to Calling Module.
This prevents different scanning behaviour from being developed independently for every transaction.
Transfer Asset Module
The Transfer Asset module should support movement of assets between locations, departments, cost centers, custodians or other applicable organizational assignments.
The field user should Scan/Search Asset → View Current Assignment → Select Transfer Type → Select Destination Location/Department/Custodian → Capture Reason/Remarks → Submit. If approval is required, the transaction should enter the configured Asset360 workflow rather than immediately updating the master asset record.
For multiple assets, the application should support controlled batch transfer where the FSD and permissions allow it.
Successful transfers should update the Asset 360° history and become visible immediately in the web application for online transactions.
Maintenance Module
The Maintenance module should give technicians access to assigned maintenance work. The landing screen should show categories such as My Work Orders, Preventive Maintenance, Open Jobs, Overdue Jobs and Completed Jobs as applicable.
A technician should be able to open a Work Order and view Asset, Work Order Number, Problem/Service Description, Priority, Status, Location, SLA/Due Date, Service Category and maintenance instructions.
The mobile workflow can support:
Accept Job → Start Work → Inspect Asset → Record Diagnosis → Record Action Taken → Add Spare Parts → Capture Photos/Documents → Enter Labor/Time → Update Condition → Complete Work → Submit.
Maintenance completion should update the central Work Order and Asset maintenance history.
Audit Module
The Asset Audit module should support physical asset verification. Audit assignments should normally originate from the Asset360 Web Application and be downloaded to the assigned mobile user/team.
The workflow should support:
Select Audit → Download/Load Assigned Assets → Scan Barcode/QR/RFID → Match Asset → Confirm Location → Confirm Custodian → Confirm Condition → Capture Exception → Add Photo/Remarks → Mark Verified.
The application should differentiate between Found, Missing, Unexpected, Wrong Location, Wrong Custodian, Damaged and other configured exception conditions.
The user should be able to view progress such as:
Assigned 1,000 | Verified 820 | Exceptions 35 | Pending 145
and submit the completed audit back to the web application.
Stock Take Module
The Stock Take module should primarily support Inventory and Spare Parts verification. A stock-count assignment should be created on the web application and made available to authorized mobile users.
The workflow should support Select Stock Take → Select Store/Warehouse → Scan Spare Part → Display System Quantity where permitted → Enter/Scan Physical Quantity → Record Variance → Add Reason/Remarks → Submit.
The system should maintain counted quantities separately from the current system stock until the applicable stocktake/reconciliation process is completed. Mobile users should not directly overwrite the stock balance.
Requests Module
The Requests module should provide field users with a centralized area to initiate and track applicable requests such as Asset Transfer Request, Maintenance Request, Asset Return, Disposal Request or other configured Asset360 processes.
The available request types should be returned by the server based on role and configuration. Each request should show its current status and approval progress where applicable.
This module should integrate with the central Asset360 Workflow & Approvals engine rather than implementing independent approval logic inside the mobile application.
Tasks Module
The Tasks module should consolidate work assigned to the logged-in user. This can include audits, maintenance jobs, asset verification, receiving activities, approvals where mobile approval is enabled, or other actionable assignments.
Tasks should be categorized into Pending, In Progress, Overdue and Completed. Each task should carry a Module/Transaction Type so selecting it navigates directly to the corresponding operational screen.
For example:
Task: WO-000125 → Maintenance Work Order
Task: AUD-0028 → Asset Audit
The landing-page My Tasks cards should use the same task service.
Notifications
The notification icon should display application alerts relevant to the logged-in user. Notifications can include Work Order Assignment, Approval Required, Request Approved/Rejected, Audit Assignment, PM Due, Stock/Reorder alert where permitted, and other configured events.
Selecting a notification should deep-link the user to the associated transaction wherever possible.
Read/unread status should synchronize with the server so that the mobile and web application maintain a consistent notification state where applicable.
Sync Module
The Sync module is particularly important because Asset360 should support both online and batch/offline operation.
The screen should show:
Connection Status | Last Successful Sync | Pending Uploads | Downloaded Changes | Failed Transactions | Conflicts
The user should be able to select Sync Now. Synchronization should also occur automatically according to configured rules.
For offline assignments, the mobile device should download only the permitted working dataset rather than the complete Asset360 database.
Offline Mode
When connectivity is unavailable, the application should automatically switch to Offline Mode where supported. The header should clearly indicate that the user is working offline.
The application should use an encrypted local database containing the user's downloaded assignments, permitted asset records, relevant masters and other required information. Transactions created offline should enter a local Sync Queue.
Each offline transaction should contain a unique transaction ID, user, device, date/time, affected record, transaction type, original server version and changed information.
When connectivity returns:
Mobile Queue → Sync API → Authentication → Validation → Conflict Check → Asset360 Business Service → Central Database → Mobile Confirmation.
Successful transactions should be removed from the pending queue only after server acknowledgement.
Settings Module
The Settings screen should contain mobile-specific user configuration rather than the full Asset360 system administration functionality.
It can include Profile, Language, Sync Preferences, Offline Storage, Scanner Configuration, RFID Reader Configuration, Printer Configuration, Notification Preferences and About/Application Version, according to permissions and device capability.
RFID readers and mobile printers should be paired/configured here where supported. For example, an authorized user may select the Zebra mobile printer used for Asset360 label printing.
More Menu
The More menu should provide access to less frequently used functionality so that the landing page remains uncluttered. Depending on permissions, this could include Documents, Service History, Spare Parts, Suppliers/Service Providers, Approvals, Reports/Dashboards, Help, About and Logout.
The developer should make this menu configuration-driven. A customer-specific mobile deployment should therefore not require redesigning the landing page simply because a module is disabled.
Bottom Navigation
The mobile application should maintain a persistent bottom navigation bar for the most common functions:
Home | Scan | Central Scan Action | Assets | Profile
The large central Scan button should be available from most operational screens because physical identification is a core Asset360 mobile function.
The back button should always return the user to the logical previous step without unexpectedly clearing a partially completed transaction.
Role-Based Mobile Modules
The landing page must be dynamically generated according to the logged-in user's role. A Maintenance Technician, for example, might primarily see Assets, Maintenance, Tasks and Scan. An Asset Auditor could see Assets, Audit, Stock Take and Tasks. An Asset Manager could receive Assets, Receive, Transfer, Audit, Requests and additional functions.
This should be driven by:
User → Role → Module Permission → Action Permission → Organization/Data Scope.
Permissions must come from the same Roles & Permissions configuration used by the Asset360 Web Application.
Web and Mobile Integration
The developer should treat the mobile application as another client of the same Asset360 platform:
Asset360 Web Application↘API Gateway / Authentication Layer→ Asset360 Business Services→ Central Database↗Asset360 Mobile Application
Online mobile transactions should therefore become immediately visible on the web application. A received asset created through mobile should appear in Asset Management; a completed Work Order should appear in Maintenance; an audit scan should update Audit progress; and a transfer should appear in the Asset 360° movement history.
Master data should flow primarily in the opposite direction:
Web Administration → Central Master Data → APIs/Sync → Mobile Application.
This includes Companies, Business Units, Departments, Cost Centers, Locations, Asset Groups, Classes, Categories, Subcategories, Statuses, Conditions, Criticalities, Suppliers, Service Providers and other controlled lists.
Developer Design Principle
The mobile application should be built around reusable services and components rather than developing each module independently. Common components should include Authentication, Asset Search, Barcode/QR/RFID Scanning, Camera/Photo Capture, Document Upload, Location Selection, Master-Data Dropdowns, Asset 360° View, Workflow Submission, Label Printing, Notifications, Offline Database and Synchronization.
The overall operational architecture should be:
Login → Retrieve User Permissions → Landing Page → Select Module/Task → Scan/Search → Retrieve Asset/Transaction → Execute Field Activity → Validate → Submit Online OR Store Offline → Synchronize → Central Asset360 → Update Web Application → Audit & History.
This approach will make the Asset360 Mobile Application a controlled field execution layer of the Web platform, with one common asset record, one set of master data, one security model, one workflow engine, and one transaction history across both applications.
